# 8.2 结项回答：TrainCache 为什么用 etcd

结论：TrainCache 继续用 etcd，不自研 Raft。mini-Raft 这一个月的产出是对共识协议的理解，代码不进生产。三条工程理由按能核对的证据给：TrainCache 用到 etcd 的哪些能力、etcd 实测到的优势、自研付掉的代价。数字都取自 `docs/8.1` 的五轮对拍。

## 一、TrainCache 用到 etcd 的六件事，mini-Raft 只做得到两件

TrainCache 不直接调 etcd，读写全部经 apiserver 落到 etcd。它用到的六件事和 mini-Raft 的对应情况：

| TrainCache 用到的 | mini-Raft 有没有 | 差在哪 |
|---|---|---|
| watch：informer 收到事件才做协调 | 没有 | 日志只往 Follower 复制，没有向客户端推变更的通道 |
| 版本号乐观并发：状态写带版本，冲突就重试 | 没有 | 写是无条件覆盖，条目进来直接进日志 |
| Lease 选主：定期续租，租约过期说明上一个主死了 | 没有 | 租约只在服务端用来做一致性读，不暴露给客户端 |
| 请求大小上限是个能查的常量 | 有 | 三道上限：value 1MiB、key 1KiB、请求体 4MiB |
| 按 key 精确读 | 有 | 读接口形状对得上 |
| ConfigMap 的列举 | 没有 | 没有列举，也没有前缀查询 |

缺的四项里，watch 和 Lease 决定控制器怎么跑：收到事件才做事，续租失败就把主让出去。要补 watch，服务端得记住每个客户端读到哪了并持续推给它；mini-Raft 的一条复制消息只在写路径上由发送方串行发出，没有长期连接。要补 Lease，得给客户端一个带过期时间的键空间，过期由服务端判，等于在 KV 之外再做一套定时器。六件事里四件做不了，自研省下的东西立刻又要还回去。

## 二、etcd 比手写 Raft 好在哪，这轮量到的

| 好在哪 | 数字 |
|---|---|
| Follower 上的写也直接回 200，客户端不用自己找主 | etcd 200、6.3ms；mini-Raft 503 带主节点地址、0.19ms |
| Follower 上的线性一致读也能接 | etcd 200、0.64ms；mini-Raft 503、0.11ms |
| 主节点上的线性一致读快 | etcd 0.38ms，mini-Raft 17.0ms，差 45 倍 |
| 写路径也更快 | etcd 5.6ms，mini-Raft 16.9ms，差 3 倍 |
| 杀主后请求由服务端兜住，重试不都落在客户端 | etcd 2 发失败、2 次换地址；mini-Raft 13 发失败、13 次换地址 |
| 被隔离的主节点自己下台 | etcd 隔离窗口 8/8 次采样不认主；mini-Raft 8/8 次仍自认主 |
| 隔离一台非主节点不引起换届 | etcd 任期 +0、解冻后不换届；mini-Raft 任期 +3、解冻后换届一次 |

两边选举耗时差不多，日志里的当选时刻中位数在 1.0 到 1.2 秒。不可用时间 mini-Raft 1276ms 比 etcd 的 2166ms 短，差在客户端重试：mini-Raft 的 Follower 立刻回 503 带主节点提示，客户端每次失败就换地址，新主一出现就接上；etcd 的一发写压在死进程上，2 秒超时才回话。这一格 mini-Raft 占优，代价是 13 发写要客户端自己重试，etcd 只有 2 发。

还有一格反着来。旧值读 mini-Raft 100 发全读到新值，etcd 37 发落后一条。原因是 mini-Raft 的线性读几乎每发都走确认轮，确认轮把新的提交点带给所有 Follower；etcd 的 `serializable` 读直接读本地。这一格 mini-Raft 占优，代价已经算在主节点读的 45 倍差里。

恢复的正确性两边都过：杀主后全量读回 155 个 key，已回执却丢的两边都是 0。mini-Raft 五轮里有两轮各出现 1 条「没回执却读得到」，写入在杀主前进了日志并提交、回话丢了；etcd 的超时那一发没进日志，读不回来。两种结果都在「写可能已生效、客户端不知道」的范围内，不构成丢数据。

这轮没测、只列出来的能力：watch、条件写、Lease、前缀列举、快照与补发的多年回归，以及压缩、整理、备份三个运维命令。backend 配额 2147483648 字节判不补，mini-Raft 没有这一层。

## 三、自研花掉了多少

实现 5771 行非测试 Go 代码，25 个文件；测试 12866 行、34 个文件，测试是实现的 2.2 倍。对拍客户端另算，4 个文件 1733 行。41 条裁决记在五份 decisions 文档里，`docs/` 里 2986 行。18 次提交，2026-10-06 到 2026-11-06，一个人。

最贵的一项是测试占比：测试行数是实现的 2.2 倍，故障注入分 `kill -9`、冻结、单向切断、掉电落点四组，改一行选举代码要把四组全跑一遍。etcd 自己的测试占比这轮没量，这条对比算未验证。

读数还要付口径成本，这轮花在三处：靠 value 里的序号倒推提交情况，会把没回执的写算成没提交的数据，改成每发一个 key 才数得准；etcd 的 5 个进程逐个等就绪永远过不去，多数派要三个，必须先全拉起来；etcd 的出站连接源地址是 127.0.0.1，按地址切流量会漏，必须给每台一个网络命名空间。每加一种读数，这类核对就要重来一次。

## 四、什么条件下值得自己写

四条同时成立才动手，有一条不成立就买现成的。

第一，需要的能力能列全，而且缺的项数不超过已有的项数。TrainCache 这边是 2 比 4，缺的比有的多，不成立。只需要强一致 KV 加快照的嵌入式场景，清单三行写完，成立。

第二，手里有一条现成方案满足不了的硬约束，而且能写成数字。能成立的形式是「单请求必须到 32MiB」「跨三地往返 80ms 下写延迟要低于 5ms」「共识必须嵌进已有进程，不能多起一个服务」。撞上限就换布局的不算：TrainCache 遇到过大的状态明细，解法是把大的那张表挪去对象存储，改数据放哪里比改复制协议便宜得多。

第三，把自研当长期承诺，愿意每次改动重跑故障注入和一致性检查，而且这套门禁有人守。这轮的比例是参考：测试 12866 行对实现 5771 行。守不起的，第三个月开始就在攒没人验证的补丁。

第四，目标是学会这套协议，或者复制协议本身就是产品差异所在。数据库内核、跨地域复制存储、自定义一致性语义的中间件属于后半条。

TrainCache 对这四条的答案：第一条 2 比 4；第二条有便宜得多的解法；第三条机时预算在数据面，不在共识引擎；第四条存储不是它的产品。四条都不成立，所以继续用 etcd。
