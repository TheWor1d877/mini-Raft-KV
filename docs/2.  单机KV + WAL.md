先不碰分布式，做一个单机版本：

## 流程
1. 实现一个内存 KV 存储（`map[string]string` 加锁即可）
2. 加入WAL：在Put写入之前先追加写，再改动内存中的map
3. 启动时候重新WAL恢复状态，用crc32(Castagnoli)校验识别损坏的尾部记录，将坏尾直接裁剪
4. Get根据key找value，key不存在返回`ErrKeyNotFound`（空串value与不存在可区分）

## WAL日志
日志记录格式 len ￨ crc32 ￨ entry
crc32覆盖len + entry的全部内容
entry的格式为 op ￨ keylen ￨ key ￨ vallen ￨ value，字段宽度与上限见 2.1 §5

## fsync
Put默认按照64为一个批次进行fsync，不依赖OS主动fsync

## 数据目录
默认数据放到进程工作目录下的 `data/`，命令行与配置可覆盖

wal文件名用零填充递增序号：00000001.wal(八位)
单个wal文件限制100MB大小

写新的wal文件先以临时名字创建(O_EXCL)，立刻rename成正式名，之后的追加全部落在正式名上
rename 在 POSIX 上是原子的，这是“文件级原子提交”的标准手法。临时名只覆盖创建那一瞬，为什么不能全程用临时名见 2.3 D13

LOCK文件用flock(fd, LOCK_EX | LOCK_NB)实现,排他锁、非阻塞。启动时先拿锁。防止两个进程同时写同一 WAL 导致损坏的

整体结构：
```text
data/
  CURRENT              # 指向当前活跃 WAL 文件名（可选，单文件时可省）
  wal/
    000001.wal         # 按序号递增的 WAL 文件
    000002.wal
  LOCK                 # 进程独占锁，防止两个进程同时打开同一目录
```

## 错误码
定义哨兵错误 + var包装,包括不限于：
```go
var (
    ErrKeyNotFound   = errors.New("key not found")
    ErrCorruptRecord = errors.New("corrupt record")
    ErrIO            = errors.New("io error")
    ErrLocked        = errors.New("data dir locked")
    ErrTooLarge      = errors.New("entry too large")
)
```
整体要求：
调用方用 errors.Is 判断类别，不要匹配字符串。
需要携带细节时用 fmt.Errorf("...: %w", ErrCorruptRecord) 包装，保留类别可判断性。

细节要求：
key 不存在是正常控制流，不是异常
坏记录的错误里要带偏移量（offset=12345），否则排障时不知道坏在哪。
IO错误的时候要拿到底层syscall.Errno，包装的时候将原始 error也使用%w写入进去

## 日志字段
使用zap作为结构化日志
日志输出位置：`data/log/`
字段名统一使用小写下划线来做
通用字段：
1. ts: 时间戳
2. level: 级别
3. msg: 消息正文
4. component: 可选字段: wal / kv / recovery

## 取舍与话术
bbolt使用Cow页做崩溃安全能替代WAL，在当前场景下完全能覆盖
但是本项目不使用这个，原因：
这个项目的目标是把 WAL 和恢复链路自己走一遍，bbolt 会把这一层完全藏起来
写路径完全被 bbolt 的事务模型接管，它的写事务是串行化的，我原本想验证的‘追加写 + 批量 fsync 的吞吐取舍’就没法按自己的方式做
本项目设计出来就是为了“论证”，如果使用bbolt，整个恢复过程变成黑盒，无法查看恢复链路

etcd 的 pkg/wal 并不是一个设计给外部项目直接引用的通用库，它的整个生命周期是围绕 etcd 的 Raft 状态机设计的，而不是一个“你给它字节、它帮你安全追加”的通用日志。所以外部使用不了
