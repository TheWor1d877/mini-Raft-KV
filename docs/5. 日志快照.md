日志无限增长会吃满磁盘，重启时 replay 时间也扛不住。使用日志快照对日志进行压缩：将当前状态机保存为快照，然后丢弃掉快照之前的日志。

## 压缩触发

压缩时间：可以手动触发，或者日志达到最大数量触发。

快照不能频繁触发，扫状态机、写大文件、fsync，开销远大于普通日志复制。

快照不能并发写，两个快照同时写会浪费 IO、互相竞争；更严重的是可能基于不同时刻的状态各写一份，文件/元数据指针互相覆盖，恢复时可能选到不一致的那份。

## 删除边界

压缩逻辑：默认删除到 `min(snapshotIndex, safeIndex)`，其中 `safeIndex` 是所有成员中最小的 commitIndex，即 `min(matchIndex[peer])`。

`matchIndex[peer]`：leader 确认该 follower 已经复制成功的最高日志 index（即 follower 的 lastLogIndex 在 leader 视角下的下界）。

加一点按照字节数兜底，防止每条字节都很大，条目还没到阈值，但是内存压力已经很大了。

Leader apply 落后：快照点被 applyIndex 卡住，日志删不动，这是背压，要告警 + 治理 apply 慢，不要放宽删除边界。

## 豁免规则

豁免规则：落后 Leader CommitIndex 超过阈值（设置为 1000 条记录）的，算 `min(snapshotIndex, safeIndex)` 时不需要考虑他们，恢复的时候用快照 + 进几条记录恢复。

被豁免后开启倒计时，超过 5min 就自动降级为 learner。

别豁免要在 log 中报警，而不是静默状态。

## 删除操作与崩溃恢复

删除操作：先写入 tmp 快照，然后 fsync，将快照 rename，之后再删除日志字段。

崩溃恢复以“快照文件 + 元数据指针”为准，残留旧日志 replay 时跳过 `<= snapshotIndex` 的条目，从 `snapshotIndex+1` 开始。

## 落点与恢复顺序

合并之后日志是唯一的恢复源，快照是旧日志能丢的依据：`raft/wal/` 里的条目被快照覆盖之后，那段日志不再承担恢复责任，丢不丢它由快照文件与元数据指针决定。

快照落点 `<data-dir>/raft/snapshot/`，文件名带快照 index，元数据指针落 `raft/state` 那一类的原子重写小文件里，记 `snapshotIndex` 与 `snapshotTerm`。快照 index 只能取 `lastApplied` 与 `commitIndex` 之间的值：快照点之后的条目还在日志里，没有理由提前丢。

恢复顺序：

1. 读元数据指针与快照文件。指针缺字段或文件不存在时按「没有快照」起。
2. 读快照重建状态机。
3. 回放 `raft/wal/` 里 index 大于 `snapshotIndex` 的条目，直到 `lastApplied`。
4. `(lastApplied, commitIndex]` 继续补 apply 并写回游标。

快照与日志的落盘边界仍按 `3.1` 的口径：日志的落盘边界在追加那次 `Sync()` 上，快照文件自己的 `Sync()` 与 `rename` 是它的一次提交；两份文件都写坏时以日志为准，日志能独立重建到 `lastApplied`。

## Learner 降级与恢复

Learner：Raft 中的非投票成员，它会接收日志复制、跟上最新状态，但不参与选举投票，也不计入 quorum。

成员配置在 Raft 中是一条特殊日志条目，Leader 将 X 降级到 learner 写入日志复制给所有的节点，每个节点收到这条日志后，更新自己本地的成员配置视图。

恢复成 voter 本质还是一样走日志复制。
