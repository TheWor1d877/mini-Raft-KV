# 8. 与 etcd 对拍

## 一、这一步拿什么

同一串操作、同一组故障时序，分别打给 mini-Raft 和 etcd 3.7.0，把两边的结果逐格摆在一起，差异逐条落到一条机制或一个默认值上。产出是无故障行为对照表、故障恢复对照表、外加每轮的原始记录目录。结项那三条工程理由只能引用这里量出来的数字，引用不出来的写法作废。

比三样东西，每样都定了通过标准。

| 比什么 | 怎么记 | 通过标准 |
|---|---|---|
| 返回值 | 每条操作的状态码、响应体的键集合、`code` 字符串、给不给 Leader 提示 | 键集合的差异要能指回一条设计决定 |
| 顺序 | 同一个 key 是第几次写、两边的日志序号（`index` 与 `revision`）、任期 | 同一条写在两边各占一格，序号推进节奏一致 |
| 恢复快照 | 故障后把写过的 key 全量读回，逐条比对 | 已回执的写一条不能少；没拿到 200 却读得到的写单独计数，出现即记录 |

## 二、跑之前配平三件事

拓扑对称：5 个 etcd 进程对 5 个 mini-Raft 进程，同一个二进制、各自独立 `--data-dir` 与端口、不起容器（D11）。

参数配平：下面这组默认值不对齐，重选耗时和写放大两格的数字就没有可比的意思。

| 参数 | etcd 3.7.0 | mini-Raft | 对拍前的动作 |
|---|---|---|---|
| 心跳 | 100ms | 100ms | 已同 |
| 选举超时 | 默认 1000ms | 默认 500ms | 两边都是 [T, 2T) 随机（`raft.go:418`、`3.1` §6）。驱动显式给成同一个基线 1000ms：`--election-timeout 1000`、`-election-timeout-ms 1000` |
| 快照阈值 | `snapshot-count` 10000 | 默认 1000 | 驱动给成 10000：`-snapshot-entries 10000`。`auto-compaction-mode` 是 periodic 而 `retention` 默认 0s，等于不自动压缩，压缩策略另测一格 |
| Pre-Vote | 默认开 | 无（`3.3` 已定不实现） | 差异直接归到这一条机制：隔离单台非主节点 6 秒，mini 任期涨、etcd 不涨（`docs/8.1`） |
| 每次提交 Sync | bbolt `NoSync: false`，每次提交 Sync backend | raft 日志 Sync 一次，state 游标按批 | 两侧各自的 Sync 次数进归因表，不计入实现质量（D6、D11） |
| 单请求上限 | `max-request-bytes` 1572864 字节；gRPC 单次消息上限 2097152 字节 | value 上限 1048576 字节、key 上限 1024 字节、请求体上限 4194304 字节 | 两边各造 1MiB、1MiB+1、1572864、1572865、2MiB、4MiB 六档 value，逐档记状态码 |
| backend 配额 | 2147483648 字节 | 无 | 判不补：mini-Raft 没有 backend 这一层，TrainCache 也不会写到 2GiB |

装置相同：两边用同一套动作，`kill -9`、`SIGSTOP`、按方向切断，注入时刻写进记录。每轮把两边的版本、启动参数、端口逐条列进记录，缺任一项该轮作废。

## 三、etcd 侧的取法与起法

etcd 3.7.0 的官方发布包在这台机器上取不到（GitHub 发布直连不通），用 go module 源码自己编，依赖走 `goproxy.cn` 补齐。产物在 `~/tools/etcd-v3.7.0/etcd`，36545975 字节，`--version` 回 `etcd Version: 3.7.0`。换机器要重编，编法记录在本节末。

JSON 端点靠 gRPC-Gateway，`--enable-grpc-gateway` 默认值就是 true（`embed/config.go:567`），客户端口同时收 HTTP，`/v3/kv/put` 与 `/v3/kv/range` 的 key 和 value 是 base64 字符串（D9）。起法有一条坑：只给 `--initial-cluster` 不给 `--initial-advertise-peer-urls` 会在 bootstrap 直接 fatal，报成员表里的地址与 advertise 地址不一致，所以每个进程的三个 URL 都要显式给。

编法走过两条死路：`go install go.etcd.io/etcd/v3/cmd/etcd@v3.7.0` 报顶层模块里没有这个包；`go install go.etcd.io/etcd/server/v3@v3.7.0` 因该模块的 `go.mod` 里有 replace 指令被拒。可用的是自己包一层 main 调 `etcdmain.Main`。

```bash
mkdir -p /tmp/etcdbuild && cd /tmp/etcdbuild
printf 'module probe\n\ngo 1.23\n\nrequire go.etcd.io/etcd/server/v3 v3.7.0\n' > go.mod
printf 'package main\n\nimport (\n\t"os"\n\n\t"go.etcd.io/etcd/server/v3/etcdmain"\n)\n\nfunc main() { etcdmain.Main(os.Args) }\n' > main.go
GOPROXY=https://goproxy.cn,direct GOSUMDB=off GOFLAGS=-mod=mod go build -o etcd .
```

## 四、五种负载怎么打

`docs/1` 定的五种负载，逐格写成两边各返回什么。

单键 Put/Get：一个 key 写 20 次，每次 value 带递进序号，读完把两边的序号序列并排。这一格同时给无故障基线的单条写延迟与单条读延迟。

批量写：mini-Raft 没有批量入口，这一格按 N 次单条发比，两边发同一串。一次事务提交多 key 归第六节的能力格。

读到旧值：在 Leader 上任满一个租约窗口后 `SIGSTOP` 冻住 Leader，同时用两个客户端分别走 `consistency=local` 与 `serializable=true`，看两边的旧值窗口各有多长，再与线性一致档对照——线性一致档这一格必须要么读到新值要么超时。

客户端重试：同一条写重发两次，用递进序号看它生效几次。两边都没有幂等 id：mini-Raft 的 `req_id` 是服务端自增序号，客户端传不进去；etcd 每次写占一个 `revision`。预计两边都是占两格，把这格钉住的证据是序号与 `index`／`revision` 的推进。

Leader 切换时的写：以 100ms 节奏持续发写，中途 `kill -9` 当前 Leader，记四件事——失败开始时刻、写恢复时刻、期间返回的状态码集合、以及恢复前后各 key 的最终值。etcd 侧的当选时刻取它日志里的角色变更行，mini-Raft 侧沿用 `leader_failover.sh` 的口径（新 Leader 的 `role changed`）。

## 五、四组故障时序

同一故障时刻打到两边，比的是恢复轨迹的形状。

| 故障 | 打给 etcd | 打给 mini-Raft | 记 |
|---|---|---|---|
| Leader `kill -9` | 进程级 SIGKILL | 同一信号，同一条 bash 语句发出 | 不可用窗口、`raft_term` 增量、已回执写的读回结果、日志里的当选时刻 |
| Leader `SIGSTOP` 4000ms 再 `SIGCONT` | 同一信号 | 同一信号 | 冻住期间的写与一致性读结果、解冻后旧 Leader 是否下台 |
| 主节点隔离 6000ms（1 对 4） | 在它自己的网络命名空间里按对端地址切 | 按成员地址成对切 | 少数派的写失败时刻、多数派的当选时刻、被隔离者解冻前是否仍自认主 |
| 单台非主节点隔离 6000ms | 同上 | 同上 | 被隔离者自己的任期增量（Pre-Vote 那格） |

隔离装置两边不一样，原因是回环地址上的源地址选择。mini-Raft 的出站连接绑自己的地址，按地址成对切就切干净。etcd 的出站 peer 连接只绑端口，源地址由路由选成 127.0.0.1，对端回包是「对端成员地址:992x → 127.0.0.1:临时端口」；同一个网络命名空间里按地址切不中这一路（按对端地址全向切会把成员之间的流量一起切掉），按端口切又只挡住一端。所以 etcd 侧每台一个独立网络命名空间，用 veth 接进 10.20.0.0/24 的网桥，隔离规则下在被隔离那台自己的命名空间里执行，进出都按对端成员地址封。客户端走网桥地址 10.20.0.1，不是成员地址，照常打得到被隔离的那台。整套装置只在本轮 `unshare -rn` 的网络命名空间里，主机上其它 etcd 进程不受影响。

Pre-Vote 那格从第四行出：不实现 Pre-Vote 的每一轮选举超时都给自己加一次任期，带了 Pre-Vote 的预投票拿不到多数就不加。第三行同时给另一件事：etcd 的 CheckQuorum 让被隔离的主节点在等不到多数派回执时下台，mini-Raft 没有这条检查，解冻前一直自认主。

## 六、两类格与归因规则

行为格：同一操作两边都给结果，必须跑、必须归因。归因写到一条具体机制或一个具体默认值，写到这里为止；归不出的记「未归因」并进本文件的 TODO，留成一条待查项。

能力格：mini-Raft 决定不做的功能，只列 etcd 提供什么、TrainCache 用不用得上，不跑。下面这些格已经在各阶段决定里挂过号。TrainCache 实际用到的 etcd 能力六项、mini-Raft 缺其中的哪四项，对照在 `docs/8.2` 第一节。

| 格 | 出处 |
|---|---|
| 每次提交 Sync backend | D6、D11 |
| key/value base64 与 JSON 形状 | D9 |
| 非 Leader 写与读的转发 | D18、D24、`3.3`、`4.1` §9 |
| Pre-Vote 与任期膨胀 | `3.1` §9、D22 |
| 一致性读复用心跳、读索引放 `header.revision` | D25、`4.1` §4 |
| 地址表静态与成员动态增删 | D37、`6.2` §5 |
| 一次一条配置变更对 joint consensus | D38、`6.2` §5 |
| WAL 记录头格式 | D2、`2.3` |
| 条件写、租约 TTL、watch、串行读、备份与压缩工具 | `docs/1` 的能力清单那一格 |

## 七、跑的顺序与记录

整轮十一档，顺序是 `topology`、`single`、`batch`、`stale`、`retry`、`bigvalue`、`freeze`、`partition`、`prevote`、`failover`、`readback`。前六档无故障，出第一张表；中间四档各一种故障，出第二张表；`readback` 把这一轮写过的 key 全量读回。读数与归因落在 `docs/8.1`，结项回答落在 `docs/8.2`。

一条命令复跑整轮：`ETCD_BIN=~/tools/etcd-v3.7.0/etcd scripts/parity.sh`。脚本自己编 `bin/miniraft-node` 与 `bin/miniraft-parity`，两侧各起 5 个进程：mini-Raft 在 127.0.0.11-15 的 8801-8805 上；etcd 每台在自己的网络命名空间里，地址 10.20.0.21-25 的 9801-9805 上，peer 口 9901-9905。两边心跳 100ms、选举基线 1000ms、快照阈值 10000。含 `partition` 或 `prevote` 时整轮先 `exec unshare -rn`，iptables 规则只作用于本轮进程，主机上 kind 那套 etcd 不受影响。逐档打同一串操作，在同一个时刻对两边的 Leader 动手，最后全量读回。收尾走 `trap`，两侧进程各自按清单 SIGTERM，`kill -9` 之后的数据目录留在本轮目录里看现场。

只跑某几档：`STAGES="partition prevote" scripts/parity.sh`。取分布：整轮跑五次，再 `bin/miniraft-parity -phase stats -aggdir data/parity -rounds 5` 把最近五轮的 `summary.tsv` 合并成 `phase`、`field`、`n`、`min/median/max`。

每轮一个目录 `data/parity/<时间戳>/`，`mini` 与 `etcd` 各一份数据根。文件按档位分：`ops-<kind>.jsonl` 每操作一行，字段 `ts_client_ms`、`ts_client_done_ms`、`phase`、`op`、`key`、`value_seq`、`status`、`index`、`term`、`revision`、`leader_hint`、`code`、`latency_us`、`note`；`topology.txt` 记两边的二进制路径、启动参数、地址表、数据目录、客户端绑的源地址与 etcd 是否在独立命名空间，缺任一项该轮作废；`topology-<kind>.txt` 记响应体的键集合与非 Leader 回话；`expect-<kind>.json` 记每个 key 发过哪几发、哪几发拿到 200；`bigvalue-<kind>.txt`、`failover-<kind>.txt`、`readback-<kind>.txt` 各记一档；`summary.tsv` 汇总所有档位的读数。

一致性检查按序号做：每个 key 读到的序号必须单调不减，且读到的值必须落在它发起读之前已写入的区间内。读回档逐条判两件事——拿到 200 却读不回来的是丢条，没拿到 200 却读得回来的是幽灵条；杀主档每一发写占一个独立 key，这两件事各自能数出来，不靠序号前缀推。
