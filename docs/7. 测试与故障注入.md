# 测试与故障注入

## 比对什么
每个已确认的写用唯一 key，恢复后逐条读回，一条都不能丢。另外统计没拿到 200 却存在的写：超时允许出现，收到 503 之后出现即失败。四条安全性单独检查：每 term 至多一个 leader、同 index 的 term 与命令一致、commitIndex 与 lastApplied 不回退、已提交前缀不消失。隔离 leader 后强一致读必须 503 或超时，`consistency=local` 只记录。现有 `crash_inject.sh` 只覆盖单节点持久性，`leader_failover.sh` 只看 200 不比对值。

## 杀进程
5 节点按角色杀。leader 杀在 fsync 前后、apply 前后、配置变更提交前后，看确认写是否丢失、lastApplied 能否追平、配置能否从日志恢复。follower 杀在收 AppendEntries 中、装快照中、回放日志中连续三次，看能否补齐、临时文件是否清理、恢复是否幂等。candidate 杀在拉票中途，确认同一 term 不出现两个 leader。最后整集群同时杀，看能否选出 leader 并恢复全部已提交写。写路径和拉票窗口只有毫秒级，要加暂停开关才能稳定停进去。

## 网络和时钟
用每节点前的 TCP 代理或 iptables 按方向切断，补多数派隔离、少数派隔离、leader 单向失联两个方向。包级补延迟、丢包、重复、乱序；延迟要超过 `rpcTimeout()`（默认 100ms），重复和乱序放在内存夹具的注入队列里。分区跨多轮选举时记录 term 增长速度。实现没有在线多数派检查，隔离后的旧 leader 要记下强一致读开始拒绝、以及收到更高 term 的两个时刻。

时钟跳变不影响租约，租约走进程启动后的单调时钟。测租约用 `SIGSTOP` 冻结 leader。默认租约窗口 450ms 小于读超时 1000ms，租约不会命中；先把选举超时调到 1500ms 以上，确认日志出现 `read served by lease`。冻结分 500ms 和 4s 两档，分别看旧 leader 是否下台。墙钟前后跳各跑一轮，只确认快照触发时间受影响。

## 成员变更和快照
隔离 voter 并把降级阈值调小，等 leader 自动降级。5 节点逐个隔离最多降到 2 个 voter，再往下手动降级，记录 voter 与 learner 数量和配置 index。配置变更进日志但拿不到多数派回执时杀 leader，新 leader 要恢复同一份配置，双多数派仍成立。

快照 leader 侧三处已测，补安装侧：装到一半杀，看临时文件和指针是否同进同退；leader 在 follower 落后时删日志前缀，看 follower 收到快照还是缺头的日志；同一 follower 连续装两次，看第二次是否受残留影响。专测“state 已写、快照文件和指针未写”的窗口，看节点能否启动并追上快照点，这一项同样要暂停开关。传输期间保持写入，装完后接上新日志，不跳段、不重复 apply。磁盘补写满、fsync 返回 EIO、只读挂载、尾记录截断四种。真掉电记为未覆盖，`kill -9` 只代表进程崩溃。

## 负载与记录
并发客户端、读写混合、超时重试、热键带序号逐条比对。每项故障至少 5 轮，记随机种子和故障时刻，另跑一轮无故障基线。每轮一个目录，汇总记确认写、恢复后读到、丢失、未确认却存在四类条数，以及 503 与超时数、重选耗时、不可用窗口、term 变化；每节点记角色、term、commitIndex、lastApplied、日志尾部 index 与 term。客户端历史带 id、序号、起止时间、返回码，供 toxc 做线性一致检查。

## 边界和顺序
不测 Byzantine 与消息篡改，不做跨机房、动态地址表、joint consensus。分三批：先补现有脚本的比对，再做 TCP 代理与 `SIGSTOP`，最后做成员变更和快照安装的叠加；前一批读数稳定再开下一批。

# 故障注入流程表

| 故障类型                                | 注入方法                                                 | 理论上恢复后状态                                                                   |
|-----------------------------------------|----------------------------------------------------------|------------------------------------------------------------------------------------|
| 节点崩溃（leader、follower、candidate） | 暂停开关 + `kill -9`，按角色与窗口取点                   | 已回执的写不丢；日志由 leader 补齐；同 term 不出现两个 leader                      |
| 网络分区（多数派、少数派隔离）          | 代理或 iptables 按方向切断                               | 多数派侧选新 leader，旧 leader 写失败；少数派隔离时原 leader 继续提交              |
| leader 单向失联                         | 只断一个方向，两个方向各跑一次                           | 发不出时 follower 重选、旧 leader 下台；收不到时写无法提交，租约过期后拒绝强一致读 |
| 包级故障（延迟、丢包、重复、乱序）      | 代理延迟超过 `rpcTimeout()` 100ms；夹具注入队列          | 超时重试，过期回执被忽略；收敛到一致日志，不重复 apply                             |
| 节点冻结（500ms、4s）                   | `SIGSTOP` 后 `SIGCONT`，长档先把选举超时调到 1500ms 以上 | 短档不重选；长档选新 leader，旧 leader 下台并拒绝强一致读                          |
| 时钟跳变                                | `date -s` 前后跳各跑一轮                                 | 只改快照触发时间与日志时间戳，选举与租约不变                                       |
| 自动降级叠加分区                        | 隔离 voter，调小降级阈值                                 | 降到 2 个 voter 仍可提交；恢复后 learner 追平，需手动提升                          |
| 快照安装崩溃                            | 暂停开关 + `kill -9`，覆盖 state 窗口与传输期写入        | 节点能启动；临时文件清理；接上新日志，不跳段、不重复 apply                         |
| 磁盘故障（写满、只读、EIO、尾截断）     | 小 tmpfs、remount、文件系统注入、截断段文件              | 写入报错不产生半条记录；截断时回退上一条完整记录或明确报错                         |


1. 节点崩溃
   让一个节点在关键时刻被 `kill -9`。leader 在写盘前后被杀，看客户端已经收到 200 的写会不会丢；在 apply 前后被杀，看重启后应用进度能不能追上提交进度。follower 在收日志、装快照、回放日志时被杀，看它回来能不能补齐、临时文件有没有清掉。candidate 在拉票中间被杀，看同一个 term 会不会出现两个 leader。这些窗口只有毫秒级，要先加暂停开关，把进程停在指定位置再杀。

2. 网络分区（多数派、少数派隔离）
   把 5 个节点切成两拨，互相连不上。leader 被切到只有 2 个节点的那拨，另外 3 个会选出新 leader，旧 leader 写不进新数据。反过来把 2 个 follower 切走，leader 这边还有 3 个，写照常提交。看的是两拨各自能不能写，以及恢复后旧 leader 会不会下台。

3. leader 单向失联
   只断一个方向。leader 发得出去、收不到回执：follower 收不到心跳，会选新 leader，旧 leader 看到更高的 term 后下台。leader 收得到、发不出去：follower 照常收到心跳，不会选新 leader，写永远凑不齐多数派，客户端一直超时。旧 leader 的租约过期后，强一致读要返回 503 或超时。两个方向结果相反，各跑一次。

4. 包级故障
   在代理上给包加延迟、丢包、重复、乱序。延迟要超过 `rpcTimeout()`，默认 100ms，否则请求在超时前就回来了，测不到过期回执的处理。重复和乱序放在内存夹具里做，字节代理做重复会把 HTTP 帧打乱。看的是超时重试后日志能不能收敛、同一条命令会不会 apply 两次、过期回执会不会被当成新请求。

5. 节点冻结
   用 `SIGSTOP` 冻住 leader 的进程，模拟长时间 GC 或虚拟机暂停。短档冻 500ms，不到选举超时，其他节点不会选新 leader。长档冻 4s，其他节点会选新 leader，解冻后旧 leader 必须下台，强一致读必须拒绝。默认租约窗口 450ms 比读超时 1000ms 短，租约一次都不会命中，测之前先把选举超时调到 1500ms 以上，并确认日志里出现 `read served by lease`。

6. 时钟跳变
   改系统时间，看 Raft 会不会受影响。租约用的是进程启动后的单调时钟，改墙钟不影响选举和租约，只影响日志时间戳和快照最小间隔的判断。跑这一轮是确认代码里没有别的地方用墙钟。

7. 自动降级叠加分区
   隔离一个 voter，把降级阈值调小，让 leader 把它降成 learner，这期间多数派还要能写。5 个节点逐个隔离，最多降到 2 个 voter，再往下要手动降级。恢复后被降级的节点以 learner 身份追数据，不会自动变回 voter。看的是 voter 和 learner 各剩几个、配置 index 停在哪、只剩 2 个 voter 时还能不能提交。

8. 快照安装崩溃
   leader 侧的三处提交点已经测过，这里测 follower 装快照。装到一半被杀，看临时文件有没有清理、指针和正式文件是不是一起出现。重点测 state 已经写好、快照文件和指针还没写的那个窗口，这时重启可能起不来，也可能用旧日志重放出旧状态。还要测装快照期间继续写入，装完后能不能接上新日志、不跳段、不重复 apply。这个窗口太短，同样要暂停开关。

9. 磁盘故障
   写满、只读挂载、fsync 返回 EIO、尾记录截断。前三种让写盘失败，看节点是明确报错，还是把半条记录留在盘上。尾记录截断是杀掉进程后把段文件末尾截掉几个字节，重启看能不能认出半条记录，回退到上一条完整的记录，或者直接报错。fsync 注入做不了就记未覆盖。真掉电没有装置，`kill -9` 只代表进程崩溃，不代表掉电。
