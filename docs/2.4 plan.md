## 沉默腐蚀型逻辑专项

本模块没有金额、权限、分页那类逻辑，会烂掉的是下面这些。每项都要有不变量断言，不能只靠「跑通了」。

| 逻辑 | 会怎么烂 | 专项测试策略 |
|:---|:---|:---|
| 批次计数器与 `Flush` | 滚动、失效、Close 之后计数不归零或对不上已写偏移，导致该 Sync 的没 Sync | 不变量：`Sync` 时的文件偏移 ≥ 已返回成功的记录末尾偏移；在滚动点、Close 前、失效后三个位置各断一次 |
| 坏尾截断位置 | 截多了丢正常数据，截少了下次恢复再撞上同一条 | 断言截断后重开一次成功、二次重开不重复截断；对账「写入条数 = 恢复条数 + 丢弃条数」 |
| 追加序与 map 生效序 | 失败分支或并发下 map 出现 WAL 里没有的键 | 每轮用例结束把 map 与 WAL 逐条对账；并发跑完再对账 |
| 幂等重放 | 客户端重试后统计口径变化、`op_seq` 空洞 | 同 key 同 value 连发 10 次，断言 map 与重放一次的结果一致 |
| crc 覆盖范围 | 有人把校验范围改成只盖 entry，`len` 翻转就检不出 | 单测专门翻 `len` 的每一个 bit（32 次），断言全部判坏 |
| 文件命名与排序 | 序号不做零填充，字符串排序下 `10.wal` 排在 `2.wal` 前面，恢复顺序错 | 造 12 个文件断言按序号排序；恢复后的键值等于按序重放的结果 |
| 目录锁生命周期 | Close 没释放、进程崩溃后 flock 由内核释放但代码里自己留了标志位挡住重启 | 崩溃后直接重启能拿到锁；Close 后二次 Open 成功 |
| 时间与时区 | 日志 `ts` 混用本地时间和 UTC，跨机对不上 | 断言 `ts` 为 UTC RFC3339 |
| 配置默认值 | 默认路径、默认批次大小在多处硬写，改一处漏一处 | 默认值只从 `config.go` 出，测试比对三处引用同一常量 |

## 覆盖判断

| 区域 | 当前判断 | 不足时的补充 |
|:---|:---|:---|
| 记录编解码与 crc | 已覆盖（T6） | — |
| 追加与批量 fsync 的落盘语义 | 已覆盖（T7） | 优先级低：不同 `O_APPEND` 与显式偏移两种写法的差异 |
| 恢复与坏尾 | 已覆盖五种坏尾（T10） | 坏尾后再有正常数据的人为构造已补，断言连同其后全部丢弃 |
| 并发 | 已覆盖（T11 里 1 秒 `-race` 读写混合） | 更长的负载留给 T18 |
| 崩溃恢复 | 已覆盖 | 滚动途中被杀、未提交临时段残留两种时机已进 T13；磁盘真满造不出来，追加失败用只读 fd、Sync 失败用管道代替（D5） |
| HTTP 边界 | 已覆盖 | 并发 `req_id` 唯一性与响应—日志一致性两条断言都在 `http_api_test.go` |
| 目录锁跨文件系统 | 不适用 | 按 D8 划在范围外 |
| 压缩与快照 | 不适用 | 本期不做（D7） |
| 与已有模块的回归 | 不适用 | 本模块是第一个，无既有模块可回归；从 M3 起每步都要跑全量 `go test ./...`，防止新代码改坏旧用例 |
| 长时间运行 | 缺失 | T18：10 分钟连续写，观察文件增长与重启耗时，数据进 `docs/0` |

## 风险

- 一周里 M7 最容易被挤掉，但它是 `docs/1` 要的对拍。M0~M6 做完就先跑 M7 的最小版本（单键那一格），别等 M8。
- 批量 fsync 的丢写窗口只在掉电时兑现，`kill -9` 实测一条不丢：直观预期会落空两次，一次是以为进程被杀就丢数据，一次是以为不丢就说明批量 Sync 安全。出现解释不了的丢写，先查批次计数器和 `Sync` 时机，别先怀疑 crc。
