# 5.1 日志快照设计

## 1. 模块定位

负责：把状态机写成快照文件并原子提交，按边界删除日志前缀，给落后成员补发快照，启动时先读快照再回放日志。

不负责：成员配置变更与 learner 降级的实现（doc 6）、故障注入矩阵（doc 7）、etcd 对拍（doc 8）。doc 5 基线里与 learner 相关的规则由 doc 6 承载。

合并之后 raft 日志是唯一的恢复源，日志只增不减：重启要全量回放，磁盘占用随写入条数线性涨（`2.1` §9）。快照是旧日志能丢的依据。快照落 `<data-dir>/raft/snapshot/`，文件名带快照 index，元数据指针落 `raft/snapshot/current.json`，记 `snapshotIndex` 与 `snapshotTerm`（5.3 D31）。

快照 index 只能取 `lastApplied` 与 `commitIndex` 之间的值：快照点之后的条目还在日志里，没有理由提前丢。

## 2. 架构概览

```text
internal/raft/snapshot.go    快照的生成、原子提交与读回，元数据指针的读写
internal/raft/compact.go     删除边界的计算与日志前缀删除
internal/raft/install.go     接收对端发来的快照
internal/raft/wal.go         日志视图增加基线 index，支持按 index 删前缀
internal/kvstore/kv.go       状态机导出与整体替换两个入口
```

一次压缩要过的路径：判定触发条件 → 选快照点 → 锁内取出状态机全量键值 → 锁外写快照文件并改名 → 锁内更新元数据指针 → 算删除边界 → 删日志前缀 → 写 `state` 游标。

落后成员补齐走另一条路径：Leader 发现某成员的复制游标落到自己日志基线以下 → 发 `POST /raft/install-snapshot` → 该成员把状态机整体替换成快照内容 → 更新本地游标与指针 → 删除本地日志前缀。

## 3. 包结构与依赖方向

- 允许：`internal/raft` → `internal/kvstore`。
- kvstore 的导出面增加两个方法与一个类型：`Snapshot() []Entry` 导出全量键值，`Restore(entries []Entry)` 整体替换状态机，`type Entry struct { Key, Value string }`。快照文件的字节编码在 raft 侧做，kvstore 不认快照的 op 值。
- raft 侧新增三个文件，职责按 §2 分开：`snapshot.go` 只管快照文件与指针，`compact.go` 只管边界与删除，`install.go` 只管接收路径。
- 禁止：`internal/kvstore` 引用 `internal/raft`。

## 4. 核心接口

```go
// snapshot.go
type Snapshot struct {
    Index   uint64 // 快照点对应的日志 index
    Term    uint64 // 该 index 处的 term
    Entries int    // 快照里的键值条数
    Bytes   int64  // 快照文件字节数
    Checksum uint32 // 整份文件的 crc32c
}

func (s *snapshotter) create(index, term uint64, entries []kvstore.Entry) (*Snapshot, error)
func (s *snapshotter) load() (*Snapshot, []kvstore.Entry, error)

// compact.go
func (n *Node) safeIndex() uint64
func (n *Node) dropLogPrefix(index uint64) error

// install.go
type InstallSnapshotReply struct {
    OK bool `json:"ok"`
    SnapshotIndex uint64 `json:"snapshot_index"`
}
func (n *Node) handleInstallSnapshot(index, term uint64, body []byte) (InstallSnapshotReply, error)

// node.go
func (n *Node) TriggerSnapshot() (index uint64, err error)
```

`Transport` 接口加一个方法 `InstallSnapshot(to string, index, term uint64, body []byte) error`，`3.1` §4 的接口定义同步加这一行。内存 transport 的实现走同一个 `handleInstallSnapshot`。

契约：

| 方法 | 输入输出 | 错误语义 | 并发与幂等 |
|:---|:---|:---|:---|
| `snapshotter.create` | 快照点 index 与 term、状态机全量键值 | 写文件或改名失败返回 `ErrIO`；改名之前失败不留正式名文件 | 调用方保证同一时刻只有一个快照在生成；写文件期间不持 `Node` 的锁 |
| `snapshotter.load` | 无 | 指针文件不存在、字段缺失、快照文件缺失或校验不符，一律按「没有快照」返回 | 启动路径上调用一次 |
| `safeIndex` | 无 | 不返回错误 | Leader 取全部成员的 `matchIndex` 最小值，豁免中的成员不参与（§7）；Follower 取本地 `commitIndex` |
| `dropLogPrefix` | 要保留的第一条 index | `ErrIO`；删到一半失败返回错误，已删的段不恢复 | 只删 index 之前的条目与整段文件，保留的那一段截到它的帧起点 |
| `handleInstallSnapshot` | 请求 index、term 与快照文件字节 | 快照文件校验不符返回 `ErrCorruptRecord`；请求 index 不大于本地快照点或小于本地 `lastApplied` 返回成功 | 收到的 index 不大于本地快照点时直接返回成功，不改状态机 |
| `TriggerSnapshot` | 无 | 非 Leader 返回 `ErrNotLeader`；快照点选不出来（`lastApplied` 为 0）返回 `ErrStateMismatch` | 手动触发入口，与自动触发走同一条路径 |

HTTP 路径：

| 路径 | 请求 | 响应 | 出错 |
|:---|:---|:---|:---|
| `POST /raft/snapshot` | 无 | `{"ok":true,"snapshot_index":12,"entries":34}` | 非 Leader 503 `not_leader`；快照点选不出来 409 `state_mismatch`；写盘失败 500 `io_error` |
| `POST /raft/install-snapshot?index=&term=` | 请求体是快照文件的原始字节 | `{"ok":true,"snapshot_index":12}` | 缺 query 参数 400；快照文件校验不符 500 `corrupt_record`；写盘失败 500 `io_error` |

`statusFor` 加一条 `ErrStateMismatch` → 409 `state_mismatch`，其余 code 沿用 `2.1` §4 的既有集合。

补发快照走 HTTP，不引 gRPC（5.3 D32）。

两条路径与 `/put`、`/get` 共用同一个监听端口（`3.1` §4）。

## 5. 数据格式

快照文件是 8 字节 magic 加 4 字节条目数，后面接一串帧：

```text
MRSNAP01                    8B magic
entries                     4B 键值条数，大端
frame                       len 4B | crc32c 4B | payload
payload                     op 1B(=0x20) | keylen 4B | key | vallen 4B | value
```

帧头与 crc 复用 `kvstore.EncodeFrame`／`DecodeFrame`／`CheckFrame`，`len` 覆盖 `len` 字段与 payload 全部字节。`op` 取 `0x20`（5.3 D34）：raft 日志条目用 `0x10`，快照记录用 `0x20`，两个目录互读都判坏记录，沿用 `wal.go` 里「op 值不重叠，读错目录立刻判坏」的做法。快照记录与 KV 条目同形，语义是状态而不是操作，所以 op 值不同。

元数据指针 `raft/snapshot/current.json` 是一行 JSON：

```json
{"snapshotIndex":12,"snapshotTerm":3,"entries":34,"bytes":4210,"checksum":1836472}
```

`checksum` 是整份快照文件的 crc32c：文件损坏时指针能判出来，不靠回放出错的状态机。写入方式与 `state` 小文件同款：临时名写入 → Sync → rename → Sync 父目录（`3.1` §5）。

日志视图增加基线。压缩之后日志的第一条不再是 index 1，`wal` 结构体多两个字段：`baseIndex` 是视图第一条的 index，没有快照时是 1；`baseTerm` 是 `baseIndex-1` 那一格（快照点）的 term，没有快照时是 0。`entryAt(index)` 按 `index - baseIndex` 取下标，`index < baseIndex` 表示这条已经不在本地日志里。删前缀时被删掉的最后一条如果正好落在新的 `baseIndex-1` 上，它的 term 就进 `baseTerm`；落在更早就说明本地已经不认得那一格，`baseTerm` 由拿着快照点 term 的调用方写（生成快照与接收快照两条路径都在删完之后补这一格）。

复制请求的 `prevLogIndex` 取 `nextIndex-1`，压缩之后它会落在 `baseIndex-1` 上：本地日志里没有这一格，`prevLogTerm` 直接用 `baseTerm`。接收方同样压缩过日志时，`prevLogIndex` 等于本地快照点、`prevLogTerm` 等于本地快照 term，按对上处理，条目从快照点之后接着追加。

恢复扫描不再要求第一条的 index 是 1：有快照时，日志从 `snapshotIndex+1` 起必须连续，第一条晚于 `snapshotIndex+1` 就是洞，判 `ErrStateMismatch`；早于它的残留条目由快照覆盖，扫描时跳过，视图的基线仍落在 `snapshotIndex+1`。没有快照时第一条必须是 1。

## 6. 目录与配置

```text
data/node-1/
  LOCK                        目录锁，一节点一目录，由 `kvstore.Open` 持有，覆盖 `raft/`
  raft/
    state                     原子重写小文件，装四个标量
    wal/00000001.wal          八位零填充递增序号，100MB 滚动
    snapshot/
      current.json            元数据指针，记 snapshotIndex 与 snapshotTerm
      00000012.snap           快照文件，文件名带快照 index
  log/miniraft-node.log       结构化日志
```

快照文件写临时名再改名：`00000012.snap.tmp` 写完 Sync 之后改名成正式名。启动时 `*.tmp` 删掉，它不是提交点。

| 开关 | 默认 | 含义 |
|:---|:---|:---|
| `-snapshot-entries` | `1000` | 上次快照点之后的日志条数达到该值触发一次快照；`0` 表示关掉自动触发 |
| `-snapshot-bytes` | `64MB` | 日志目录字节数超过该值也触发一次快照，防止每条字节很大时条数迟迟不到阈值 |
| `-snapshot-min-interval-ms` | `60000` | 两次快照的最小间隔，防止连续触发 |
| `-snapshot-exempt-entries` | `1000` | 落后成员落后多少条之后豁免出 `safeIndex` 的计算（doc 5 基线 §豁免规则） |

不设 `-snapshot-disabled` 这个开关：手动入口任何时候可调，自动触发由上面两个阈值控制，两个阈值都为 0 时自动触发全关。

`Config` 增加的字段：`SnapshotEntries uint64`、`SnapshotBytes int64`、`SnapshotMinIntervalMS int64`、`SnapshotExemptEntries uint64`。

## 7. 关键流程

启动恢复（doc 5 基线 §落点与恢复顺序）：

1. 读元数据指针与快照文件。指针缺字段、文件不存在或校验不符时按「没有快照」起。
2. 读快照重建状态机。
3. 回放 `raft/wal/` 里 index 大于 `snapshotIndex` 的条目，直到 `lastApplied`。
4. `(lastApplied, commitIndex]` 继续补 apply 并写回游标。

崩溃恢复以「快照文件 + 元数据指针」为准，残留的旧日志 replay 时跳过 `<= snapshotIndex` 的条目，从 `snapshotIndex+1` 开始。

生成与提交（doc 5 基线 §删除操作与崩溃恢复）：

1. 锁内选快照点：index 取 `min(lastApplied, commitIndex)`，term 取该 index 处的 term。`lastApplied` 为 0 时没有快照点。
2. 锁内导出状态机全量键值，锁外写快照文件：临时名写入 → Sync → 改名 → Sync 父目录。导出走 kvstore 自己的读锁，与快照点在同一段持锁内完成，导出的内容正好是快照点那一刻的状态。
3. 锁内更新元数据指针（临时名 → Sync → rename → Sync 父目录）。
4. 锁内写 `state` 游标。
5. 算删除边界并删除日志前缀。

指针更新在删日志之前：崩溃停在两步之间时，指针指向新快照，日志前缀还在，重启按 §恢复顺序跳过 `<= snapshotIndex` 的条目，结果一致。指针更新之前崩溃时，磁盘上多一个没有指针指向的快照文件，启动时按指针恢复，那份文件删掉。

删除边界（doc 5 基线 §删除边界）：

- `safeIndex` 是所有成员中最小的 `matchIndex`，即 `min(matchIndex[peer])`。`matchIndex[peer]` 是 Leader 确认该成员已经复制成功的最高日志 index。
- 删除到 `min(snapshotIndex, safeIndex)`。
- Leader 的 `safeIndex` 取全部成员的 `matchIndex` 最小值，自己算一个成员。Follower 没有 `matchIndex`，取本地 `commitIndex`。
- 字节数只作触发条件，不改删除边界。

豁免（doc 5 基线 §豁免规则）：

- 某个成员的 `matchIndex` 落后 `commitIndex` 超过 `-snapshot-exempt-entries` 条时，它不参与 `safeIndex` 的计算。
- 豁免发生时在日志里报警，记成员 id、落后条数与 `commitIndex`，不静默处理。
- 豁免之后该成员靠快照补齐：Leader 发现复制游标落到自己日志基线以下时发 `POST /raft/install-snapshot`。
- 豁免成员的倒计时降级为 learner 归 doc 6（5.3 D33）：豁免后开始倒计时，超过 5 分钟降级。doc 6 写降级与恢复的规则：成员配置是 Raft 里的一条特殊日志条目，Leader 把某个成员降级为 learner 时写入日志并复制给所有节点，各节点收到后更新自己的成员配置视图；learner 接收日志复制、不参与投票、不计入 quorum；恢复成 voter 同样走日志复制。

接收快照：

1. 校验 magic、条目数与 crc32c，任一项不符返回 `ErrCorruptRecord`。
2. 请求 index 不大于本地快照点，或小于本地 `lastApplied` 时直接返回成功，不改状态机。
3. 锁外把快照内容解成键值对，锁内整体替换状态机。
4. 把 `lastApplied` 推到快照 index，`commitIndex` 取本地值与快照 index 的较大者，写 `state` 游标。
5. 写本地快照文件并更新指针，删除本地日志中 `<= snapshotIndex` 的条目。

触发（doc 5 基线 §压缩触发）：

- 手动：`POST /raft/snapshot`。
- 自动：`Tick()` 里判定，上次快照点之后的条数达到 `-snapshot-entries`，或日志目录字节数达到 `-snapshot-bytes`，并且距上次快照超过 `-snapshot-min-interval-ms`。
- 同一时刻只生成一个快照：判定与快照点选取在锁内完成，状态机导出与写文件在锁外进行，锁外期间用快照状态位挡住第二次触发。
- Leader apply 落后时快照点被 `lastApplied` 卡住，日志删不动：删除边界停在快照点之前，这一轮一条不删。这是背压，触发一条告警并治理 apply 慢，不放宽删除边界。

## 8. 不变式

1. 快照 index `<= lastApplied <= commitIndex`。
2. 指针里的 `snapshotIndex` 与快照文件对应，文件缺失或校验不符时按没有快照起，不按部分快照起。
3. 恢复时 `index <= snapshotIndex` 的日志条目不进状态机。
4. 同一时刻一个节点只生成一个快照。
5. Leader 删除日志前，该 index 已被全部成员复制；被豁免的成员除外。
6. `lastApplied` 永不领先 `commitIndex`。
7. 状态机内容与快照内容一致：快照点之后的条目按日志回放，快照点之前的状态只从快照来。
8. 快照文件里的内容对应它的 `snapshotIndex`：导出与快照点在同一段持锁内完成。

## 9. 风险与约束

- 快照写盘开销大：扫状态机、写文件、fsync 三步都比普通日志复制贵。阈值与最小间隔两个参数控制触发频率，快照触发期间节点的写延迟会抬高。
- 快照文件占用磁盘与日志同等量级：压缩省掉的是日志前缀，代价是快照文件本身。键值很多时快照文件可能比省下的日志还大。
- 状态机导出需要加接口：`kvstore.KV` 现在只有 `Apply` 与 `Get`，没有全量导出的入口。
- 崩溃窗口有三个：快照文件写到一半（临时名文件，启动时删掉）、指针更新前（旧快照仍在指针上，新快照文件没有指针指向，启动时删掉）、删日志途中（指针已更新，日志前缀部分删除，重启按指针跳过）。
- 落盘边界沿用 `3.1` 的口径：日志的落盘边界在追加那次 `Sync()` 上，快照文件自己的 `Sync()` 与 `rename` 是它的一次提交。快照文件与日志都写坏时以日志为准，日志能独立重建到 `lastApplied`；日志前缀已经删掉的节点只剩快照这一份，快照损坏即不可恢复。
- 落后成员补快照是一次整文件传输：快照越大传输越久，期间该成员不参与提交之外的复制。
- Pre-Vote 与 leadership transfer 不做，term 膨胀的观测量归 doc 7。

## 10. 日志字段

`component` 取 `raft`，事件名与字段如下：

| 事件 | 字段 |
|:---|:---|
| `snapshot created` | `snapshot_index`、`snapshot_term`、`entries`、`bytes`、`cost_ms` |
| `snapshot committed` | `snapshot_index`、`file` |
| `snapshot installed` | `from_node`、`snapshot_index`、`snapshot_term`、`entries`、`bytes` |
| `wal prefix dropped` | `kept_from_index`、`dropped_entries`、`dropped_segments`、`freed_bytes` |
| `snapshot blocked by apply lag` | `commit_index`、`last_applied`、`lag_entries` |
| `snapshot exemption applied` | `peer_id`、`lag_entries`、`commit_index` |
