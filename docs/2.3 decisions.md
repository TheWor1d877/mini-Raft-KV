# 2.3 单机 KV + WAL 决策记录

D1~D13 对应 `2.1` 里的引用。基线说法来自 `docs/2.  单机KV + WAL.md`，本文只补「为什么这么定」和「后面怎么验」。

## D1 自研 WAL，不用 bbolt

- 背景：`go.etcd.io/bbolt` 是 Go 里现成的崩溃安全存储库，写路径不用自己管。
- 备选：bbolt；自研追加日志；内存 map 不落盘。
- 结论：自研。
- 理由：bbolt 用 COW 页接管了崩溃安全，写事务串行化。本模块要验证的「追加写 + 批量 fsync 的吞吐与丢写取舍」在 bbolt 里没有可调整的位置；恢复也在 bbolt 内部完成，`docs/1` 要的论证拿不出过程数据。
- 影响：帧格式、坏尾处理、恢复扫描都得自己写自己测。
- 替代方案什么时候赢：数据规模超出内存、或者不需要讲 WAL 这一层。
- 验证：T13 的崩溃注入给出一张表（确认条数／已 Sync 条数／恢复条数／重启耗时），另跑一组 bbolt 同负载对照，两个数字都要能报出来。

## D2 不引用 etcd 的 pkg/wal

- 背景：etcd 自带的 `pkg/wal` 是一个现成的复用候选。
- 备选：直接引用；抄它的格式；完全自定。
- 结论：完全自定，格式只作参考。
- 理由：`pkg/wal` 的生命周期围绕 etcd 的 Raft 状态机，接口假设上层给它的是 raft entry 序列，与本模块「给字节、安全追加」的用法对不上；引用它会把 Raft 层的概念提前带进本模块。
- 影响：动手实现时先读它的记录头，把差异写进对拍笔记，不写进代码。
- 验证：T14 之前做一次字段对照，逐字核源码。

## D3 CRC-32C（Castagnoli），校验范围含 len

- 背景：帧是 `len｜crc32｜entry`，标准库两张表都提供。
- 备选：IEEE；只盖 entry；盖 entry 再单存校验文件；换 xxh3 或 sha256。
- 结论：Castagnoli，crc 覆盖 `len` 与 `entry`。
- 理由：`len` 不在校验范围时，长度翻转会让解析跳到错误偏移，后面整段判坏，且报不出真实损坏位置。Castagnoli 和 IEEE 检错能力相当，选它与 etcd 的 WAL 一致，对拍时少一个变量。校验文件方案多一次 IO，不划算。
- 影响：算法一旦写进文件就不能换，换实现前必须确认老文件全是同一张表算的；恢复时同一个文件里多处 crc 失败，先怀疑表选错。
- 验证：T6 里逐 bit 翻 `len`（32 次），再翻 entry 里的位，断言全部判坏；再断言 IEEE 表算出的值与 Castagnoli 不同，防止误用。

## D4 entry 是不透明字节，op 只定义 Put

- 背景：本模块只服务 KV，但后面的 Raft 要拿这套 WAL 做日志存储。
- 备选：WAL 直接存 KV 结构；WAL 存字节、上层自己编码；现在就放 term。
- 结论：WAL 只认字节；kv 层编码 `op｜keylen｜key｜vallen｜value`，`op` 占 1 字节、当前只放 Put。
- 理由：帧格式里不出现 KV 语义，Raft 接手时不用改 WAL；留一个 op 字节，加 Delete 或改快照标记都不动帧。
- 影响：entry 布局与上限见 `2.1` §5，`keylen` 与 `vallen` 都用 4B 大端；key 上限 1KB、value 上限 1MB，超限返回 `ErrTooLarge`，在追加之前就拒掉，盘里不许出现读不出来的记录；空串和「不存在」在编码层可区分，`Get` 靠 map 里有没有键来判。本期不提供 Delete，`docs/1` 的负载里没有它。
- 验证：T6 边界用例（key/value 空串、恰好上限、超上限、`op` 非 0x01、逐字节布局）；T11 断言空串值能被读回。

## D5 fsync 失败按 fail-stop 处理

- 背景：日志追加之后要 Sync；Sync 返回错误时，盘上到底有几次追加是未知的，而客户端可能已经拿到过成功回执。
- 备选：忽略继续；把失败的那条重试；重试后仍失败就停止接受写；整个进程直接退出。
- 结论：日志置失效标志，`Propose` 之后一律返回 `ErrIO`，`Get` 继续，入口层把进程退掉。
- 理由：Sync 失败意味着盘上状态不可知，继续写会在一个不知道边界的文件上追加，把损坏范围扩大。直接退出会让崩溃注入实验分不清是故障还是 bug，所以保留 Get 和日志，由入口层决定退出。
- 影响：写路径只有一处会触发失效——日志追加之后的那次 Sync（`2.1` §7）。客户端必须处理这个错误，重试语义依赖 D4 的幂等；进程不做自动恢复，重启走正常恢复流程。是否置失效标志，只看一条判据：盘上有什么是否已知。滚动时建新段失败，此前的条目已经落盘、边界已知，返回 `ErrIO` 但不置失效标志。`state` 游标文件写失败不进这条链，它只让本次角色转移作废（`3.3` D14）。
- 验证：Sync 失败用段 fd 换成管道（Write 成功、Sync 必返回 EINVAL）钉住：`internal/raft/wal_test.go` 的 `TestRaftLogSyncFailureDisablesWritesOnly` 断失效标志生效、后续写全 `ErrIO`、`Get` 可用、失效原因只报一次、盘上长度不变；`internal/raft/http_rpc_test.go` 的 `TestRaftLogSyncFailureClosesTheWritePath` 断 HTTP 侧只通知入口一次。建新段失败用 `chmod 0555` 挡住 `raft/wal/`：`internal/kvstore/crash_restart_test.go` 的 `TestProcessSurvivesBlockedSegmentCreation` 断进程只回 500、失效标志不置位、权限恢复后继续可写。追加失败（磁盘真满造不出来）用只读 fd 代替。

## D6 fsync 边界：一条写一次 Sync，不设批量阈值

- 背景：每条写都 Sync 最安全也最慢，攒一批 Sync 省系统调用但留出丢写窗口。
- 备选：每条都 Sync；攒固定条数；按时间；按字节；只靠 OS 自己刷。
- 结论：一条写一次 Sync，没有批量阈值，也没有手动 `Flush` 这条路。唯一的开关是 `-raft-fsync=false`，它只跳过 Sync 系统调用，追加照常，给吞吐对照留一档。
- 理由：一条逻辑写要过的边界已经只剩日志追加那一处（`3.1` §7、`3.3` D19），再往上加批次就是把已确认的写留在 page cache 里；客户端等的「已提交」和盘上的「已落盘」由此是同一时刻，`acked` 与 `durable` 之间不再有窗口要解释。
- 影响：写吞吐被 Sync 卡住，D19 的三档对照量的就是这笔代价；掉电与内核崩溃时已确认的写在 Sync 之后，不进丢写窗口。`-raft-fsync=false` 那一档在进程被杀时同样不丢（页缓存归内核持有，重启读同一份文件看得到全部已确认字节），差别只有掉电能兑现，本机造不出掉电，所以那一档只报数、不断言。
- 验证：`scripts/crash_inject.sh` 的三档 `fsync=true` 状态各跑 3 次，`not_durable` 与 `lost` 恒为 0，含 kill 落在第 1 条之后（`docs/0` 崩溃注入表）；`fsync=false` 两档同样 `not_durable 0、lost 0`，是页缓存的证据，不是 Sync 的证据。`internal/raft/wal_test.go` 的 `TestRaftLogFsyncFalseSkipsTheSyscall` 断开关只跳过系统调用。

## D7 不做 CURRENT、不删老文件、文件头不加 magic 和版本

- 背景：多文件日志需要一个「从哪读起」的依据，老文件需要回收。
- 备选：CURRENT 指针；按序号扫目录；滚动时删最老文件；快照后截断。
- 结论：按八位零填充序号扫目录；老文件全部保留；帧头不加 magic 和版本。
- 理由：CURRENT 是又一个需要原子更新的对象，多一处崩溃不一致；扫目录在这个量级成本可忽略。删老文件和截断都属日志压缩，是 `docs/5` 那条线上的事。文件只从约定目录读；magic 检测不出损坏，损坏检测交给 crc。
- 影响：日志只增不减，重启的全量回放时间随段总量线性增长，`scripts/crash_inject.sh` 的 `boot_ms` 量的就是它。日志是唯一恢复源之后，「旧日志能丢」只能靠快照，快照因此从「本期不做」变成压缩的前置工作（`docs/5`、`3.1` §9）。
- 验证：恢复只依赖文件名排序，用例在 `internal/raft/wal_test.go`；`TestRaftLogRollsOverWithContiguousSeq` 断老文件仍在、段号连续；增长曲线那一格见 `2.2` §5 的 T18 缺失项。

## D8 数据目录用工作目录相对路径

- 背景：进程要在开发机和 CI 上都能不准备环境就跑起来，默认路径的选择决定这一点。
- 备选：固定绝对路径；相对当前工作目录；只接受命令行传入。
- 结论：默认 `./data`，命令行和配置可覆盖，日志落在 `./data/log`。
- 理由：文件系统根下的路径普通用户没有写权限，测试和 CI 跑不过；相对工作目录让 CI 无需准备环境，命令行覆盖留给测试注入临时目录。
- 影响：文档、脚本、CI 三处必须用同一个默认值，配置改一处就要改齐；测试用例统一用 `t.TempDir()`，工作目录保持干净。`flock` 的独占语义在本地盘和 bind mount 上成立，退化发生在 NFS 与某些网络块存储上，测试与 CI 跑在本地盘（runner 本地盘），不做容器卷实验。
- 验证：T5 配置用例断言缺省值、覆盖值和非法值三种；CI 里跑一遍不建目录也能通过。

## D9 内存 map 全量常驻，本期不设上限

- 背景：恢复要把所有记录重放进 map。
- 备选：设条数上限并拒绝写；分片落盘；LRU 淘汰；不管。
- 结论：不管，作为假设写进文档。
- 理由：本模块的数据量由测试脚本控制，量级在内存装得下的范围内；上限和淘汰是压缩那条线上的事，跟 D7 一起留给以后。
- 影响：结论里必须带上数据量假设，面试官问到「数据超内存怎么办」就答「本期没做，压缩和淘汰是后续模块」；重启耗时随日志长度线性增长，`scripts/crash_inject.sh` 的 `boot_ms` 给数字。
- 验证：`scripts/crash_inject.sh` 每次跑都出 `boot_ms`（进程起来到就绪），从 1 条到 1000 条恢复量的三档都在 9.5~10.7ms，看不出回放的增量；这条曲线要单独计时才拿得到，见 `2.2` §5 的缺失项。

## D10 进程入口用 HTTP JSON，不引 gRPC

- 背景：崩溃注入和 etcd 对拍都要外部驱动进程，得有一种调用入口。
- 备选：HTTP JSON（stdlib `net/http`）；stdin 行协议；只做库、测试里起子进程；gRPC。
- 结论：HTTP JSON，`POST /put`、`GET /get`，状态码映射见 `2.1` §4；不引 gRPC。
- 理由：对拍要把同一份操作序列分别打给 mini-Raft 和 etcd，只有两边都能收 HTTP，客户端脚本才是一份代码两个地址；etcd 开 gRPC-Gateway 后收 JSON，代价是它的 key/value 在 JSON 里是 base64，脚本各写一层编码。stdin 做并发压力别扭，还要另写客户端；只做库跑不了对拍那一格；gRPC 要带 protoc 工具链和生成代码，超出这一周的预算。
- 影响：客户端路径的 handler 是 `internal/raft/rpc.go` 的 `NewHandler`，只做参数校验、错误映射和 `req_id` 生成，角色判断、复制与提交都在 `Node` 里；日志字段多一个 `req_id`。两个进程入口共用这同一份 handler。
- 验证：T12 的状态码映射断言在 `internal/raft/http_rpc_test.go`（`TestGetContractTwoConsistencyModes`、`TestIllegalRequestsGetTheirOwnStatusCode`、`TestNotLeaderHintKeysStayWhenLeaderUnknown`），T14 的脚本对两边发同一组请求。etcd 侧 JSON 端点的路径和 base64 约定，动手实现时对着官方文档核实。

## D11 etcd 对照起 5 节点集群

- 背景：mini-Raft 是 5 节点，对照环境的节点数要不要一致。
- 备选：etcd 单节点；etcd 5 节点；引第三方托管 etcd。
- 结论：一个二进制用脚本起 5 个 etcd 进程，各配独立 `--data-dir` 与端口，开 `--enable-grpc-gateway`，不起容器，拓扑与 mini-Raft 对称。
- 理由：对拍要讲「同样的操作、同样的故障」，节点数不一致时，多数派行为、leader 切换耗时、写放大都没有可比性。单节点 etcd 只能对拍 API 语义，`kill -9` 一格直接失去意义。托管实例拿不到进程控制权，注入不了故障。
- 影响：M7 需要一份起 5 个 etcd 与 5 个 mini-Raft 的脚本，一台机器上 10 个进程，内存和磁盘要留量；etcd 版本写进对拍记录，取当时的稳定版。etcd 默认每次提交都 Sync backend，这条差异要单独归因（D6）。
- 验证：T14 的记录里两边各自的拓扑、版本、启动参数逐条列出，缺任何一项，该次对拍不算有产出。

## D12 共识层的小状态用重写式小文件，日志序列用追加式日志

- 背景：doc 3 要持久化 `currentTerm`、`votedFor`、`log[]`、`commitIndex`、`lastApplied`，全都落本地盘。
- 备选：五样都进本模块 WAL；`currentTerm` 与 `votedFor` 各用一个小文件、`log[]` 用 WAL；接一个嵌入式 KV 存这五样。
- 结论：`log[]` 用追加式日志：帧头与 crc 口径复用本模块导出的 `EncodeFrame`／`DecodeFrame`／`CheckFrame`，落盘对象是 `data/node-N/raft/wal/` 那一份 WAL，KV 的写不再另存一份；`currentTerm`、`votedFor`、`commitIndex`、`lastApplied` 四个标量共用一个 `*.tmp` + rename 的原子重写小文件（`3.3` D14、D15）。
- 理由：按访问形状分。只增、重启时按序重放才知道最新值的，用追加日志；体量几十字节、任何时候都要直接读到最新值的，用重写文件。Raft 要求投出这一票之前 `votedFor` 已经落盘，小文件同步写在这条路径上直白；塞进 WAL 就得靠重放才知道当前值，白花时间还容易出错。
- 影响：D4 的字节布局就此冻结，term 放进日志记录自己的头字段里，不改帧；`raft/wal/` 与 `raft/state` 两个文件的读写、滚动、坏尾裁剪、截断与恢复扫描都归 `internal/raft`，本模块对外只到帧与 entry 的编解码这一层（`3.1` §3）。状态机侧只剩内存 map，一次改动由 `kv.Apply` 承担（`2.1` §4）。
- 验证：doc 3 设计时按这条划分写文件清单（`3.1` §5、§6）；帧契约固定为「给字节、按序读回」，用例在 `internal/raft/wal_test.go`。恢复链只有一条：重启后 map 由日志回放重建，`internal/raft/recovery_test.go` 断两路恢复（回放 `[1, lastApplied]` 与补 apply `(lastApplied, commitIndex]`）拼出的 map 等于写入终态。

## D13 临时名只覆盖创建那一瞬，段文件全程用正式名接收写入

- 背景：基线写的是「新 wal 文件先写临时名字，写完再 rename」，而 §6 同时要求恢复时忽略并删除 `*.tmp`。
- 备选：全程用临时名接收写入、写满或关闭才改名（基线原意）；创建之后立刻改名，之后只用正式名。
- 结论：建段以 `NNNNNNNN.wal.tmp` 打开（`O_EXCL`），随即 rename 成正式名，所有追加落在正式名上。
- 理由：两条要求同时成立时，前一种写法等于把活跃段里的每条记录都判成可丢弃：进程崩溃时该段还是临时名，恢复按 §6 删掉它，丢的是整段（上限是段上限默认 100MB），而写路径的边界是一条一次 Sync、已确认的写一条都不能丢（D6）。改成创建即改名，`*.tmp` 只覆盖「文件已创建、名字尚未提交」这一瞬，残留的文件只可能是 0 字节，删掉不丢数据；段内的半条记录仍由 §5 的坏尾裁剪处理，`*.tmp` 的处理与坏尾裁剪各管一段。
- 影响：滚动日志里的 `to_file` 就是正式名；rename 依赖 POSIX 原子性（与 D8 同源）。恢复删 `*.tmp` 发生在扫描之前，上次的残留挡不住 `O_EXCL`。
- 验证：`internal/raft/wal_test.go` 的 `TestRaftLogRemovesTmpResidue`（残留 tmp 被删、活跃段回到真实最大序号）与 `TestRaftLogRollsOverWithContiguousSeq`（段号连续、`*.tmp` 不残留）；进程级那一格由 `scripts/crash_inject.sh` 的 `stale_tmp` 列与 `internal/kvstore/crash_restart_test.go` 的段目录断言钉住。
