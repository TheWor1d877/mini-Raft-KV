# 2.3 单机 KV + WAL 决策记录

D1~D13 对应 `2.1` 里的引用。基线说法来自 `docs/2.  单机KV + WAL.md`，本文只补「为什么这么定」和「后面怎么验」。

## D1 自研 WAL，不用 bbolt

- 背景：Go 生态里 `go.etcd.io/bbolt` 提供崩溃安全存储，写路径不用自己管。
- 备选：bbolt；自研追加日志；内存 map 不落盘。
- 结论：自研。
- 理由：bbolt 用 COW 页把崩溃安全整层藏起来，写事务串行化，本模块要验证的「追加写 + 批量 fsync 的吞吐与丢写取舍」没有下手的地方；恢复链路变黑盒，`docs/1` 要的论证拿不出数据。
- 影响：帧格式、坏尾处理、恢复扫描都得自己写自己测。
- 替代方案什么时候赢：数据规模超出内存、或者不需要讲 WAL 这一层。
- 验证：T13 的崩溃注入给出一张表（确认条数／已 Sync 条数／恢复条数／重启耗时），另跑一组 bbolt 同负载对照，两个数字都要能报出来。

## D2 不引用 etcd 的 pkg/wal

- 背景：etcd 自带的 WAL 包看着能复用。
- 备选：直接引用；抄它的格式；完全自定。
- 结论：完全自定，格式只作参考。
- 理由：`pkg/wal` 的生命周期围绕 etcd 的 Raft 状态机，接口假设上层给它的是 raft entry 序列，不是一个「给字节、安全追加」的通用库；引用它会把 Raft 层的概念提前拽进本模块。
- 影响：落地时要读它的记录头，把差异写进对拍笔记，不写进代码。
- 验证：T14 之前做一次字段对照，逐字核源码，别凭印象。

## D3 CRC-32C（Castagnoli），校验范围含 len

- 背景：帧是 `len｜crc32｜entry`，标准库两张表都提供。
- 备选：IEEE；只盖 entry；盖 entry 再单存校验文件；换 xxh3 或 sha256。
- 结论：Castagnoli，crc 覆盖 `len` 与 `entry`。
- 理由：`len` 不在校验范围时，长度翻转会让解析跳到错误偏移，后面整段判坏，且报不出真实损坏位置。Castagnoli 和 IEEE 检错能力相当，选它跟 etcd 的 WAL 对齐，对拍时少一个变量。校验文件方案多一次 IO，不划算。
- 影响：算法一旦写进文件就不能换，换实现前必须确认老文件全是同一张表算的；恢复遇到系统性 crc 失败，先怀疑表选错。
- 验证：T6 里逐 bit 翻 `len`（32 次）和翻 entry 若干次，断言全部判坏；再断言 IEEE 表算出的值与 Castagnoli 不同，防止误用。

## D4 entry 是不透明字节，op 只定义 Put

- 背景：本模块只服务 KV，但 WAL 后面要当 Raft 的存储底座。
- 备选：WAL 直接存 KV 结构；WAL 存字节、上层自己编码；现在就放 term。
- 结论：WAL 只认字节；kv 层编码 `op｜keylen｜key｜vallen｜value`，`op` 占 1 字节、当前只放 Put。
- 理由：帧格式里不出现 KV 语义，Raft 接手时不用改 WAL；留一个 op 字节，加 Delete 或改快照标记都不动帧。
- 影响：entry 布局与上限见 `2.1` §5，`keylen` 与 `vallen` 都用 4B 大端；key 上限 1KB、value 上限 1MB，超限返回 `ErrTooLarge`，在追加之前就拒掉，盘里不许出现读不出来的记录；空串和「不存在」在编码层可区分，`Get` 靠 map 里有没有键来判。本期不提供 Delete，`docs/1` 的负载里没有它。
- 验证：T6 边界用例（key/value 空串、恰好上限、超上限、`op` 非 0x01、逐字节布局）；T11 断言空串值能被读回。

## D5 fsync 失败按 fail-stop 处理

- 背景：一批记录攒到 64 条才 Sync，Sync 失败时这批里有已对调用方返回成功的写。
- 备选：忽略继续；把失败的那条重试；重试后仍失败就停止接受写；整个进程直接退出。
- 结论：置失效标志，`Put` 之后一律返回 `ErrIO`，`Get` 继续，入口层把进程退掉。
- 理由：Sync 失败意味着盘上状态不可知，继续写会在一个不知道边界的文件上追加，把 corruption 变大。直接退出会让崩溃注入实验分不清是故障还是 bug，所以保留 Get 和日志，由入口层决定退出。
- 影响：上层客户端必须处理这个错误，重试语义依赖 D4 的幂等；本模块不做自动恢复，重启走正常恢复流程。失效的判据是「盘上有什么是否已知」，不是「写有没有报错」：滚动时建新段失败，之前那批已经 Sync 过、边界已知，返回 `ErrIO` 但不置失效标志。
- 验证：T17 用两种造错方式分开钉住两件事。fsync 失败：把段 fd 换成管道，Write 成功而 Sync 必返回 EINVAL，断言失效标志生效、后续 Put 全 `ErrIO`、`Get` 可用、失效原因只报一次、重启后读到的等于盘上真有的。建新段失败：`chmod 0555` 数据目录下的 `wal/`，断言 Put 返回 `ErrIO` 而失效标志不置位、权限恢复后继续可写、已确认记录一条不少。追加失败（磁盘真满造不出来）用只读 fd 代替，见 M3 的 `wal_append_test.go`。

## D6 批量 fsync 阈值 64 条

- 背景：每条 Put 都 Sync 最安全也最慢。
- 备选：每条都 Sync；攒 64 条；按时间（比如 100ms）；按字节；只靠 OS 自己刷。
- 结论：默认 64 条一批，可配置，`Flush()` 手动强制。
- 理由：基线明确不依赖 OS 主动刷。按条数比按时间好复现，测试能精确算出丢写窗口；字节数要换算 entry 长度，多一层。
- 影响：掉电最多丢最近 63 条已返回成功的写；进程被杀不丢，页缓存归内核持有，新进程读同一份文件仍能看到全部已确认字节，所以这个窗口只有掉电才兑现。这个数字必须出现在 T13 的结论里；对拍时 etcd 侧默认每条 Sync，两边吞吐差要归因到这里，不能混进「实现质量」。
- 验证：T7 用例断言第 64 条前后 Sync 各发生一次；T13 在批次未满时 `kill -9`，实测恢复条数等于确认条数、丢写 0，而未 Sync 的条数落在 `0..63`，最大窗口正好 63 条（`docs/0` 产出表）。命令行 `-fsync=false` 提供「完全不 Sync」这一档，给 T14 的吞吐对照用；它只跳过系统调用，批次计数与 `Flush()` 照常。

## D7 不做 CURRENT、不删老文件、文件头不加 magic 和版本

- 背景：多文件 WAL 需要一个「从哪读起」的依据，老文件需要回收。
- 备选：CURRENT 指针；按序号扫目录；滚动时删最老文件；快照后截断。
- 结论：按八位零填充序号扫目录；老文件全部保留；帧头不加 magic 和版本。
- 理由：CURRENT 是又一个需要原子更新的对象，多一处崩溃不一致；扫目录在这个量级成本可忽略。删老文件和截断都属日志压缩，本期不做，这是范围决定。不加 magic 是因为文件只从约定目录读，加magic 挡不住真正的 corruption，crc 已经在做这件事。
- 影响：WAL 只增不减，重启扫描时间和磁盘占用随写入量线性增长；这是 T18 长时间运行实验要量的东西。
- 验证：T10 断言恢复只依赖文件名排序；T9 滚动用例断言老文件仍在、恢复结果包含全部历史；`2.4` 覆盖判断里那条「长时间运行」补上增长曲线。

## D8 数据目录用工作目录相对路径

- 背景：进程要在开发机和 CI 上都能不准备环境就跑起来，默认路径的选择决定这一点。
- 备选：固定绝对路径；相对当前工作目录；只接受命令行传入。
- 结论：默认 `./data`，命令行和配置可覆盖，日志落在 `./data/log`。
- 理由：文件系统根下的路径普通用户没有写权限，测试和 CI 跑不过；相对工作目录让 CI 无需准备环境，命令行覆盖留给测试注入临时目录。
- 影响：文档、脚本、CI 三处必须用同一个默认值，配置改一处就要改齐；测试用例统一用 `t.TempDir()`，不碰工作目录。`flock` 的独占语义在本地盘和 bind mount 上成立，退化发生在 NFS 与某些网络块存储上，本项目不碰那种卷，CI 跑在 runner 的本地盘，不单独做容器卷实验。
- 验证：T5 配置用例断言缺省值、覆盖值和非法值三种；CI 里跑一遍不建目录也能通过。

## D9 内存 map 全量常驻，本期不设上限

- 背景：恢复要把所有记录重放进 map。
- 备选：设条数上限并拒绝写；分片落盘；LRU 淘汰；不管。
- 结论：不管，作为假设写进文档。
- 理由：本模块的数据量由测试脚本控制，量级在内存装得下的范围内；上限和淘汰是压缩那条线上的事，跟 D7 一起留给以后。
- 影响：结论里必须带上数据量假设，面试被问「数据超内存怎么办」就答「本期没做，压缩和淘汰是后续模块」；重启耗时随 WAL 增长，T18 给数字。
- 验证：T18 的连续写实验记录「记录条数—重启耗时」两个点，超出预期就把它升级为 issue。

## D10 进程入口用 HTTP JSON，不引 gRPC

- 背景：崩溃注入和 etcd 对拍都要外部驱动进程，得有一种调用入口。
- 备选：HTTP JSON（stdlib `net/http`）；stdin 行协议；只做库、测试里起子进程；gRPC。
- 结论：HTTP JSON，`POST /put`、`GET /get`，状态码映射见 `2.1` §4；不引 gRPC。
- 理由：对拍要把同一份操作序列分别打给 mini-Raft 和 etcd，只有两边都能收 HTTP，客户端脚本才是一份代码两个地址；etcd 开 gRPC-Gateway 后收 JSON，代价是它的 key/value 在 JSON 里是 base64，脚本各写一层编码。stdin 做并发压力别扭，还要另写客户端；只做库跑不了对拍那一格；gRPC 要带 protoc 工具链和生成代码，超出这一周的预算。
- 影响：`internal/kvstore/http.go` 只做参数校验、错误映射和 `req_id` 生成，业务逻辑一律留在 kv；日志字段多一个 `req_id`。
- 验证：T12 的 `http_api_test.go` 断状态码映射，T14 的脚本对两边发同一组请求。etcd 侧 JSON 端点的路径和 base64 约定落地时对着官方文档核实，不凭印象。

## D11 etcd 对照起 5 节点集群

- 背景：mini-Raft 是 5 节点，对照环境的节点数要不要一致。
- 备选：etcd 单节点；etcd 5 节点；引第三方托管 etcd。
- 结论：一个二进制用脚本起 5 个 etcd 进程，各配独立 `--data-dir` 与端口，开 `--enable-grpc-gateway`，不起容器，拓扑与 mini-Raft 对称。
- 理由：对拍要讲「同样的操作、同样的故障」，节点数不一致时，多数派行为、leader 切换耗时、写放大都没有可比性。单节点 etcd 只能对拍 API 语义，`kill -9` 一格直接失去意义。托管实例拿不到进程控制权，注入不了故障。
- 影响：M7 需要一份起 5 个 etcd 与 5 个 mini-Raft 的脚本，一台机器上 10 个进程，内存和磁盘要留量；etcd 版本写进对拍记录，取当时的稳定版。etcd 默认每次提交都 Sync backend，这条差异要单独归因，不能混进实现质量（D6）。
- 验证：T14 的记录里两边各自的拓扑、版本、启动参数逐条列出，缺一项这份数据不算产出。

## D12 共识层的小状态用重写式小文件，日志序列复用 WAL

- 背景：doc 3 要持久化 `currentTerm`、`votedFor`、`log[]`，三样东西都落本地盘。
- 备选：三样都进本模块 WAL；`currentTerm` 与 `votedFor` 用独立小文件、`log[]` 用 WAL；接一个嵌入式 KV 存这三样。
- 结论：`log[]` 复用本模块的字节追加，`currentTerm` 和 `votedFor` 各用一个 `*.tmp` + rename 的原子重写小文件。
- 理由：按访问形状分。只增、重启时按序重放才知道最新值的，用追加日志；体量几十字节、任何时候都要直接读到最新值的，用重写文件。Raft 要求投出这一票之前 `votedFor` 已经落盘，小文件同步写在这条路径上直白；塞进 WAL 就得靠重放才知道当前值，白花时间还容易出错。
- 影响：D4 的字节布局就此冻结，term 放进 raft entry 自己的载荷字节里，不改帧；小文件的读写与崩溃安全归 doc 3 那个模块，本模块不实现。
- 验证：doc 3 设计时按这条划分写文件清单；本模块只需保证「给字节、按序读回」这一条契约不变。

## D13 临时名只覆盖创建那一瞬，段文件全程用正式名接收写入

- 背景：基线写的是「新 wal 文件先写临时名字，写完再 rename」，而 §6 同时要求恢复时忽略并删除 `*.tmp`。
- 备选：全程用临时名接收写入、写满或关闭才改名（基线原意）；创建之后立刻改名，之后只用正式名。
- 结论：建段以 `NNNNNNNN.wal.tmp` 打开（`O_EXCL`），随即 rename 成正式名，所有追加落在正式名上。
- 理由：两条要求同时成立时，前一种写法等于把活跃段里的每条记录都判成可丢弃——进程崩溃时该段还是临时名，恢复按 §6 删掉它，丢的是整段（上限 100MB），而 D6 承诺的窗口是最多 63 条。改成创建即改名，`*.tmp` 只覆盖「文件已创建、名字尚未提交」这一瞬，残留的必然是空文件，删掉不丢数据；段内的半条记录仍由 §5 的坏尾裁剪处理，两个机制各管一段。
- 影响：滚动日志里的 `to_file` 就是正式名；rename 依赖 POSIX 原子性（与 D8 同源）。恢复删 `*.tmp` 发生在扫描之前，`O_EXCL` 不会被上一次的残留挡住。
- 验证：`rollover_test.go` 的高序号残留用例（tmp 被删、活跃段回到真实最大序号）与换段前落盘用例；T13 的「`*.tmp` 未 rename」注入时机。
