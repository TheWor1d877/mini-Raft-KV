## 状态持久化
currentTerm、votedFor、log[]这些需要持久化到当前节点上面
currentTerm：当前任期号
votedFor:当前任期内投给的候选人 ID，未投票为空
log[]: Raft 复制日志条目数组

注意： 如果votedFor不持久化，节点重启之后可能同一个任期中投出两票，导致脑裂
原因： 一个term中每个节点最多只能投一票，voted等价承诺我不会投给别人，如果投出两票可能让两个候选都得到“多数派”的支持

## http接口
定义两个接口：`RequestVote`与`AppendEntries`
```text
POST /raft/request-vote
POST /raft/append-entries
```
#### RequestVote 负责选举超时时候的投票
```text
{
  "term": 3,
  "candidateId": "node-2",
  "lastLogIndex": 10,
  "lastLogTerm": 2
}
```
```text
{
  "term": 3,
  "voteGranted": true
}
```
投票触发时机：
若 req.term < currentTerm，拒绝，返回 currentTerm。
若 req.term > currentTerm，更新 currentTerm=req.term，清空 votedFor，转 follower，持久化。
若 votedFor 为空或等于 candidateId。

候选人的最后一条日志至少跟本节点一样新才能投票

#### AppendEntries 负责追加写日志
```text
{
  "term": 3,
  "leaderId": "node-1",
  "prevLogIndex": 9,
  "prevLogTerm": 2,
  "entries": [
    { "term": 3, "index": 10, "command": "set x=1" }
  ],
  "leaderCommit": 8
}
```
相应：
```text
{
  "term": 3,
  "success": true,
  "conflictTerm": null,
  "conflictIndex": 0
}
```
entries=[] 时表示心跳
prevLogIndex=0、prevLogTerm=0 表示从日志头开始。

所有 RPC 回复前都先比较 term。若请求 term 更大，当前节点更新 currentTerm、清空 votedFor、转 follower 并持久化
若本地 term 更大，拒绝请求并返回本地 term。
若请求 term 相等，按角色和日志规则处理。


## 选举超时
所有角色都使用tick来驱动定时器，选举超时在T到2T之间，取 500ms——随机化是防止大家同时发起投票；
每个节点维护一个选举截止时间 electionDeadline。每个 tick 检查当前时间是否超过 electionDeadline。
Leader 使用 tick 驱动心跳定时器，定期发送空 AppendEntries，心跳间隔应显著小于 T，设置成100ms
所有角色都使用 tick，但不同角色检查的定时器不同：Follower/Candidate 检查选举超时，Leader 检查心跳发送周期。
follower 和 candidate 在选举超时后发起或重新发起选举

重置选举超时时间的方式：
收到当前 Leader 的有效 AppendEntries 后，重置选举超时为新的随机值
给候选人投票后，重置选举超时。
自己发起选举时，重置选举超时


## 完整选举流程
Follower 的 electionDeadline 到期，未收到 Leader 心跳或有效 AppendEntries。
Follower 转 Candidate。
currentTerm++。
votedFor = 自己，并立即持久化 currentTerm 和 votedFor。
重置随机选举超时。
并行向其他所有节点发送 RequestVote，携带自己的 term、candidateId、lastLogIndex、lastLogTerm。
自己的一票计入票数。

处理响应：
若响应 term > currentTerm，更新 currentTerm、清空 votedFor、持久化、转 Follower。
若响应 term < currentTerm，忽略旧响应。
若仍为 Candidate 且收到的同意票数达到多数派 N/2+1，转 Leader。
若选举超时前未获多数票，Candidate 超时后开始新一轮选举：currentTerm++，重新投票。
收到相同或更高 term 的 AppendEntries 时，Candidate 立即转 Follower。

当选 Leader 后：
初始化 nextIndex[i] = lastLogIndex + 1，matchIndex[i] = 0。
立即向所有 Follower 发送心跳或 AppendEntries，建立权威。
立刻追加一条 no-op 日志条目，并复制到多数派后提交。no-op 用于尽快推进 commitIndex，间接提交之前旧 Term 的日志。
日志中必须打印每次 term 变化、角色变化、投票请求、投票结果、拒绝原因。例如：
```text
node=1 term 2->3 role=follower->candidate vote=self
node=1 grant vote to node=2 term=3
node=2 deny vote to node=1 term=3 reason=log stale
node=1 role=candidate->leader term=3```

## 日志复制
将命令追加到 Leader 本地 log[]，分配当前 term 和下一个 index
先持久化本地日志。
并行向所有 Follower 发送 AppendEntries。
Follower 按一致性检查规则接收或拒绝。
Leader 根据响应更新对应 Follower 的 matchIndex 和 nextIndex。
当某条日志被多数派节点复制，且满足提交规则后，Leader 推进 commitIndex。
Leader 将 commitIndex 之前的日志应用到状态机，然后回复客户端成功。

提交规则：Leader 只能通过“当前任期的日志条目被多数派复制”来推进 commitIndex。不能仅因为旧任期日志被多数派复制就直接提交旧任期日志。当前任期条目提交后，它之前的日志条目被间接提交。Leader 上任后追加 no-op 并复制提交，可以尽快完成这一过程。

Follower 处理 AppendEntries 的基线流程：
若 req.term < currentTerm，返回失败和 currentTerm。
若 req.term > currentTerm，更新 currentTerm、清空 votedFor、持久化、转 Follower。
若 req.term >= currentTerm，重置选举超时。
检查 prevLogIndex 和 prevLogTerm。
若检查通过，删除冲突的后续日志，追加 entries[]，持久化日志。
更新 commitIndex = min(leaderCommit, 本地最后日志 index)，应用已提交日志到状态机。


## 日志修复
日志索引从 1 开始，空日志长度为 0。prevLogIndex=0 表示从日志头开始。

快速回退：
conflictTerm：冲突位置那条日志的 term
conflictIndex：该 term 在 Follower 日志里第一条的 index
Follower 没有 prevLogIndex 这条日志时，返回 conflictIndex = 自己日志长度 + 1，conflictTerm = 空。

如果Leader有conflictTerm 这个 term：
nextIndex = Leader 日志中 term 等于 conflictTerm 的最后一条 index + 1

Leader 没有 conflictTerm 这个 term：
nextIndex = conflictIndex

Follower 日志太短，conflictIndex = 自己长度 + 1
nextIndex = conflictIndex

修正后 nextIndex 至少为 1，然后重新发送 AppendEntries，直到一致性检查通过
Leader 每次推进 commitIndex 时，选择多数派 matchIndex 中最大的、且属于当前任期的日志索引作为新的 commitIndex。随后将 commitIndex 之前的日志应用到状态机
