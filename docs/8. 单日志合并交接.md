# 8. 单日志合并交接

给接手改动的 agent。目标是把 KV WAL 与 Raft 日志合成一份持久日志，由 Raft 日志承担全部职责，并把它的对外名字改成 WAL。文中路径与行号按 `main` 分支当前状态核对过。

## 一、现状

节点数据目录现在有三处持久化对象：

| 对象 | 路径 | 内容 | 写入时机 |
|---|---|---|---|
| KV WAL | `<data-dir>/wal/%08d.wal` | `op(1B)+keylen(4B)+key+vallen(4B)+value` | 每次 `Put`，每 64 条一次 fsync |
| Raft 日志 | `<data-dir>/raft/log/%08d.rlog` | `op(1B)+term(8B)+index(8B)+command` | Leader 每条一次 fsync，Follower 每批一次 |
| Raft 游标 | `<data-dir>/raft/state` | currentTerm、votedFor、commitIndex、lastApplied | 每批 apply 一次 |

一次集群写落两次盘。Raft 日志的 command 字段装的就是那条 KV 记录：`Propose` 用 `kvstore.EncodeEntry` 编出 command（[internal/raft/node.go:496](file:///home/howardhe/Project/mini-Raft/internal/raft/node.go#L496)），apply 时再用 `kvstore.DecodeEntry` 解回 key/value 并调 `kv.Put`（[internal/raft/commit.go:58](file:///home/howardhe/Project/mini-Raft/internal/raft/commit.go#L58)），`Put` 内部再追加一条 KV WAL。docs/0 第 67 行的字节账：一条 12B key + 128B value 的写在 5 节点集群落 10 帧，Raft 帧 174B 里 149B 是 KV 帧的原样副本。

恢复链现在走两段：`kvstore.Open` 用 `scanWAL` 全量回放 KV WAL 重建 map（[internal/kvstore/recovery.go:20](file:///home/howardhe/Project/mini-Raft/internal/kvstore/recovery.go#L20)），随后 `NewNode` 只把 `(lastApplied, commitIndex]` 的差额从 Raft 日志补 apply（[internal/raft/node.go:196](file:///home/howardhe/Project/mini-Raft/internal/raft/node.go#L196)）。KV WAL 是主恢复源。

帧格式与恢复语义在两个包里是同构的：8 字节帧头（4B 长度 + 4B CRC32C）由 `kvstore/record.go:11` 定义，Raft 日志直接引用；段的原子创建（`.tmp` 写完 rename）、损坏处截断、`op` 字节的预留位，两边各写了一份实现。`docs/2.1 design.md` 第 13 行与 `docs/2.3 decisions.md` 的 D4（entry 是不透明字节，op 只定义 Put）写的原意就是让 Raft 复用这套帧格式，实际做出来的是复用格式、另起一套文件与恢复代码。

## 二、目标状态

一份日志，目录 `<data-dir>/raft/wal/`（与 `raft/state` 同前缀），文件名 `%08d.wal`，临时文件 `%08d.wal.tmp`。记录格式保持 Raft 日志现有的 `op+term+index+command`，`command` 沿用 `kvstore/record.go` 的 KV entry 编码，帧头不变。

`op` 取值维持 `0x01`（`OpPut`）与 `0x10`（`OpRaftEntry`）两个，快照标记不在合并期分配，留到第 5 步实现快照时再定；同时不改动 no-op 条目「空 command」的表示，apply 分支 `len(e.cmd) > 0` 照旧。

状态机是内存 map，不再有独立的操作日志。恢复顺序：读最近快照（快照落地前直接从日志头回放）重建 map，回放推进到 `lastApplied` 为止，`(lastApplied, commitIndex]` 继续补 apply 并写回游标。

fsync 点跟提交边界走：Leader 追加每条后一次，Follower 收到一批后一次。KV WAL 的 64 条批次与 `kv.Flush` 这条链整体取消；`state` 文件的每批一次保留，它存的是游标不是数据。

单机档改成单节点集群：成员表只有自己的节点，`Majority()` 等于 1，`Propose` 追加后当场满足提交条件，不发 RPC；选举要不要照跑留在 TODO，第 3 步开工前定。`cmd/miniraft-kv` 的进程载体保留并改写成单节点集群入口，`scripts/crash_inject.sh` 与 `bench_single_vs_raft.sh` 的档 1 继续挂在它上面，D21 对照臂与 M6/T13 这条线不重开；代价是单机档的读数背上 raft 帧头，口径按第五节改。

命名口径：类型 `raftLog` 改称日志的 WAL 名，`OpRaftEntry` 的取值与文档里的「raft 日志」称谓统一改成 WAL。改名的窗口必须在 `kvstore` 包里现有 `wal` 类型与 `WALDir` 删除之后，否则两个包各占一名。

## 四、实施次序

按依赖排，每步结束都要过门禁再进下一步。

0. M14（一致性读）收口提交。工作树里 `read.go`、`read_test.go`、`bench_read_modes.sh` 与 doc 4 的口径都在，门禁全绿；不先落一个可回退的基线，第 1 步的等价性对拍改坏了分不清是合并引入还是读路径引入。
1. 恢复单源化，先不动写入。把重启路径改成「日志全量回放重建 map」，KV WAL 照写不读。三处前置：`kvstore` 先加只做 apply 的入口（走 `Put` 回放等于把恢复变成写操作，会再追一条 KV WAL）；`NewNode` 的构造顺序拆开（现在收的是已经回放完的 `*kvstore.KV`）；`kvstore.Open` 加恢复源开关，第 3 步之前单机档没有 raft 日志，仍只能走 `scanWAL`。跑 crash_inject 与集群重启用例，断言两条恢复路径重建出的 map 逐 key 相等。这一步产出等价性证据，是后面删 KV WAL 的前提。
2. 停写 KV WAL，删 `kvstore` 的 wal 与 recovery 及其测试。D5 的失效语义（fsync 失败即关写路径）在 raft 日志里已经有一份，`kv` 那份随之取消。
3. 单机档改单节点集群，重建 `crash_inject.sh` 与 `bench_single_vs_raft.sh` 的对照臂。
4. 改名：类型、目录、扩展名、日志字段、文档称谓。改动面纯机械，放最后，避免前三步背着旧名和新名两套口径。
5. 快照与压缩（`docs/5. 日志快照.md`）。日志成了唯一恢复源，没有快照时重启时间随日志长度线性涨，`docs/2.1 design.md` 第 182 行的已知限制在合并后会落到日志头上。

## 六、风险点

- 截断边界。`truncateTo` 只允许发生在 `lastApplied` 之后（[internal/raft/append.go:100](file:///home/howardhe/Project/mini-Raft/internal/raft/append.go#L100) 的调用点）。正确实现里已提交条目不会被截，合并后这条从「隐含性质」变成「必须钉住的断言」，要在 `truncateTo` 入口加检查并配一个用例：构造一个已 apply 的位置，让高任期 Leader 试图截到它之前，断言拒绝。
- 游标与日志的一致性检查。`checkCursors` 现在挡的是 `state` 比日志长（[internal/raft/node.go:204](file:///home/howardhe/Project/mini-Raft/internal/raft/node.go#L204) 附近）。合并后 map 的正确性也依赖这两个文件同源，`lastApplied` 指向的条目必须能解码成一次 KV 操作，解不出来要在启动期失败而不是静默跳过。
- 空 command 的 no-op 条目。当选时写的那条 no-op 长度为 0，apply 时靠 `len(e.cmd) > 0` 跳过（[internal/raft/commit.go:53](file:///home/howardhe/Project/mini-Raft/internal/raft/commit.go#L53)）。合并后回放日志头时这条分支还在，快照标记如果借用 `op` 字节，别与 no-op 撞值。
- 数据目录不兼容。旧目录里 `wal/` 与 `raft/log/` 两份内容都在，新代码只读一处。默认不做迁移，脚本用的目录全部新建，代价是手上已有的实验数据目录读不出来；要保留哪一份得先说明用途。
- 基准数字全部作废。D19、D21、D27 依赖的吞吐与延迟读数写在 docs/0 的表里，写路径与 Sync 次数变了就必须重跑，不能沿用。
