# 8.1 对拍的跑法与读数

同一串操作、同一组故障分别打给 mini-Raft 和 etcd 3.7.0，两边各 5 个进程。整轮跑五遍，下面的数字是五轮的中位数，括号里是最小值到最大值；单轮的 p50 先在各轮里算好，再取中位数。原始记录在 `data/parity/20261106-220206`、`220310`、`220414`、`220511`、`220616` 五个目录。读回口径改过一次，更早目录里的幽灵条计数按旧口径算，不用。

## 一、装置与复跑

| 部件 | 位置 | 做什么 |
|---|---|---|
| etcd 3.7.0 | `~/tools/etcd-v3.7.0/etcd` | 按 `docs/8` 第三节自己编的二进制 |
| etcd 起停 | `scripts/etcd_up.sh`、`scripts/etcd_down.sh` | 一次把 5 个进程全拉起来，再等它们就绪 |
| 对拍客户端 | `cmd/miniraft-parity` | 一份代码两个适配器：mini-Raft 走 `/put` 与 `/get`，etcd 走 `/v3/kv/put` 与 `/v3/kv/range`，后者的 key 和 value 要各解一次 base64 |
| 驱动 | `scripts/parity.sh` | 起两边集群、逐档调客户端、在同一时刻对两边的主节点动手、按进程组收尾 |
| 汇总 | `bin/miniraft-parity -phase stats -aggdir data/parity -rounds 5` | 把最近五轮的 `summary.tsv` 合并成 `n` 与 `min/median/max` |

复跑只用一条命令：

```bash
ETCD_BIN=~/tools/etcd-v3.7.0/etcd scripts/parity.sh
```

两边要对齐的参数，`topology.txt` 里逐条记着：

| 参数 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 心跳 | 100ms | `--heartbeat-interval 100` |
| 选举超时基线 | `-election-timeout-ms 1000`，随机取 [1000,2000)ms | `--election-timeout 1000`，同样随机 |
| 快照阈值 | `-snapshot-entries 10000` | `--snapshot-count 10000` |
| 数据目录 | `<轮次目录>/mini/node-i`，ext4 NVMe | `<轮次目录>/etcd/node-i`，同一块盘 |

mini-Raft 的 5 个进程在同一个网络命名空间里，监听 127.0.0.11-15 的 8801-8805；客户端绑 127.0.0.100，这个地址不在成员表里，按成员地址成对切流量时不会误伤客户端。

etcd 每台一个自己的网络命名空间，用 veth 接进 10.20.0.0/24 的网桥，监听 10.20.0.21-25 的 9801-9805，peer 口 9901-9905；客户端绑网桥地址 10.20.0.1。绕这一圈的原因是 etcd 的出站 peer 连接只绑端口，源地址由路由选成 127.0.0.1，在同一个命名空间里按对端地址切，回包那一路切不中。隔离规则下在被隔离那台自己的命名空间里执行，进出两个方向都按对端成员地址封。

整套装置跑在 `exec unshare -rn` 里，只动本轮进程的网络；主机上 kind 那套 etcd 不受影响。

跑的时候有四条规矩，少任何一条数字就错。

写固定在主节点，这一发失败才换地址。打给 Follower 的话，mini-Raft 侧 100 发全被拒，恢复过程里一条正常写都没有，量到的是客户端找主节点花的时间，量不到集群重新有主花的时间。

杀主的每一发写占一个新 key，从 `parity-fo-1` 排到 `parity-fo-100`。读回时拿着 key 直接判断这一发提交没有。所有写共用一个 key、靠 value 里的序号倒推会数错：没回执的写被后来的值盖住，早先按那种数法多算了 11 条（mini）和 2 条（etcd）。

不可用时间按回话到达的时刻算，不按发出去的时刻。etcd 有一发写在主节点死后压在队列里，2 秒后才回话；按发出时刻算，这一发落在整个窗口之外，不可用时间会报成没有。

杀主时刻由驱动写进 `killstamp`，两边 `kill -9` 在同一条 bash 语句里发出，两组 failover 并行跑。

## 二、两边回什么

| 看什么 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 写成功回哪些键 | `index,ok,req_id,term` | `header` |
| 读成功回哪些键 | `key,read_index,req_id,stale,term,value` | `count,header,kvs` |
| 数字是什么类型 | JSON 数字 | 字符串，比如 `"revision":"4"` |
| 写打到 Follower | 503，`code=not_leader`，带 `leader_addr`，191µs（147-431） | 200，6339µs（5569-11813） |
| 线性一致读打到 Follower | 503，106µs（68-134） | 200，642µs（542-687） |
| 读旧值打到 Follower | 200，`stale=true` | 200，`serializable=true` |

前两行的差别来自一个默认值：etcd 的 JSON 由 protobuf 生成，业务字段全塞在 `header` 里，64 位整数编成字符串；mini-Raft 把字段平铺在顶层，数字就是数字。

Follower 上的写差 6.1ms。etcd 的 Follower 在 raft 层把提案转给主节点（`go.etcd.io/raft/v3` 的 `stepFollower`），HTTP 回话等这趟转交和复制走完；mini-Raft 判一下自己的角色就回 503，所以只有 0.19ms。线性一致读同理：etcd 把 `MsgReadIndex` 转给主节点，拿到索引再读本地，0.64ms；mini-Raft 按 D24 直接回 503。

## 三、一条写占几格序号

| 操作 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 一个 key 连写 20 次 | `index 3→22`，每次加 1 | `revision 4→23`，每次加 1 |
| 20 次读到的序号 | 1 到 20 单调不减，倒退 0 次 | 1 到 20 单调不减，倒退 0 次 |
| 同一个 value 连发两次 | `index 93→94` | `revision 94→95` |
| 50 个 key 挨个写 | 写完 1684ms（1178-1764），读完 53ms | 写完 358ms（289-379），读完 17ms |

两边一条写都占一格序号，推进节奏一致。起点差一格是各自开局的初始化写入，这一格只看步长。

重发同一个 value，两边各多占一格，都不去重。mini-Raft 的 `req_id` 是服务端自增的，客户端塞不进去；etcd 每次写占一个 `revision`。要去重只能客户端自己做。

mini-Raft 没有批量入口，50 个 key 是 50 次单发，写完的时间就是单条写延迟乘 50，跟 etcd 的 358ms 差在这里。一次事务提交多个 key 属于能力差异，见 `docs/8` 第六节。

## 四、一条 value 能塞多大

| value 字节 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 1048576（1MiB） | 200 | 200 |
| 1048577 | 413，`value is 1048577 bytes, limit 1048576` | 200 |
| 1572864 | 413 | 400，`etcdserver: request is too large` |
| 1572865 | 413 | 400，同上 |
| 2097152（2MiB） | 413 | 429，`received message larger than max (2097177 vs. 2097152)` |
| 4194304（4MiB） | 413，`request body over the entry limit` | 429 |

五轮六档的返回完全一致。mini-Raft 有三道上限：value 1048576 字节、key 1024 字节、请求体 4194304 字节（`internal/kvstore/config.go:22-24`），撞哪一道都是 413，错误消息里写明是哪一道。etcd 分两层拒：请求体超过 `max-request-bytes`（默认 1572864）时服务层回 400，超过 gRPC 单次消息上限（2097152）时传输层先拒，回 429。

TrainCache 的两条设计按这两个上限定。一个 WarmupTask 的状态明细最多 61589 字节，因为整条 4.18MiB 同时超过 mini-Raft 的 1MiB 和 etcd 的 1572864；路径索引整张表放对象存储，因为塞不进单条上限。

## 五、一次写、一次读花多久

| 操作 | mini-Raft p50／p99 | etcd p50／p99 |
|---|---|---|
| 单条写 | 16.9ms（11.1-18.3）／28.0ms | 5.6ms（4.9-6.3）／9.5ms |
| 单条线性一致读 | 17.0ms（12.5-19.0）／21.0ms | 0.38ms（0.35-0.48）／0.52ms |
| 批量里的单条写 | 32.9ms（22.8-33.0）／42.0ms | 6.1ms（5.1-7.0）／15.3ms |
| 读旧值（打 Follower） | 0.21ms（0.16-0.31）／19.9ms | 0.33ms（0.31-0.40）／0.61ms |

mini-Raft 的写慢 3 倍，线性一致读慢 45 倍（16.98÷0.38）。

慢在哪里能指到代码。一条写从主节点的 `Propose` 开始，追加并同步日志，然后把 AppendEntries 排进 `outbox`，由 `drainOutbox` 一条一条串行发送（`internal/raft/node.go:393-403`），四条回执一条接一条等，写完再等 apply。一条线性一致读几乎每次都走确认轮：`-read-mode` 默认 lease，但租约窗口要盖住 `ReadTimeoutMS`（默认 1000ms）才复用它（`internal/raft/read.go:139-157`），1000ms 的选举窗口盖不住，于是每次读都发一轮确认，代价与写同量级。读旧值不走这条路，直接读本机 KV，0.21ms 是五轮里最快的一格。

etcd 的写每个提交同步一次 bbolt，主节点线性读走一次 ReadIndex 往返，回环上的往返比 mini-Raft 的四条串行 RPC 短。这条按 D6、D11 的口径记，不算实现好坏；etcd 侧的流水线与批量提交没有读代码核实，只量到结果。

## 六、读旧值能读到多旧

写完紧跟一发线性一致读、再跟一发读旧值，各 20 轮，五轮共 100 发。

| 看什么 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 线性一致读到旧值 | 0/100 | 0/100 |
| 旧值读到旧值 | 0/100 | 37/100（每轮 5-11 发） |
| 最多落后几条 | 0 | 1 |

线性一致档两边一发不错。旧值档 mini-Raft 一发没读到旧数据：前面那发线性一致读走确认轮，确认轮的 AppendEntries 把新的提交点一起带给所有 Follower，等旧值读落到 Follower 时值已经应用。etcd 的 `serializable` 读直接读本地存储，线性一致读走 ReadIndex，不保证那台 Follower 已经应用最新一条，落后时就是前一条。

这个比例受发送节奏影响，每轮写、线性读、旧值读串行发，约 40ms 一轮。改成并发发写再测，比例才有独立的意义，这一条留在 TODO。

## 七、杀掉主节点之后

`kill -9` 打在两边同下标的节点上，客户端按 100ms 一发持续写，共 100 发。

| 看什么 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 第一发失败的回话距杀主 | 31ms（9-58） | 58ms（31-68） |
| 不可用时间 | 1276ms（1150-1776） | 2166ms（2143-2182） |
| 期间的状态码 | 连接被拒或断开×1、503×10-16、200×62-68 | 连接被拒×1、超时×1、200×77 |
| 失败的发数 | 13（11-17） | 2 |
| 客户端换地址次数 | 13 | 2 |
| 日志里的当选时刻距杀主 | 1184ms（1010-1759） | 1030ms（961-1114） |
| 任期增量 | +1 | +1 |

当选时刻两边都从日志取：mini-Raft 看 `role changed` 的 `new_role=leader`，etcd 看 `became leader at term`。

两边的选举耗时差不多，都在 1 到 1.2 秒。不可用时间差 890ms，差在客户端做法上。mini-Raft 的 Follower 收到写立刻回 503 并带主节点地址，客户端每一发失败就换地址重问一遍角色表，五轮失败 11 到 17 发、其中 10 到 16 发是 503，新主节点一出现就能接上；etcd 的那一发压在已经死掉的进程上，2 秒超时才回话，客户端只换了 2 次地址，恢复时刻被这一发拖到 2.1 秒。选举本身没有差这么多。

拒绝连接两边各一次，都是 TCP 连到已经回收的端口。任期都只加 1。

## 八、冻住主节点四秒

`SIGSTOP` 冻住两边的主节点 4000ms，客户端照常把写和两种读打向这个节点。

| 看什么 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 冻住期间发出的请求 | 7-8 发，全部 500ms 超时，0 发成功 | 6-7 发超时；四轮里有一发在解冻后才回话 |
| 第一发失败回话距冻住 | 520ms（502-1825） | 530ms（523-1859） |
| 解冻后旧节点还自认主 | 否，5/5 | 否，5/5 |
| 旧节点上的线性一致读 | 503 `not_leader`，5/5 | 200，5/5 |
| 任期增量、换届 | +1，5/5 换出新主 | +1，5/5 换出新主 |

客户端单发超时 500ms，冻住的进程不回话，窗口里每发都要等满超时。第一发失败的落点受冻住时刻卡在哪一发请求中间影响，范围到 1.9 秒。

两边解冻后旧节点都不再自认主：它醒来后收到新任期的心跳或 AppendEntries，按任期大小自动降级。差别在之后的一发线性一致读：etcd 的旧节点作为 Follower 把 ReadIndex 转给新主，回 200；mini-Raft 按 D24 回 503 带主节点提示。这一格与第二节 Follower 读同一套规则。

## 九、把主节点隔离出去

把主节点从其余四台之间切断 6000ms，客户端照常打它，同时盯着多数派一侧，每 150ms 取一次被隔离者的自认状态。

| 看什么 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 窗口内的写 | 8-9 发，0 成功，全部 300ms 超时 | 8-9 发，0 成功，全部 300ms 超时 |
| 窗口内的线性一致读 | 0 成功 | 0 成功 |
| 窗口内的旧值读 | 8-9 发全部 200 | 8-9 发全部 200 |
| 多数派选出新主距隔离 | 1171ms（1032-2617） | 1029ms（946-1105） |
| 被隔离者仍自认主 | 8/8 次采样，5/5 轮 | 0/8 次，5/5 轮 |
| 解冻后任期增量 | +1 到 +2 | +1 |
| 解冻后是否再换届 | 否，5/5 | 否，5/5 |

被隔离的主节点写不进日志，窗口内的写只能超时；旧值读读本机，两边都照常回 200。多数派在 1.0 到 2.6 秒内选出新主，与被隔离者无关。

真正的差别是「还认不认自己」。etcd 默认开 `CheckQuorum`（`server/etcdserver/bootstrap.go` 里写死 true），主节点每个选举超时检查一次多数派的回音，等不到就自己下台，所以隔离窗口里的每一次采样它都不认主；mini-Raft 没有这条检查，被隔离的 Leader 在解冻前一直自认主，旧值读也一直回 200。补上这条检查的代价是主节点上多一个判据，收益是被隔离的主节点不会拿着过期身份继续服务本地读。

## 十、单台非主节点隔离（Pre-Vote）

把一台非主节点切出去 6000ms，看它自己的任期涨不涨，解冻后集群是否为它让路。

| 看什么 | mini-Raft | etcd 3.7.0 |
|---|---|---|
| 隔离期间被隔离节点的任期 | +3，五轮都是 +3 | +0，五轮都是 +0 |
| 解冻后集群任期增量 | +4 | 0 |
| 解冻后是否换届 | 是，5/5 | 否，5/5 |
| 解冻后 Leader | 被隔离的那台，5/5 | 原 Leader，5/5 |

mini-Raft 不实现 Pre-Vote（`3.3` 已定），被隔离的 Follower 每轮选举超时都把自己的任期加一，6 秒里加 3 次；解冻后它带着更高的任期发起投票，集群为它选一次，5 轮里都是这台当上新主。etcd 开 Pre-Vote，预投票拿不到多数就不加任期，解冻后原 Leader 不动。

这就是不实现 Pre-Vote 的代价：一次隔离换来一次无谓的换届和 4 个任期的抬升。任期抬升本身不影响正确性，代价是这一次换届。

## 十一、数据有没有回来

杀主之后把这一轮写过的 key 全量读回，逐条对，每轮 155 个 key。

| 目标 | 已回执却读不到 | 没回执却读得到 | key 总数 |
|---|---|---|---|
| mini-Raft | 0 | 2/5 轮各 1 条 | 155 |
| etcd 3.7.0 | 0 | 0 | 155 |

已回执的写一条没丢，两边五轮都是 0。mini-Raft 那两条属于同一个 key `parity-fo-21`：这一发在杀主前 31 到 35 毫秒发出，主节点把它写进了日志并提交，自己在回话前被杀，客户端拿到的是 EOF。读回时值在，客户端手里是失败，按判定规则记成「没回执却读得到」，落在「写可能已生效、客户端不知道」这一类，不算丢数据。

etcd 五轮没有出现这种条目。它那一发没回执的写压在死掉主节点的队列里，2 秒超时回话，根本没进日志，所以读不回来。
