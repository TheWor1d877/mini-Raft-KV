# 4.1 Raft 一致性读设计

## 1. 模块定位

本模块处理：`/get` 的两条线性一致读路径（Lease Read 与 ReadIndex）、领导权租约的建立与失效、读索引下界的捕获、等待状态机应用到位。

不改写：写路径的日志复制与提交（`3.1`）、state 与 raft 日志的落盘形状（D12、D14、D15）、`cmd/miniraft-kv` 的单机 `/get`（D21、D30）。`internal/kvstore` 的导出面与签名一个字节都不动。

边界：线性一致读只在 Leader 上服务，非 Leader 回 503 带 Leader 提示，不做服务端转发（D24）；本地旧数据读降成显式档 `consistency=local`，是独立档位，不参与线性一致的判定；租约、读索引、确认轮次全部是内存状态，一个字节都不落盘（基线共同不变量 4）。

`docs/1` 划走的 membership 变更与 Pre-Vote 仍然不做。toxc 的 `linearizable` 报告与故障注入矩阵归 doc 6，本模块只交付读路径的行为与三档读数。

## 2. 架构概览

```text
internal/raft/read.go      新增：租约状态、确认轮次与计票、读队列、等待应用、时钟注入位
internal/raft/node.go      Tick 的 Leader 分支多一步「有排队读就补一轮确认广播」；transition 里清租约与轮次；Close 作废在途读
internal/raft/append.go    appendOnce 带上 readRound；handleAppendReply 里认轮次计票、结算读索引、丢弃跨轮回执
internal/raft/rpc.go       /get 读 consistency 参数、按读法分派；两个 AppendEntries 的 JSON 各多一个 readRound 字段
internal/raft/config.go    -read-mode、-clock-drift-ms、-read-timeout-ms 三个开关与租约安全窗校验
cmd/miniraft-node          不改：读请求的 context.WithTimeout 在 rpc.go 的 handleGet 里设，上界取 Config.ReadTimeoutMS（D28）
```

一次线性一致读要过的路径：客户端 `GET /get?key=&consistency=` → handler 判角色 → 读请求登记（记下到达时的 `commitIndex` 当下界）→ 租约有效则直接取读索引，无效则排一轮 AppendEntries 广播 → 按成员 id 升序串行发出、回执当场计票（D23）→ 多数派成功即定读索引并建租约 → 等 `lastApplied` 追上读索引 → `kv.Get` 返回。

一次本地读（`consistency=local`）仍是 `kv.Get` 一步，与 `3.1` 交付的形状相同，响应体多两个字段标明这条读没有领导权确认。

## 3. 包结构与依赖方向

- 允许：`internal/raft` → `internal/kvstore`，读路径用 `kvstore.KV.Get`（`data` map 的读锁）和 `3.1` §4 已有的游标。
- 读路径不进 `internal/kvstore`：状态机那一层没有领导权概念，`local` 档读的是本地 map（D30）。`consistency` 参数只在 raft 的 handler 上解析。
- 禁止：墙上时间进入状态机判定。全模块只有一个时钟注入位（D26），`node.go`、`append.go`、`commit.go`、`vote.go` 四个文件里 `time.Now()` 与 `time.Since` 一次都不出现，选举与心跳只看 tick 计数（D16 覆盖选举与心跳，租约计时走时钟注入位）；`rpc.go` 的 `duration_ms` 与 `state.go` 的 `sync_ms` 只做日志计时、不参与判定，不受这条约束。
- 测试夹具沿用 `cluster_fixture_test.go`：Node 持假时钟，内存 transport 的用例回执按序号注入，不改动 transport 的串行顺序（D23）。用例仍零 `sleep`。

## 4. 核心接口

```go
type Consistency int8 // ConsistencyLinearizable / ConsistencyLocal，对应 /get 的 consistency 两个取值

func (n *Node) Read(ctx context.Context, key string, mode Consistency) (value string, index, term uint64, err error)
func (n *Node) LeaseRemaining() int64        // 相对注入时钟的剩余毫秒，<=0 表示没有效租约
func (n *Node) ReadRound() uint64            // 当前在途确认轮的编号，0 表示没有在途

type Stats struct {
    Term, CommitIndex, LastApplied, LastLogIndex, Votes uint64
    Role                                               Role
    LeaseRemainingMS                                   int64  // 新增
    ReadRound                                          uint64 // 新增
}
```

`Get(key)` 保留给包内与旧用例，等价于 `Read(ctx, key, ConsistencyLocal)` 去掉读索引那一项；`Node.Read` 是客户端路径的唯一入口。

`AppendRequest` 与 `AppendReply` 各加一个字段（D25）：

```go
type AppendRequest struct { ...; ReadRound uint64 `json:"readRound"` } // 0 = 这一轮不为任何读做确认
type AppendReply  struct { ...; ReadRound uint64 `json:"readRound"` }  // 原样带回发起时的编号
```

契约：

| 方法                      | 输入输出       | 错误语义                                                                                                                                                                                                                                             | 并发与幂等                                                                                                                      |
|:--------------------------|:---------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------------------------------------------------------------------------------------|
| Read                      | ctx、key、mode | 成功回值、读索引、确认所用的任期；`ErrKeyNotFound` 属正常控制流。非 Leader 的线性读回 `ErrNotLeader`（带 leader 提示，与 `/put` 同一份 `notLeaderResponse` 形状）；本地读不返回该错误；ctx 超时或取消回 `ErrCanceled`；发现更高任期回 `ErrNotLeader` | 每个读请求独立登记下界与等待，重试视为新读、重新走对应读法的领导权条件（基线不变量 6）；同一 key 并发读不合并结果，只共享确认轮 |
| LeaseRemaining／ReadRound | 无             | 不返回错误                                                                                                                                                                                                                                           | 读数走注入时钟与一把互斥锁，供 `Stats()`、测试与注入脚本读                                                                      |
| Tick                      | 无             | 不返回错误                                                                                                                                                                                                                                           | Leader 分支在心跳广播之外多一次 `scheduleReadRound()`：读队列非空且没有在途轮次就补发一轮（§7「发起确认轮」）                   |
| Close                     | 无             | `ErrIO`                                                                                                                                                                                                                                              | 顺序不变，多一步：在途读一律拿 `ErrCanceled`，租约与轮次清空（基线共同不变量 4）                                                |

HTTP 形状（`/get` 的两个新字段与一条新状态码）：

| 路径                         | 请求                                                                             | 响应                                                                                                                                             | 出错                                                                                                                                                                                                 |
|:-----------------------------|:---------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `GET /get?key=&consistency=` | query：`key` 必填；`consistency` 取 `linearizable`（默认）或 `local`，其余值 400 | `{"key","value","req_id","read_index","term","stale":bool}`；`local` 档的读索引回 `0`、任期回本地任期，`stale` 回 `true`，表示这条读没有领导权确认 | 线性读在非 Leader 上 503 `not_leader`，五个键与 `/put` 那格完全一致；等待应用超时或任期变化 500 `canceled`／`not_leader`；`key` 缺失 400；`key` 不存在 404 `key_not_found`；`consistency` 非法值 400 |
| `POST /raft/append-entries`  | 原六项加 `readRound`，必填七项                                                   | 原四项加 `readRound`                                                                                                                             | 非法 JSON 与缺字段 400；`readRound` 缺失即 400，补零后为读发起的确认轮与例行心跳在请求上无法区分（`3.1` §4 的必填检查口径延伸）                                                                      |

`read_index` 与 `term` 是本设计新增的两个键。etcd 把一致性读的索引放在响应头 `header.revision` 里，对拍时这一格的映射写在 doc 7。

进程退出码沿用 `2.1` §4 三档，新增一格：`-read-mode` 与 `-clock-drift-ms` 算不出安全的租约窗口时按配置非法退 2，不静默降级成 ReadIndex（D29）。

## 5. 数据格式

读路径不落任何新盘。`raft/state` 仍是四个标量一行 JSON（D14），`readIndex`、租约截止时间、确认轮编号都只存在内存里：重启后角色一律 Follower、租约窗口为空，第一个线性读要重新走一轮确认（基线共同不变量 4）。

`AppendRequest` 的 `readRound` 是 `uint64`，JSON 里与其余字段同层。轮次编号在 Leader 每次发起确认轮时自增，跨任期不复用：转成 Follower 归零、重新当选接着自增。Follower 不解释这个字段，只把请求里带来的编号原样回显（D25）。

租约是一个三元组：起点单调时刻（本轮广播发出前取）、成立的任期、截止时刻。截止时刻按基线公式 `起点 + -election-timeout-ms - -clock-drift-ms` 算；确认完成时截止早于当前时刻，本轮就不建租约，读数照常返回（这一轮的确认对当次读仍然有效）。

`kv.Get` 的返回值不带索引，读索引由 raft 侧给出：`max(确认完成时的 commitIndex, 该读到达时的下界)`。取大来自基线共同不变量 2：确认期间提交索引继续推进就用更新的，不能拿更旧的。

## 6. 目录与配置

数据目录不变（`3.1` §6），`raft/` 下仍是 `state` 与 `log/`。

| 开关 | 默认 | 含义 |
|:---|:---|:---|
| `-read-mode` | `lease` | `lease`／`readindex`，决定线性读走租约还是逐读确认。`/get` 带 `consistency` 时以参数为准；`consistency` 只取 `linearizable`／`local`，与本级开关是两条轴，`local` 只能由请求指定 |
| `-clock-drift-ms` | `50` | 租约的时钟漂移余量，与 `-tick-ms` 同量级；`< 0` 报错 |
| `-read-timeout-ms` | `1000` | 单次线性读从登记到返回的上界，由 handler 换成 `context.WithTimeout`；`<= 0` 报错 |

`Config` 新增三个字段：节点级默认读法 `ReadMode`（取值 `lease`／`readindex`，与请求级的 `Consistency` 是两个类型、两条轴）、`ClockDriftMS`、`ReadTimeoutMS`。`Validate()` 在 `3.1` §6 那五条之外新增三条：

1. `ClockDriftMS < 0`、`ReadTimeoutMS <= 0`、`ReadMode` 不在两个取值里，各自报错。
2. `ReadMode == lease` 时要求 `ElectionTimeoutMS - ClockDriftMS > (N-1) × rpcTimeoutMS`。RPC 按成员 id 串行发出，一轮广播的最坏耗时是 `(N-1) × min(2×-tick-ms, -election-timeout-ms)`（`3.1` §9）；余量不够时，确认还没完成租约就已过期，Lease Read 一次也命中不了。默认 5 节点、T=500ms、RPC 超时 100ms 时右边是 400ms、左边是 450ms，余量只剩 50ms。
3. `ReadMode == readindex` 时不做上面那条检查，只把 `-read-timeout-ms` 与 RPC 超时比一次：读超时小于 `(N-1) × rpcTimeout` 时，一轮广播还没走完读就超时。

换算只在 `NewNode` 做一次：`leaseWindowNS = (ElectionTimeoutMS - ClockDriftMS) × 1e6`。`-tick-ms` 不进这个公式，租约按注入的单调时钟算（D26、§7）：起点取广播发起那一刻，截止时刻是起点加这个窗口，窗口按墙上时间的长度计，不按 tick 数计。

## 7. 关键流程

**时钟注入位。** `Node` 上一个字段 `now func() int64`，返回单调纳秒，真实实现是 `time.Since(processStart)`，测试实现是一根可以被用例拨动的计数器。租约的建立、失效判定、`LeaseRemaining()` 三处只经这个函数取时间，其余位置一律不调用它（D26）。用例把假时钟按「每次 `Tick()` 前进 `-tick-ms`」推进，仍可断言「调 11 次 `Tick()` 之后租约剩 400ms」这类形状。

**读请求登记。** `Read` 持锁先判一致性档：`mode == ConsistencyLocal` 直接 `kv.Get` 返回，读索引回 0、任期回本地任期，不进读队列、不发确认轮。线性读接着走四步：判角色；取 `lowerBound = commitIndex`；把这一条读排进 `readQueue`（每格记到达序、下界与一个 `chan readResult`）；调用 `scheduleReadRound()`。

**发起确认轮。** `scheduleReadRound()` 只在「读队列非空且没有在途轮次」时动作：`readRoundSeq++`，把 `readQueue` 里此刻已到的读整体快照成本轮成员（到达序晚于快照的读留在队列里等下一轮，基线 ReadIndex 的合并条件就落在这一步），记 `activeRound = {round, term, startNS = now(), acks: 自己一票, members}`，再按成员 id 升序给其余节点各排一条 `appendOnce`，`req.ReadRound` 填本轮编号。发起时刻的租约起点也记在这里，取的是发起那一刻，不用任何一条回执到达的时刻（基线 Lease Read 第一段）。

三个调用点共用这一个函数：`Read` 登记之后、一条回执结算之后、`Tick()` 的 Leader 分支。谁先看到队列非空谁发，同一时间最多一个在途轮次。

**回执计票。** `handleAppendReply` 在现有分支之后加一段：`reply.ReadRound != 0 && reply.ReadRound == n.activeRound.round` 且 `reply.Success` 且 `n.activeRound.term == n.term` 且本节点仍是 Leader 才 `acks++`；编号对不上就是跨轮回执，打 `stale read round dropped` 丢弃，不并入计票（基线 Lease Read 的「跨轮不得拼凑」）。`acks` 达到 `N/2+1` 立即结算，不等剩下的回执。结算之后才到的回执不进任何一轮的计票，也不再打这条日志：那一轮已经结束，它不是错位的回执，只是迟到。

**结算。** 定 `readIndex = max(commitIndex, 每个成员的 lowerBound)`（逐成员取大，基线共同不变量 2），给 `ReadMode == lease` 的本节点建租约：`leaseUntil = startNS + leaseWindowNS`，若 `leaseUntil <= now()` 则本轮不生效、打一条 `lease rejected`；`activeRound` 置空；把每个成员的 `readResult{readIndex, term}` 送进它的 channel；队列里还留着读就再调一次 `scheduleReadRound()`。

**等待应用。** 返回的前提是 `lastApplied >= readIndex`，够时才允许调 `kv.Get`。不够就排进 `applyWaiters`（`index → []chan struct{}`），`finishApply(through)` 在写完 state 之后兑现 `index <= through` 的那些格。等待由 `ctx` 的超时兜底，超时回 `ErrCanceled`，读失败后不降级成本地读（基线共同不变量 1、D5 的下游）。

**租约命中。** `ReadMode == lease` 且 `leaseUntil > now()` 且 `leaseTerm == n.term` 时，读直接取 `readIndex = max(commitIndex, lowerBound)` 进等待应用这一步，一次 RPC 都不发。剩余租约不足以覆盖读超时的上界（`now() + ReadTimeoutMS > leaseUntil`）时本轮不复用这条租约，重新发一轮确认续期（基线 Lease Read 第三段的保守估计）。

**租约失效。** 四个入口当场清空：发现更高任期（`transition` 里）、主动转成 Follower、`Close`、进程重启。已登记未返回的读跟着走：更高任期与转成 Follower 回 `ErrNotLeader`，`Close` 回 `ErrCanceled`（与在途提案同一条口径，`3.1` §4）。不留任何「旧租约继续本地读」的路径（基线 Lease Read 末段）。失去多数派连通能力表现为确认轮凑不齐过半回执，本模块不额外判定：串行 RPC 下这条信息只能从回执里读到，再加一个开关就多一处和回执不一致的状态。

**Follower 侧。** 只多做一件事：`handleAppendEntries` 的回执把请求里的 `readRound` 原样回显。其余六步、一致性检查、截后缀与 Sync 一概不变，为读发起的那一轮广播与例行心跳共用 `appendOnce`，区别只有 `readRound` 是否为 0。带条目的同任期 `success` 回执同样计票：回执本身说明对方在这一任期承认当前 Leader，不额外要求条目数组为空。

## 8. 不变式

1. 线性一致读返回时，`readIndex >= 该读到达时的 commitIndex`，且 `lastApplied >= readIndex`。两条都能从响应体的 `read_index` 与 `Stats()` 的游标核对。
2. 一轮确认的票只来自同一编号、同一任期、`success=true` 的回执；跨轮或跨任期的回执丢弃，多数派阈值仍是 `N/2+1`。
3. 租约只在确认完成时未过期才成立，且 `leaseTerm == 当前 term`；任期一变，租约与在途轮次同时归零。
4. 只有本轮发起前已到达的读共享本轮确认与读索引；之后到达的读必须等下一轮。
5. 租约、读索引、轮次编号不持久化，`raft/state` 的字节布局在 doc 4 之后与 `3.1` §5 逐字节相同。
6. `consistency=local` 之外，任何响应都不携带未确认领导权的数据；`stale:true` 只可能出现在本地读那一格。
7. 客户端重试不携带上一次的确认结果，服务端也不缓存读结果，同一个 key 重试两次就是两次独立判定。

## 9. 风险与约束

- 默认配置的租约余量只有 50ms（§6 第 2 条）。一轮广播里只要有一个节点慢，租约就在确认完成时过期，Lease Read 的行为等同 ReadIndex。命中率为 0 属于合法结果，M14 的读数要同时给 `lease granted`／`lease rejected` 两条日志的计数，并把 `-election-timeout-ms` 调到 1000ms 再跑一档对照。
- 单调时钟的前提是进程不暂停。容器冻结、SIGSTOP、宿主机休眠时，`time.Since` 和其余节点的选举计时会脱钩，租约在这一类故障下不安全。时钟跳变与进程冻结的注入归 doc 6，本模块只在 `-clock-drift-ms` 上留一个可拨的量。
- 每次为读发起的确认轮都要给其余 4 个节点各发一条请求，串行 4 跳（D23）。ReadIndex 档的单次读延迟下界就是这个数，与 `3.1` §9 写给 `/put` 的那条同一条链；M14 的读延迟表按这个口径读。
- 读队列与 apply 等待表用同一把 `sync.Mutex`，`kv.Get` 只在确认过 `lastApplied` 之后调用，读路径与 apply 循环串行，不引入第二把锁。
- 非 Leader 一律回 503 会把客户端的重试压力集中在 Leader 上；etcd 会把读转发过去，这一格差异留给 doc 7 记录，本模块不实现转发。
- 一次读可能要等两次落盘：确认轮之后紧接着要等一批 apply 的 state 游标落盘。等待应用按墙上时间计时，与 tick 数无关，单节点集群那档量出的 9.8ms 级 Sync 差值会直接进读延迟（D19、D27）。

## 10. 日志字段

沿用 `2.1` §8 的封装与脱敏口径、`3.1` §10 的 `component` 集合（`wal`／`kv`／`entry`／`raft`），本模块新增这些事件：

| 事件                     | msg                        | 字段                                                                       |
|:-------------------------|:---------------------------|:---------------------------------------------------------------------------|
| 确认轮发起               | `read round sent`          | `node_id`、`term`、`read_round`、`reads`、`start_mono_ms`                  |
| 确认轮过半               | `read round settled`       | `node_id`、`term`、`read_round`、`acks`、`read_index`、`round_cost_ms`     |
| 跨轮回执丢弃             | `stale read round dropped` | `peer_id`、`read_round`、`current_round`                                   |
| 租约成立                 | `lease granted`            | `node_id`、`term`、`lease_remaining_ms`                                    |
| 确认完成时租约窗口已烧完 | `lease rejected`           | `node_id`、`term`、`read_round`、`lease_remaining_ms`（负值）              |
| 租约失效                 | `lease invalidated`        | `node_id`、`old_term`、`reason`（`higher_term`／`stepped_down`／`closed`） |
| 读命中租约               | `read served by lease`     | `node_id`、`term`、`read_index`、`lease_remaining_ms`                      |
| 读等不到应用             | `read wait timed out`      | `node_id`、`read_index`、`last_applied`、`commit_index`                    |
