# 4.3 Raft 一致性读决策记录

## D24 线性一致读只在 Leader 上服务，本地旧数据读降成显式档

- 背景：基线要求「无法确认领导权时返回失败，不得降级为本地旧数据读取」。`3.1` 交付的 `/get` 是任意节点的本地读，M12 的收口判据、`cluster_up.sh` 的探活、M13 两个脚本的读回都调用这条 `/get`；`docs/1` 的对拍负载里还专门有「读到旧值」那一格。
- 备选：`/get` 默认线性一致，本地读用 `?consistency=local` 显式请求（本条）；`/get` 保持本地读、新增一条 `/read` 走一致性读；`/get` 一律线性一致，不留本地读档。
- 结论：`/get` 不带参数就是线性一致读，按 `-read-mode` 选 Lease Read 或 ReadIndex；非 Leader 回 503 `not_leader` 带 `leader_id` 与 `leader_addr`，五个键与 `/put` 那一格完全相同；本地读只能由 `consistency=local` 请求，响应体里 `stale:true`、`read_index:0`，服务端不把它当失败兜底。
- 理由：etcd 的 Get 默认就是线性一致的，串行读要客户端显式声明 `serializable=true`。两边默认档相同时，对拍结果可以直接比；默认档不同时，doc 7 每格都要先交代「两边的默认值不同」。新增 `/read` 会让同一份数据有两个入口，`docs/1` 的负载清单写的是 Put/Get，客户端重试、读到旧值这些格都要重算一遍路径。一律去掉本地读，「读到旧值」那一格就只能靠故障注入间接观测，而加一个参数就能造出这条对照。
- 影响：`3.1` §4 的 `/get` 行按本条改写；`3.2` §3 里 `http_rpc_test.go` 与 `cluster_process_test.go` 的读回断言、`cluster_up.sh` 的探活、`leader_failover.sh` 与 `bench_single_vs_raft.sh` 的读回全部改成显式带 `consistency=local`。raft 侧的 `/get` 共 20 处，3 处是 `rpc.go` 的路由常量与错误文本，其余 17 处是调用点（`grep -c '/get' internal/raft/rpc.go internal/raft/http_rpc_test.go internal/raft/cluster_test.go internal/raft/cluster_process_test.go scripts/bench_single_vs_raft.sh scripts/cluster_up.sh scripts/leader_failover.sh`）；doc 3 那句「其余 4 个 `/get` 读到同一个值」的判据在文档里保留原样，改到 doc 3 时补一句「带 `consistency=local`」。
- 验证：`http_rpc_test.go` 断言 Follower 上的默认 `/get` 是 503 且两个 leader 提示非空、`consistency=local` 仍回 200 与 `stale:true`；`cluster_process_test.go` 断言写完一条之后的默认 `/get` 在 Leader 上立刻读得到，`kill -9` Leader 期间的线性读只有成功与失败两种，没有读到旧值这一种。

## D25 领导权确认复用一轮 AppendEntries，请求与回执各加一个 `readRound`

- 背景：ReadIndex 的每次读要一次多数派领导权确认，租约续期要的是同一次确认。`Transport` 只有 `RequestVote` 与 `AppendEntries` 两个方法，RPC 按成员 id 升序串行发出（D23）。
- 备选：新增第三条 RPC `/raft/read-index`；复用一轮 AppendEntries，请求带 `readRound`、回执回显（本条）；只用时间戳不外呼，把租约交给上一次心跳的多数派回执。
- 结论：确认轮就是一次 `broadcastAppends()`，`AppendRequest` 加 `readRound`（0 表示这轮例行心跳不为读做确认），`AppendReply` 原样回显同一个编号；`appendFields` 的必填项从 6 个变 7 个，缺 `readRound` 直接 400。Leader 侧只认「编号相同、term 相同、`success=true`」的回执计票，`acks` 过半立即结算，不等剩下的回执。
- 理由：同任期的 `success` 回执本身就是领导权证据，再开一条 RPC 会让这一条读多走两次 RPC 往返，而 D23 按串行发出，每一跳都是一次完整往返。etcd 的 ReadIndex 同样复用心跳：`HeartbeatResponse` 带 attributed 字段，对拍时这一格有对应项。区分轮次靠回显编号。「本轮发出去的回执必然当场处理」这个隐含时序靠不住：`Propose` 与 `Read` 共用一条 outbox，一个在途轮的迟到回执落进下一轮计数就会把跨轮拼成多数派，基线 Lease Read 禁止跨轮拼凑。必填检查同 `3.1` §4 那三条 POST 路径的口径：补零后，为读发起的确认轮与例行心跳在请求上无法区分。
- 影响：`Transport` 接口的方法数不变，`cluster_fixture_test.go` 与 `httpTransport` 各少一路改动；`3.1` §4 的 `AppendRequest`／`AppendReply` 两个结构体与形状表各多一字段；Follower 只多做一件回显的事，§7 的六步与一致性检查一行不动；etcd 对拍时这一格是「两侧都复用心跳」的直接对照。
- 验证：`read_test.go` 的跨轮回执丢弃用例：注入一条编号错位的 `success`，断言计票数不变、`stale read round dropped` 落日志；过半即结算的用例断言第 3 票收满时 `read round settled` 的 `acks` 是 3、后两票的迟到回执不改读索引。

## D26 租约读一个可注入的单调时钟位，作为 D16 的唯一例外

- 背景：租约的公式是「起点 + 选举超时 - 漂移余量」，要的是墙上时间。D16 规定 `Node` 不读墙上时间，选举截止与心跳周期都按 tick 次数推进，用例零 `sleep`。
- 备选：租约也在 `Node` 里读 `time.Now()`；把租约判定推到入口层与 handler，`Node` 不持时间；用 tick 数当租约长度；租约读不实现，只做 ReadIndex。
- 结论：`Node` 上一个字段 `now func() int64` 返回单调纳秒，真实实现取 `time.Since(processStart)`，测试实现是一根可被用例拨动的计数器；只有租约的建立、失效判定与 `LeaseRemaining()` 三处经它取时间，`read.go` 之外一律不通过这个函数取时间。tick 继续驱动选举与心跳，一条都不改。
- 理由：tick 计数不能当租约长度。Go 的 `time.Ticker` 在接收方忙时把错过的 tick 合并成一次，而 D23 的串行让一轮 `Tick()` 最坏要等 4 次 RPC 超时（默认 400ms，接近整个选举窗口），此时 tick 数与墙上时间不成正比，用它算出来的租约比真实的安全窗长，线性一致就守不住。推到 handler 会让租约与角色转移分属两处计时，发现更高任期时清不掉另一半。做法与 `3.1` §5 的 `openTmp` 注入位同一条：留一个函数位隔离墙上时钟，用例照样零 `sleep`。
- 影响：D16 的范围收窄成「选举与心跳不读墙上时间」，`3.1` §4 的 `Start` 那格「`Node` 内部不起定时器」跟着补一句租约的例外记在 doc 4；`-tick-ms` 不进租约公式，调它不改变租约长度；`-clock-drift-ms` 默认 50ms，与一个 tick 同量级，是给 M14 的时钟跳变注入留的可调项（正式注入归 doc 6）；`Stats()` 多两项读数，注入脚本从它取租约剩余。
- 验证：`read_test.go` 用假时钟断言「广播发起前取时间、回执过半时窗口还剩 40ms」与「同一轮把假时钟拨过 450ms 则 `lease rejected`」两格；`election_test.go` 的既有断言不变，用来证明选举路径仍然不取墙上时间。

## D27 读的等待门限取 `lastApplied`，不加一个内存游标

- 背景：apply 循环里逐条改 map，`lastApplied` 每 64 条或本轮结束时才写回 state 游标（`3.1` §7、不变式 4）。读要等「状态机至少应用到读索引」，要等的数有两个候选。
- 备选：新增内存游标 `appliedIndex`，逐条 apply 就推进，读只等它；等 `lastApplied`（本条）；读不等游标，直接读 map 再看它是否已含到读索引的条目。
- 结论：等 `lastApplied >= readIndex`。`appliedIndex` 不引入，map 的前瞻值不作为门限。
- 理由：门限要能在盘上核对。`lastApplied` 是 state 文件里的四个标量之一，注入脚本和用例都能读回来，`appliedIndex` 只存在内存里，一次崩溃就查不到当时读到哪。取舍结果落在读延迟里：一批游标落盘的时间要等进去，M13 已经量出这个量级：一条写省 9.8ms（`docs/0` 的 D19 差值），读路径上同一批落盘的时间要再等一次。直接读 map 那一格判不了：map 比 `lastApplied` 长是常态，返回值里没有可断言的位置。
- 影响：不变式 4 的口径延伸到读路径（`4.1` §8 第一条）；`3.1` §7 的应用一节不改动，doc 5 的快照要把 `lastApplied` 当压缩起点那条预留仍然够用；读延迟表里 ReadIndex 与 Lease 两档都含这段游标落盘时间，与本地读对照时要在结论里写明。
- 验证：`read_test.go` 的等待用例：注入一条 `commitIndex` 已推进、`lastApplied` 落后 30 条的状态，断言这一条读排进 `applyWaiters`，`finishApply` 兑现之后才返回；`commit_test.go` 的坏 command 那格顺带证明读不会在 apply 走不过的那一段上返回成功。

## D28 单次读的等待上界由 handler 的 ctx 决定，`Node` 内部不起定时器

- 背景：等待应用可能一直不兑现：apply 卡在解不出的条目上。基线要求「等待应用超时」时读失败，等待要有一个上界。
- 备选：`Read` 里 `select` 一个 `time.After`；handler 侧 `context.WithTimeout`，`Node` 只看 ctx（本条）；不设上界，靠客户端自己断开。
- 结论：`internal/raft/rpc.go` 的 `handleGet` 用 `-read-timeout-ms`（默认 1000ms，从 `h.n.cfg` 取）包一层 `context.WithTimeout` 再调 `Read`；`Node` 里只有 `ctx.Done()` 一条退出路径，不建计时器。
- 理由：`Node` 一旦自己起定时器就改掉 D16 与 D23 定下的执行方式：所有时间推进都来自外层调 `Tick()`，状态机单线程，用例才能零 `sleep`。上界是请求级属性，跟 ctx 走还能复用客户端提前取消的那条路径，`Propose` 已经是这个做法（`3.1` §4 的 ctx 取消那一格）。
- 影响：`-read-timeout-ms` 只在 raft 的 handler 生效，`NewNode` 不参与换算，`cmd/miniraft-node` 一个字不改；超时与取消复用 `ErrCanceled`，落到 `errors.go` 已有的 500 `canceled` 那一档，映射表不加行；`ErrNotLeader` 仍走 503；读延迟表里 p99 的截断点就是这个上界。
- 验证：`http_rpc_test.go` 断言超时那一格的状态码与 `code`；`read_test.go` 断言超时返回后 `applyWaiters` 里那一格被摘掉，不留下唤醒不了的等待。

## D29 租约安全窗做启动校验，撑不住就按配置非法退出

- 背景：租约窗口 = `ElectionTimeoutMS - ClockDriftMS`，一轮广播的最坏耗时 = `(N-1) × min(2×-tick-ms, -election-timeout-ms)`（D23）。默认 5 节点、T=500ms、RPC 超时 100ms 时右边是 400ms、左边是 450ms，余量只剩 50ms。基线的要求是「时钟与超时配置无法保证租约有效期安全时，Lease Read 不得启用或必须回退到 ReadIndex」。
- 备选：启动时校验，不满足直接报错退 2（本条）；运行时发现窗口不够就自动降级成 ReadIndex；把 `-clock-drift-ms` 设成 0 让窗口看起来够。
- 结论：`Config.Validate()` 在 `ReadMode == lease` 时判 `ElectionTimeoutMS - ClockDriftMS > (N-1) × rpcTimeoutMS`，不满足返回错误，进程按 `2.1` §4 的退出码 2 收尾；`readindex` 档不做这条检查，改判 `-read-timeout-ms > (N-1) × rpcTimeoutMS`。
- 理由：静默降级会让读延迟的成因说不清：同一份配置下一次走租约、下一次走 ReadIndex，读延迟表里两档混在一起，doc 7 对拍时分不出哪个数字出自哪条机制。与 `2.1` §6 的既有口径一致：非法值直接报错，不回落默认。`-clock-drift-ms` 设 0 是把待观测的量当成不存在，基线在这里要求扣除漂移余量。
- 影响：M14 的数据要么用默认配置（租约余量只剩 50ms，命中率可能为 0，读数本身就是结论）、要么调大 `-election-timeout-ms` 再跑一档，两档各带自己的读数；读法与时钟的开关由 `scripts/bench_read_modes.sh` 自己传：`start_raft_cluster` 增加第三个位置参数（追加到 5 个进程命令行尾部的参数），bench 按档传 `-read-mode` 与 `-election-timeout-ms`，`cluster_up.sh` 不新增读法与时钟开关；`3.1` §9 第一条（心跳与选举超时的比值）在 doc 4 延伸成一条带 RPC 超时的三元不等式。
- 验证：`state_test.go` 的 `Load` 那一层加三格：`-read-mode=lease` 配 `-election-timeout-ms 400` 报错、`-read-mode=readindex` 同配置通过、`-clock-drift-ms` 为负报错。

## D30 一致性档只在 raft 的 handler 上解析，`internal/kvstore` 的导出面不动

- 背景：`/get` 在两个二进制里都有：`cmd/miniraft-kv`（单机，`internal/kvstore/http.go`）与 `cmd/miniraft-node`（`internal/raft/rpc.go`）。`consistency` 参数加在哪一层，决定 doc 2 的测试与 D21 的 baseline 是否跟着改。
- 备选：kvstore 的 handler 也认 `consistency`，两个入口形状一致；只在 raft 的 handler 上解析（本条）；把一致性档做进 `kvstore.KV`，让 KV 层自己判断能否服务线性读。
- 结论：`consistency` 只在 `internal/raft/rpc.go` 解析，`internal/kvstore` 的 `/get` 保持三个键的响应体、一个参数都不认；`kvstore.KV` 的 `Get` 签名不变。
- 理由：单机 KV 没有领导权，「线性一致」在那一侧没有定义，加一个恒为 `local` 的参数会让 raft 的概念出现在 baseline 里。D21 留着 `cmd/miniraft-kv` 就是要一份不动的对照，它的响应形状与 `2.2` 的用例集一起冻结；KV 层判断不了自己是不是在 Leader 上，第三条备选把这一层的职责放进了 KV 层。
- 影响：`internal/kvstore` 与单机脚本那 12 处 `/get` 一个字都不改（`http.go` 2、`http_api_test.go` 5、`crash_restart_test.go` 3、`scripts/crash_inject.sh` 2）；两个响应的字段集合不同（单机三键、raft 六键），这条差异要在 doc 7 的形状对照里按设计差异登记；`3.1` §4 的 `/get` 行与 `4.1` §4 的表分别描述两侧的当前形状。
- 验证：M14 的回归里 `2.2` 的套件必须与 doc 4 之前逐格相同；`http_rpc_test.go` 断言 raft 侧 `/get` 的六键固定、`internal/kvstore/http_api_test.go` 的三键断言不变。
