# 5.2 日志快照测试说明

## 1. 测试范围与环境

测试范围：`5.1` 描述的快照生成与提交、日志前缀删除、补发快照与接收快照，以及它们与日志视图基线 index、启动恢复顺序、状态机导出面的接缝。

分层沿用 `3.2` 的四层：

| 层 | 跑法 | 特点 |
|:---|:---|:---|
| 单元 | `go test ./internal/raft`，内存 transport + `t.TempDir()` | 零 `sleep`，按 `Tick()` 次数推进时间（D16） |
| 集成 | 5 个 `Node` 共用一个内存 transport 跑压缩与补发快照 | 真文件、真 fsync，耗时集中在 IO |
| 进程级 | 测试自己 `exec` 起 5 个 `cmd/miniraft-node`，让一台落后到日志前缀被删 | 只在回归与 M16 跑，`-short` 跳过 |
| 契约 | 两条新 HTTP 路径的字段与状态码断言 | 覆盖快照文件字节的解析与错误映射 |

环境与依赖：Linux 本地盘，Go 1.22 以上，第三方依赖仍是 `go.uber.org/zap`。`go test ./...` 不依赖 docker、不依赖 etcd。

## 3. 逐文件说明

| 文件 | 被测对象 | 关键断言 | 覆盖场景 |
|:---|:---|:---|:---|
| `snapshot_test.go` | `snapshot.go`（`5.1` §4、§5、§7，D31、D34） | 快照文件逐字节布局：8B magic、4B 条目数、每帧 `len 4B｜crc32c 4B｜op 1B(=0x20)｜keylen｜key｜vallen｜value`；重开文件能按序读回全部键值；条目数与实际帧数对不上判坏；payload 的 op 取 `0x01` 或 `0x10` 都判坏记录（两个目录互读）；帧 crc 不符判坏；`create` 写文件失败时不留正式名文件，只留 `*.tmp`；指针 `current.json` 写读一致，临时名写入 → Sync → rename；指针缺字段、半行 JSON、文件不存在三种情况按「没有快照」起，不按零值继续——前两种坏输入的指针指向的是一份真实快照文件，认得出坏的只有指针的字段校验这一层；指针指向的快照文件缺失或 checksum 不符时同样按「没有快照」起；启动时 `*.tmp` 与没有指针指向的孤儿快照文件被删掉；指针落不了盘时日志前缀不删，`create` 写出的快照文件留在目录里等指针，指针恢复可写后同一次快照照样提交且基线落在快照点之后一格 | 快照格式、提交顺序、指针 |
| `compact_test.go` | `compact.go`（`5.1` §7 删除边界与豁免，不变式 5） | Leader 的 `safeIndex` 取全部成员 `matchIndex` 的最小值，自己算一个成员；Follower 的 `safeIndex` 取本地 `commitIndex`；某成员落后 `commitIndex` 超过 `-snapshot-exempt-entries` 条时不参与 `safeIndex` 计算，豁免发生时日志里出现 `snapshot exemption applied` 且带成员 id 与落后条数；删除边界取 `min(snapshotIndex, safeIndex)`，`safeIndex` 小于快照点时一条不删；`dropLogPrefix` 的三种落点：整段文件删掉、保留的那一段截到它的帧起点、保留段之前的段文件删除而保留段长度不变；删除后日志视图的 `baseIndex` 前移到保留的那一条，`entryAt` 按新基线取下标，index 小于基线时取不到；term 到首末 index 的两个映射在删除后重建；快照点被 `lastApplied` 卡住时日志删不动并打出 `snapshot blocked by apply lag`，删除边界不放松、这一轮一条不删；Leader 删完前缀之后的下一次写入照常复制到多数派并提交，组包时 `prevLogIndex` 落在基线前一格、`prevLogTerm` 取 `baseTerm`；两次触发之间小于 `-snapshot-min-interval-ms` 时第二次不触发；`-snapshot-entries` 为 0 且 `-snapshot-bytes` 为 0 时自动触发全关，手动入口照常可用 | 删除边界、日志前缀删除、触发条件 |
| `install_test.go` | `install.go`（`5.1` §7 接收快照，不变式 3、7、8） | 收到合法快照后状态机被整体替换成快照内容，快照点之后的键值仍来自日志；请求 index 不大于本地快照点时直接返回成功且状态机不动；请求 index 小于本地 `lastApplied` 时同样不动状态机；快照的 magic、条目数、crc 三项任一不符返回 `ErrCorruptRecord`；接收后 `lastApplied` 推到快照 index，`commitIndex` 取本地值与快照 index 的较大者，`state` 游标已落盘；接收后本地快照文件与指针被更新，本地日志里 `<= snapshotIndex` 的条目被删掉；补发之后 Leader 的下一条写入照常复制给这个成员并生效，一致性检查里 `prevLogIndex` 等于它的快照点、`prevLogTerm` 等于它的快照 term 时按对上处理；重复收到同一份快照结果一致 | 补发快照的接收路径 |
| `wal_test.go`（增补） | `wal.go` 的基线 index 与前缀删除 | 视图的 `baseIndex` 初值是 1；`entryAt(index)` 按 `index - baseIndex` 取下标，index 小于基线取不到；恢复扫描在有快照时要求日志覆盖 `snapshotIndex+1` 起的连续区间，第一条晚于 `snapshotIndex+1` 判 `ErrStateMismatch`，早于它的残留条目按快照覆盖跳过；没有快照时第一条必须是 1；`dropPrefix` 之后 `entriesFrom` 只给基线之后的条目；`dropPrefix` 之后 `baseTerm` 是新 `baseIndex-1` 那一格的 term，日志删空且被删的最后一条不在那一格上时 `baseTerm` 留 0 | 日志视图基线 |
| `recovery_test.go`（增补） | `node.go` 的启动恢复顺序（`5.1` §7 启动恢复） | 启动先读快照再回放：快照点之前的状态只从快照来，快照点之后的条目按日志回放，`replayed_entries` 只数快照点之后解出 key/value 的条目；`(lastApplied, commitIndex]` 的补 apply 照旧；快照文件损坏时按没有快照起，此时日志前缀必须还在，否则启动失败并说明数据不可恢复；快照点与日志两条来源的键值合并后与写入终态一致 | 恢复顺序 |
| `http_rpc_test.go`（增补） | `rpc.go` 的两条新路径（`5.1` §4 形状表） | `POST /raft/snapshot` 在 Leader 上回 200 与 `snapshot_index`、`entries`，在 Follower 上回 503 `not_leader`；快照点选不出来回 409 `state_mismatch`；`POST /raft/install-snapshot` 缺 `index` 或 `term` 回 400，快照字节校验不符回 500 `corrupt_record`；请求体是原始字节，解析后与发出去的快照文件逐字节相同；方法不对 405、路径不对 404 | 契约 |
| `cluster_process_test.go`（增补） | 5 个真进程里的补发快照 | 一台节点被停到日志前缀被 Leader 删掉，重新起来后 Leader 给它发一次 `POST /raft/install-snapshot`，它把状态机补齐并读得到快照点之后的所有写；补发之后两台的日志基线一致 | 落后成员追平 |
| `internal/kvstore/kv_test.go`（增补） | `kv.go` 的导出面 | `Snapshot()` 导出全部键值且顺序稳定；`Restore()` 整体替换 map，被替换掉的键读不到；`Restore()` 之后 `Get` 返回快照里的值；空 map 的 `Snapshot()` 返回空切片 | 状态机导出面 |

## 5. 覆盖缺口与补充计划

| 缺口 | 现状 | 影响 | 处理办法 |
|:---|:---|:---|:---|
| 真掉电 | 造不出来，`kill -9` 只到进程级 | 快照写到一半、改名之前那两处提交点只有推演 | `scripts/crash_inject.sh` 增三个 kill 落点：快照写到一半、指针更新之前、删日志途中；每个落点重启后状态机与游标要能对上 |
| 快照文件损坏后的可恢复性 | 指针记了 checksum，损坏时按没有快照起 | 日志前缀已删的节点遇到快照损坏即不可恢复 | `recovery_test.go` 断这一格：日志前缀已删时启动失败并说明数据不可恢复，不静默起一个空 map |
| 压缩收益的量化 | 现在只有 `boot_ms` 一列，压缩前后没有对照 | 快照省了多少磁盘、重启快了多少没有数字 | `scripts/bench_snapshot.sh` 给出条数 × `boot_ms` × `log_bytes` × `snap_bytes` 的表，进 `docs/0` |
| 快照期间的写延迟 | 快照触发时导出状态机要持 `Node` 的锁 | 写延迟抬高的幅度与持续时间没有读数 | `bench_snapshot.sh` 记录 `snapshot created` 的 `cost_ms`，并给出该档的 p99 |
| 长期落后的成员 | 豁免之后靠补发快照追平，单次能追平没测过 | 连续豁免的成员能不能一直追平缺证据 | `cluster_process_test.go` 里让一台节点停住 3 轮快照周期再起来，断言它最终读得到全部写 |
| 并发触发 | 同一时刻只允许一个快照，用状态位挡 | 状态位失效时的后果没测 | `compact_test.go` 在快照生成期间再触发一次，断言第二次直接返回不生成 |

## 6. 与里程碑的对应

里程碑的任务拆分与先后顺序写在 `5.4`。

M15 收 `snapshot_test.go`、`compact_test.go`、`install_test.go` 三个新文件，`wal_test.go`、`recovery_test.go`、`http_rpc_test.go`、`cluster_process_test.go`、`internal/kvstore/kv_test.go` 五个文件的扩展格。M16 收 `scripts/bench_snapshot.sh` 的实测数据与 `docs/0` 的产出表。doc 2、doc 3、doc 4 的既有套件在 M15 之后仍要逐格通过。

门禁每个里程碑跑一次：`gofmt -l internal cmd`、`go vet ./...`、`go test ./...`、`go test -race ./...`。

变异自证按轻量口径，每条判据各造一个变异，跑完还原：

| 变异 | 预期被哪个用例杀掉 | 里程碑 |
|:---|:---|:---|
| 指针更新挪到删日志之后 | `snapshot_test.go` 的提交顺序那格、`recovery_test.go` 的重启那格 | M15 |
| 指针缺字段时按零值继续（不当没有快照） | `snapshot_test.go` 的指针三种坏输入 | M15 |
| 快照记录的 op 改成 `0x01` | `snapshot_test.go` 的两个目录互读判坏 | M15 |
| 删除边界取 `snapshotIndex`，不与 `safeIndex` 取小 | `compact_test.go` 的边界那格 | M15 |
| 豁免的成员仍参与 `safeIndex` 计算 | `compact_test.go` 的豁免那格 | M15 |
| `dropPrefix` 把保留段截到帧起点前一字节 | `compact_test.go` 的三种落点 | M15 |
| 接收快照时不校验 crc32c | `install_test.go` 的坏快照那格 | M15 |
| 恢复时回放从 index 1 起，不按 `snapshotIndex+1` 起 | `recovery_test.go` 的恢复顺序那格 | M15 |
