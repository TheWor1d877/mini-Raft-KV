# 3.1 Raft 核心逻辑设计

## 1. 模块定位

负责：`currentTerm`／`votedFor`／`log[]`／`commitIndex`／`lastApplied` 的持久化，选举超时与投票，AppendEntries 一致性检查与日志修复，commitIndex 推进，把已提交条目应用到 kvstore 的状态机。

不负责：一致性读（doc 4）、日志压缩与快照（doc 5）、故障注入矩阵（doc 6）、etcd 对拍（doc 7）等模块，全部归后续里程碑。`2.1` 交付的 KV 与 WAL 原语照常复用，kv 层不改。

角色只有三个：Follower、Candidate、Leader。没有 Pre-Vote，也没有 leadership transfer，`docs/1` 把这两项划成白板讲稿。

## 2. 架构概览

```text
cmd/miniraft-node/main.go   进程入口：配置、HTTP、tick 定时器、优雅关闭；5 个节点各起一个进程（D17）
internal/raft/              node.go 角色状态机 + Tick + 待提交回调表、vote.go RequestVote 收发与投票判定、append.go AppendEntries 收发与冲突回退及 commitIndex 推进、raftlog.go log[] 的内存视图与落盘、state.go 四个标量、rpc.go HTTP 客户端与 handler（字段与 §4 一一对应）、config.go、errors.go
internal/kvstore/           2.1 交付的 KV 状态机 + 帧编解码（EncodeFrame 等）
```

一次写要过的路径：客户端 `/put` → Leader 追加 raft 日志并 Sync → 按成员 id 升序发 AppendEntries（D23）→ 多数派落盘回执 → 推进 commitIndex → apply 到 KV → 回客户端 200。Follower 收到 `leaderCommit` 后在本地推进 commitIndex 并 apply，读到的值最终一致。

## 3. 包结构与依赖方向

- 允许：`internal/raft` → `internal/kvstore`。raft 用 `EncodeFrame`／`DecodeFrame`／`CheckFrame`／`FrameHeaderSize`／`MaxEntrySize` 这套帧原语（D15），并调用 `kvstore.KV` 的 `Put`／`Get`／`Flush` 当状态机。
- 段管理不复用：`kvstore` 的列段、建段即改名、坏尾裁剪、`*.tmp` 清理和目录锁都是未导出符号，`2.1` 的导出面不动，raft 侧按同款手法在 `internal/raft` 内自己实现一份（D15）。
- 禁止：`internal/kvstore` 引用 `internal/raft`，`2.1` §3 的禁止项照旧成立。
- `cmd/miniraft-kv` 保留，作为单机 baseline，M13 的吞吐对照要用它（D21）。

## 4. 核心接口

```go
type Node struct { /* 未导出：Config、角色、term、votedFor、raftlog、commit/apply 游标、transport、kv、logger */ }

func NewNode(cfg Config, kv *kvstore.KV, tp Transport, lg *zap.Logger) (*Node, error)
func (n *Node) Start() error
func (n *Node) Tick()
func (n *Node) Propose(ctx context.Context, key, value string) (index, term uint64, err error)
func (n *Node) Get(key string) (string, error)
func (n *Node) Role() Role
func (n *Node) Leader() (id string, addr string, ok bool)
func (n *Node) Stats() Stats
func (n *Node) Close() error

type Transport interface {
    RequestVote(to string, req VoteRequest) (VoteReply, error)
    AppendEntries(to string, req AppendRequest) (AppendReply, error)
}

// 以上类型全在 node.go 里（M10），rpc.go（M12）只负责把它们与下面的 JSON 字段名一一对上。
type Role int8 // RoleFollower / RoleCandidate / RoleLeader，日志与错误里用 follower／candidate／leader
type Stats struct { Term, CommitIndex, LastApplied, LastLogIndex, Votes uint64; Role Role } // 测试与注入脚本都从这读
type VoteRequest struct { Term uint64; CandidateID string; LastLogIndex, LastLogTerm uint64 }
type VoteReply struct { Term uint64; VoteGranted bool }
type LogEntry struct { Term, Index uint64; Command []byte }
type AppendRequest struct { Term uint64; LeaderID string; PrevLogIndex, PrevLogTerm uint64; Entries []LogEntry; LeaderCommit uint64; ReadRound uint64 }
// ConflictTerm 用指针：doc 3 的示例里 Follower 日志太短那一格回 "conflictTerm": null，用 0 表达不了「没有冲突 term」，http_rpc_test.go 断言 JSON 里就是 null。
type AppendReply struct { Term uint64; Success bool; ConflictTerm *uint64; ConflictIndex uint64; ReadRound uint64 }
```

`Node` 只有一把 `sync.Mutex`，护住四个标量、日志视图、投票计数与在途回调表；`Transport` 的两个调用一律在锁外发起（D23 串行），回执在同一处调用栈里当场处理，持锁调用会在内存夹具上自死锁。`handleRequestVote`／`handleVoteReply`／`handleAppendEntries` 未导出，M12 的 handler 与内存夹具调的是同一批函数。`Tick()` 由入口层的 `time.Ticker` 每 50ms 调一次，`Node` 自己不读墙上时间，单测直接按次数调 `Tick()`，全部用例零 `sleep`（D16）。`Transport` 有两个实现：`httpTransport` 走真 HTTP，单测与多进程实验用同一个 handler；内存实现只在测试里。

契约：

| 方法 | 输入输出 | 错误语义 | 并发与幂等 |
|:---|:---|:---|:---|
| NewNode | 配置、已打开的 KV、transport、logger | 恢复 state 与 raft log 失败返回 `ErrIO`；两个文件的游标对不上返回 `ErrStateMismatch` | 一个进程一个 Node；调用前 KV 已 `Open`，`raft/` 目录的独占由 `kvstore.Open` 的 `LOCK` 覆盖，raft 不取第二把锁（同进程内另一个 fd 对同一文件再 `flock` 会拿到 `EWOULDBLOCK`）；构造完即完成恢复，角色一律 Follower、选举截止取 `[T,2T)` 的随机 tick 数，未 Start 也能读状态；返回前把 `(lastApplied, commitIndex]` 补 apply 完 |
| Start | 无 | 第二次调用返回错误 | 只置运行标志；心跳与选举都由外层调 `Tick()` 驱动，`Node` 内部不起定时器（D16、D23）。apply 在 `Tick()` 末尾、`Propose` 返回前与每个回执处理之后执行，没有常驻 goroutine。租约不归 `Tick()` 驱动：租约起点取广播发起那一刻的单调时钟，窗口在 `NewNode` 里按 `-election-timeout-ms` 减 `-clock-drift-ms` 一次算好（D26） |
| Tick | 无 | 不返回错误 | 递减选举截止与心跳周期；Follower／Candidate 到点转 Candidate 并按成员 id 升序发投票，Leader 到点串行发一轮 AppendEntries（没有待复制条目时数组就是空的，即心跳）；一次 `Tick()` 内把当轮回执全部处理完，末尾补一次 apply |
| Propose | ctx、key/value | 成功回这条条目的 `index` 与 `term`，`/put` 响应体的那两个字段就是从这来的；出错时两个游标回 0。非 Leader 返回 `ErrNotLeader`（leader 提示由 `Leader()` 读）；日志 Sync 失败返回 `ErrIO` 并置失效；ctx 取消返回 `ErrCanceled`，条目继续复制并照常提交 | 同一 key 同一 value 重复提案各自占一条日志，由 apply 的幂等兜住（D4）。路径是追加 entry、按 `-raft-fsync` 决定是否 Sync、登记回调、按成员 id 升序给其余成员各发一次 `appendOnce`，然后等 apply 兑现；等回调期间不持锁，ctx 取消只撤自己那一格 |
| Get | key | `ErrKeyNotFound` 属正常控制流 | 本地档读，不确认领导权，可能读到旧值；等价于 `Read(ctx, key, ConsistencyLocal)`。客户端读路径的唯一入口是 `Node.Read`（4.1 §4），默认档是线性一致读 |
| Role／Leader／Stats | 无 | 不返回错误 | Stats 给出 term／role／commitIndex／lastApplied／lastLogIndex／投票数，供测试与注入脚本读 |
| Close | 无 | `ErrIO` | 停 tick → 关掉在途提案（返回 `ErrCanceled`）→ Flush KV → 落 state → 关文件 |

RPC 与客户端形状（字段与 doc 3 基线一致）：

| 路径 | 请求 | 响应 | 出错 |
|:---|:---|:---|:---|
| `POST /raft/request-vote` | `term`、`candidateId`、`lastLogIndex`、`lastLogTerm` | `term`、`voteGranted` | 非法 JSON 与缺字段 400 |
| `POST /raft/append-entries` | `term`、`leaderId`、`prevLogIndex`、`prevLogTerm`、`entries[]{term,index,command}`、`leaderCommit`、`readRound` | `term`、`success`、`conflictTerm`、`conflictIndex`、`readRound` | 非法 JSON 与缺字段 400 |
| `POST /put` | `{"key","value"}` | `{"ok":true,"req_id","index","term"}` | 非 Leader 503 `{"code":"not_leader","leader_id","leader_addr","req_id"}`，五个键固定，本节点没听说过 Leader 时两个提示回空串；失效 500 `io_error`；在途提案被 `Close` 作废 500 `canceled`；超限 413；非法 JSON 与缺字段 400 |
| `GET /get?key=&consistency=` | query：`key` 必填；`consistency` 取 `linearizable`（默认）或 `local`，其余值 400 | `{"key","value","req_id","read_index","term","stale"}`；`local` 档的读索引回 `0`、任期回本地任期、`stale` 回 `true` | 线性读在非 Leader 上 503 `not_leader`，五个键与 `/put` 那格完全一致；等待应用超时 500 `canceled`；404 `key_not_found`；缺 `key` 400；`consistency` 非法值 400。形状与两档语义归 doc 4（4.1 §4） |

`readRound` 是一致性读确认轮的编号，0 表示这一条不为任何读做确认；Follower 不解释它，只把请求里带来的编号原样回显（doc 4 的 D25，4.1 §4）。`append-entries` 的必填项是七个，`readRound` 在列。

`entries[].command` 是不透明字节，就是 `kvstore.EncodeEntry` 的产物，raft 层不解它（D4 的口径延伸）。`prevLogIndex=0` 且 `prevLogTerm=0` 表示从日志头开始，日志索引从 1 起；`entries=[]` 是心跳；term 比较先于一切，三个分支的处理见 §7。三条 POST 路径的必填字段逐个查过才进状态机：`request-vote` 要四个、`append-entries` 要七个、`/put` 要 `key` 与 `value`，缺一个就 400。补零会让一条坏请求看起来像合法心跳，那个 0 会把请求送进另一条处理分支。一个请求体只装一个 JSON 对象，多出来的按 400 拒掉（与 `2.1` §4 同口径）。

进程退出码沿用 `2.1` §4：`0` 收到 SIGINT／SIGTERM 正常收尾；`1` 打不开数据目录、写路径失效、serve 或收尾出错；`2` 配置非法或日志起不来。

## 5. 数据格式

state 小文件装四个标量（D12、D14），一行 JSON：`{"currentTerm":3,"votedFor":"node-2","commitIndex":8,"lastApplied":8}`，空串 `votedFor` 表示本任期未投票。写入方式是 `state.tmp` + `fsync` + `rename`（复用 D13 的创建即改名手法）。四样东西同批提交：一个任期的 term 和票必须一起落盘，分两个文件写会出现「term 新、票旧」的中间态。

`store` 打开临时名那一步走一个可注入的 `openTmp` 函数位：真实实现是 `os.OpenFile`，测试实现返回一根管道的写端。管道上 `Write` 正常、`Sync()` 一定失败，插入管道就能单独测出 `Sync` 这一步有没有真执行。`rename` 成功而 `Sync` 被跳过时读回的字节完全相同，只看文件内容判不了。不变式 2 由两段拼起来：`store` 在 `Sync` 失败时返回 `ErrIO` 且绝不改名（M9 的 `state_test.go`），投票处理拿到 `store` 错误就不回 `voteGranted=true`（M10 的 `vote_test.go`）。

raft 日志帧沿用 `2.1` §5 的帧，`len 4B | crc32c 4B` 覆盖 `len`+entry，只换 entry 的字节布局为 `op 1B(=0x10) | term 8B | index 8B | command 变长`，全部大端。一条 entry 受 `MaxEntrySize` 4MB 约束，`command` 沿用 key 1KB／value 1MB 上限。`op != 0x10` 判坏记录，判定顺序与 `2.1` §5 一致：剩余不足 8B、`len` 越界、读不满 entry、crc 不符、op 非法。

日志修复要按 index 截断尾部，所以内存里给每条 entry 记 `(term, index, 文件序号, 文件内字节偏移, 帧总长)`。`truncateTo(index)` 保留 `index` 及其之前的条目，把盘上长度收到 `index+1` 那条的帧起点——也就是 `index` 那条的帧终点；`index` 是日志最后一条时等价于不动，`index=0` 清空全部日志。截完从那个位置重新追加。恢复扫描按 index 递增读回全部 entry，最后一条的 index 即 `lastLogIndex`，index 不连续判 `ErrStateMismatch`（raft 日志中间不能有洞）。

data/node-1/

  raft/
    state                     原子重写小文件

| 开关 | 默认 | 含义 |
|:---|:---|:---|
| `-node-id` | 必填，形如 `node-1` | 必须在 `-peers` 里出现 |
| `-peers` | 必填 | `node-1=127.0.0.1:8801,node-2=...`，5 项，成员集合各节点必须一致；id 重复或两项共用一个地址都报错；RPC 的遍历顺序按成员 id 升序，书写顺序不参与寻址；静态成员，本期不改（`docs/1`） |
| `-addr` | 由 `-peers` 里本 id 那项推出 | 监听地址，客户端与 RPC 共用一个端口；显式给的值和成员表那项不一致直接报错，RPC 寻址只走表 |
| `-data-dir` | `data/node-<id>` | 一节点一目录，D8 的相对路径口径不变 |
| `-election-timeout-ms` | `500` | T；实际超时取 `[T, 2T)` 的随机值 |
| `-heartbeat-ms` | `100` | Leader 心跳周期；`>= -election-timeout-ms` 直接报错，不回落默认，理由见 §9 第一条 |
| `-tick-ms` | `50` | 入口层调 `Tick()` 的周期 |
| `-raft-fsync` | `true` | `false` 只跳过 raft 日志的 `Sync()`；KV 的 WAL 照 `2.1` 的默认按 `-batch-size` 批次 Sync，M12 不透传 `-fsync`。给 M13 与 doc 7 留吞吐对照（D19） |
| `-batch-size`／`-max-file-size`／`-log-level` | 与 2.1 同名开关同默认值 | 透传给 kvstore |

`Config` 的字段与这些开关一一对应：`NodeID`、`Peers`（`map[string]string`，id→`host:port`，必须含 `NodeID` 自己）、`DataDir`、`ElectionTimeoutMS`、`HeartbeatMS`、`TickMS`、`MaxFileSize`、`Fsync`、`LogLevel`，这九项在 M10 的 T21.1 一次建全，M12 的 T25.1 只做 flag 解析与 `-peers` 成员集合一致性检查。时间换算成 tick 只在 `NewNode` 里做一次：`electionTicks = ElectionTimeoutMS / TickMS`（向下取整，至少 1）、`heartbeatTicks = HeartbeatMS / TickMS`（至少 1），选举截止取 `[electionTicks, 2×electionTicks)` 的均匀随机值。`Validate()` 判 `HeartbeatMS >= ElectionTimeoutMS`、`TickMS <= 0`、`ElectionTimeoutMS <= 0`、`NodeID` 不在 `Peers` 里、`Peers` 为空这五种输入。分辨率误差（±一个 tick）归 M13 的重选主耗时，见 D16。

`log/miniraft-node.log` 由 raft 侧的 `NewNodeLogger` 打开：`kvstore.NewLogger` 的文件名固定为 `miniraft-kv.log`，写在 `2.1` 的导出面上，改它等于动 `2.1`，所以 raft 按同款的 JSON 编码与 UTC `ts` 自己开一份，理由与 D15 的段管理不复用同一条。一个进程一份日志文件，`component` 取 `kv`／`recovery`／`raft`／`raftlog`／`entry` 的事件都写在里面。

## 7. 关键流程

启动：`kvstore.Open` 先拿 `data/node-N/LOCK` 并重放 `wal/` 建 map → raft 建 `raft/` 与 `raft/log/` → 读 `raft/state`（文件不存在按 term 0／votedFor 空／两个游标 0 起；空文件、缺字段、半行 JSON 返回 `ErrIO`，不按零值继续） → 扫 `raft/log/` 重建 entry 视图 → 打开最大序号文件末尾准备追加 → 补 apply `(lastApplied, commitIndex]` → 起 HTTP → 起 tick。角色一律从 Follower 起，重启不保留旧角色。

投票（收到 RequestVote）：
1. `req.term > currentTerm`：更新 term、清空 votedFor、转 Follower、落 state，然后继续判定。
2. `req.term < currentTerm`：拒，回 `voteGranted=false` 带本地 term，votedFor 不动。
3. `req.term == currentTerm` 且 votedFor 非空且不等于 candidateId：拒，原因 `already_voted`。
4. 日志新旧比较：候选人的 `(lastLogTerm, lastLogIndex)` 必须不小于本节点的对应值，逐项比（先比 term，term 相同再比 index），不够新就拒，原因 `log_stale`。
5. 四条都过：votedFor=candidateId 并 Sync state 文件，成功后才回 `voteGranted=true`（§8 不变式 2）。

发起选举（`Tick()` 里选举截止到期）：term++ → votedFor=自己 → Sync state → 重置随机截止 → 给自己计一票 → 按成员 id 升序发 RequestVote，回执当场计入（D23）。收到回执：`resp.term > currentTerm` 则接受新 term、清空 votedFor、转 Follower、落 state；`voteGranted` 计数达到 `N/2+1`（5 节点即 3 票）且仍是 Candidate 则转 Leader，初始化 `nextIndex[i]=本节点 lastLogIndex+1`、`matchIndex[i]=0`，追加一条 no-op 并立刻按成员 id 升序发一轮 AppendEntries：这一轮就把 no-op 带出去，空条目数组只在没有待复制条目时才出现。同 term 的有效 AppendEntries 让 Candidate 立即转 Follower。选举截止在集齐多数派之前再次到期，Candidate 就 term++ 重开一轮。

追加与复制（Leader 侧 `Propose`）：编码 command 字节 → 造 entry `(term=当前, index=lastLogIndex+1)` 追加并 Sync → 登记待提交回调 → 按成员 id 升序向其余 4 个节点发 AppendEntries，回执当场处理（D23）→ 更新 `matchIndex` 与 `nextIndex` → 按 §8 不变式 3 推进 commitIndex → 回调由 apply 循环兑现。no-op 条目的 command 是空字节串，apply 时跳过 KV，只用来推进 commitIndex。给某个节点的请求由 `appendOnce(peer)` 组：取 `nextIndex[peer]` 及其之后最多 64 条，`prevLogIndex`／`prevLogTerm` 取它前一条；没有待复制条目时带空数组，这就是心跳，两条路径共用这一个函数。

Follower 处理 AppendEntries：
1. `req.term > currentTerm`：更新 term、清空 votedFor、转 Follower、落 state。
2. `req.term < currentTerm`：回 `success=false` 带本地 term，不重置选举截止。
3. term 相等或刚被更新：回 Leader 心跳，重置选举截止。
4. 一致性检查：`prevLogIndex=0` 直接过；否则本地第 `prevLogIndex` 条必须存在且 term 等于 `prevLogTerm`。不过则回 `success=false`，带上两个字段：`conflictTerm` 取该位置那条的 term，`conflictIndex` 取该 term 第一条的 index；本地没有 `prevLogIndex` 这条时，`conflictIndex=本地长度+1`、`conflictTerm` 为空。
5. 过检查：带条目时才截掉 `prevLogIndex` 之后的本地后缀，再按序追加 `entries[]`，Sync raft 日志，回 `success=true`。空数组的心跳不截：它只用来确认位置和带 `leaderCommit`，删日志的是带条目的那一次——否则一个 `nextIndex=1` 的新 Leader 发出一条心跳，就会把 Follower 上自己还没复制到的条目全清掉。
6. `commitIndex = min(leaderCommit, 本地最后一条 index)`，推进后交给 apply 循环。

冲突回退（Leader 侧，D20）：`conflictTerm` 在本节点日志里存在，`nextIndex` 置该 term 最后一条的 index+1；不存在则置 `conflictIndex`；`conflictIndex` 为空（Follower 日志太短）同样用该值。两个取值都要再与原 `nextIndex`-1 取小，最小为 1：提示的那个 term 在本节点日志里可能出现在被拒位置之后，照提示值往前跳会反复重发同一条请求，一轮 `Tick()` 内不收敛，所以回退严格递减。随后立刻重发。不等回执、盲目逐条 `nextIndex--` 的朴素回退已在 D20 否决，理由记在该条。

应用：apply 循环处理 `(lastApplied, commitIndex]`，按 index 升序。command 为空跳过，否则 `kv.Put`；每满 64 条（或本轮无更多已提交条目）调一次 `kv.Flush()`，成功后才把 `lastApplied` 写回 state 文件（§8 不变式 4），`commitIndex` 跟着同一次重写落盘。Flush 失败时内存游标与 state 文件都停在上一批的边界上，本条错误交回调用方。Leader 兑现客户端：`Flush` 成功后把 `(上一批的 lastApplied, 新的 lastApplied]` 上登记的在途提案回 `nil`，`Propose` 只在 apply 完成之后返回，handler 才回 200。

写失败：raft 日志 Sync 失败按 D5 的失效即停（fail-stop）处理，置失效标志，`Propose` 之后一律返回 `ErrIO`，`Get` 继续服务，进程由入口层退出。判据同样是「盘上边界是否已知」。raft 日志的建新段失败不置失效，与 `2.1` §7 的口径对齐。

## 8. 不变式

每条都能写成断言，测试用例编号在 `3.2`：

1. 一个任期内一个节点至多投出一票，重启不重置这条，`votedFor` 落盘在回执之前。
2. 投出票的回执发出时，`currentTerm` 与 `votedFor` 已在盘上。
3. commitIndex 只因为「当前任期的条目被多数派复制」而前进；旧任期条目只能被间接提交。
4. `lastApplied` 之前的每条已提交条目，其 KV 副作用已经进 `wal/` 并 Sync；`lastApplied ≤ commitIndex ≤ lastLogIndex` 恒成立。
5. term 单调不减；任何角色在任何时刻收到的更大 term 都会先落 state 再生效。
6. 同一 index 上两个节点的条目 term 可能不同（Leader 覆盖），但 index 不连续、或本地日志出现空洞，就是 bug。

## 9. 风险与约束

- 心跳周期要小于选举超时 T，并留出足够余量；比值过大时集群会活锁：Follower 会在心跳到达前发起选举，term 一路膨胀。启动配置对 `-heartbeat-ms >= -election-timeout-ms` 直接报错。
- 没有 Pre-Vote，隔离的旧 Leader 每轮超时都推高 term，回归后全集群要跟着补一轮选举才恢复。这一项的观测量是 term 膨胀值，与 etcd（有 Pre-Vote）的差值写进 doc 7。
- raft 日志每条 Sync，写吞吐低于 `2.1` 的 64 条批次；单机 KV 的吞吐是这条差值的对照（D19、D21）。
- 每次 term 变化与投票都要重写 state 文件并 Sync，一次选举在 5 节点上产生约 5 次小文件写；频率低，代价在选主路径上，不在稳态写路径上。
- 串行 RPC（D23）把单条的尾延迟直接加进当轮 `Tick()`：一轮选举最坏是 4 次超时相加，所以 M12 的 HTTP 客户端超时取 `min(2×-tick-ms, -election-timeout-ms)`，默认即 `min(100ms, 500ms)=100ms`，4 个节点全部无响应时一轮选举也不超过 T。稳态写路径同理，一次 `/put` 的复制延迟是 4 跳之和，M13 的吞吐对照里要按这个口径读（D19、D23）。
- 一进程一节点、5 份数据目录、5 个 HTTP 端口（客户端与 RPC 合用一个端口，5 个节点各占一个，`scripts/cluster_up.sh` 用从起始端口递增的连续 5 个），一台机器上 5 个进程加 etcd 侧的 5 个（D11），内存和磁盘要留量。
- 读有两档：`/get` 默认档是线性一致读，只在 Leader 上服务；`consistency=local` 那一档读的是本地状态机，可能拿到旧值，不参与线性一致的判定（doc 4 的 D24、4.1 §4）。doc 1 负载里「读到旧值」那格只能由 local 档观测到。

## 10. 日志字段

沿用 `2.1` §8 的封装与脱敏口径（`ts`、`level`、`msg`、`component`、`caller`、`req_id`），`component` 增加取值 `raft` 与 `raftlog`；`key`／`value` 的脱敏规则同 `2.1` §8，字段名全小写下划线。选举与复制路径的字段：发出侧的四条（`request vote sent`、`request vote failed`、`append failed`、`append denied`）带的是 `peer_id`，其余每条都带 `node_id`；下表在需要区分两者时标出字段名。

| 事件 | msg | 字段 |
|:---|:---|:---|
| term 变化 | `term changed` | `node_id`、`old_term`、`new_term`、`reason` |
| 角色变化 | `role changed` | `node_id`、`old_role`、`new_role`、`term` |
| 发起投票 | `request vote sent`／`received` | sent 带 `peer_id`、`term`、`candidate_id`、`last_log_index`、`last_log_term`；received 带 `term`、`candidate_id`、`last_log_index`、`last_log_term` |
| 投票结果 | `vote granted`／`vote denied` | `term`、`candidate_id`、`reason`（`log_stale`／`already_voted`／`term_old`／`state_unpersisted`；最后一个是 state 落不了盘，不变式 2 要求这时不能回 `voteGranted=true`） |
| RPC 发送失败 | `request vote failed`／`append failed` | `peer_id`、`term`、`error`；这一票计为一次失败，不重试（D23）。`append failed` 是「给对端发 AppendEntries 没发出去」，与下面那条状态机的 `apply failed` 是两件事 |
| 计票与当选 | `votes counted` | `term`、`votes`、`needed` |
| 当选后 no-op 落不了盘 | `no-op entry not appended`／`no-op entry not persisted` | `node_id`、`term`、`error`；转 Leader 的 state 已经落了，只是这一轮不排第一轮复制。Sync 失败之后 raft 日志的写路径自己关掉（D5），这一任期的后续写入一律拿 `ErrIO` |
| 复制失败与回退 | `append denied` | `peer_id`、`prev_log_index`、`conflict_term`、`conflict_index`、`next_index`；`conflict_term` 只在对方给了任期时出现 |
| 提交与应用 | `entry applied` | `index`、`term`、`commit_index`、`last_applied`；`op_seq` 在 kv 层的 `Put 生效` 那条里（`2.1` §8），raft 侧看不到它，两条按 index 次序串起来 |
| 已提交条目进不了状态机 | `apply failed` | `node_id`、`commit_index`、`last_applied`、`error`；复制已经兑现，这批的游标停在上一批边界上重试（不变式 4、D5 的下游）。kv 层的失效日志排在同一条调用路径的下游 |
| state 落盘 | `raft state persisted` | `current_term`、`voted_for`、`commit_index`、`last_applied`、`sync_ms` |
| state 落不了盘 | `raft state transition not persisted` | `node_id`、`reason`、`error`；该次转移作废，内存里的角色与四个标量都不动（不变式 5） |
| raft 日志滚动 | `raft log rolled over` | `from_file`、`to_file`、`size_bytes` |
| 复制冲突截断 | `raft log suffix dropped` | `kept_through_index`、`dropped_entries`、`entries_left` |
| raft 日志写路径失效 | `raft log disabled` | `failed_at_offset`、`error` |
| raft 日志损坏与恢复裁剪 | `corrupt record tail`／`raft log truncated` | 前者与 `2.1` 同款 `file`、`offset`、`expect_len`、`got_len`、`reason`；后者带 `file`、`offset`、`truncated_bytes`，与 `2.1` 的 `wal truncated` 同款 |
