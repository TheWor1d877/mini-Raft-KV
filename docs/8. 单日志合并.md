# 8. 单日志合并

KV 的 WAL 与 Raft 日志合成一份持久日志，由 Raft 日志承担全部职责，对外的名字统一成 WAL。

## 一、当前状态

节点数据目录里有三处持久化对象：

| 对象 | 路径 | 内容 | 写入时机 |
|---|---|---|---|
| WAL | `<data-dir>/raft/wal/%08d.wal` | 帧头 8B + `op(1B)+term(8B)+index(8B)+command` | Leader 追加每条后一次 `Sync()`，Follower 收到一批后一次 |
| 游标 | `<data-dir>/raft/state` | currentTerm、votedFor、commitIndex、lastApplied | 每批 apply 一次 |
| 节点日志 | `<data-dir>/log/miniraft-node.log` | 结构化日志 | 事件发生时 |

`command` 装的是 `kvstore.EncodeEntry` 的产物（`op 1B(=0x01) | keylen 4B | key | vallen 4B | value`），一条 KV 写就是一条日志条目。帧头与 crc 由 `kvstore/record.go` 定义，raft 侧直接引用；段的原子创建（`.tmp` 写完 rename）、损坏处截断、`*.tmp` 清理在 `internal/raft/wal.go` 里实现。

落盘点只有一处：数据的落盘边界在日志追加那次 `Sync()` 上。`state` 文件里只有游标，不含数据。

`op` 取两个值：`0x01`（KV 的 Put）与 `0x10`（日志条目）。快照标记没有分配，留到快照那一步再定。

## 二、恢复路径

启动顺序：`kvstore.Open` 拿目录锁 → 读 `raft/state` → 扫 `raft/wal/` 重建 entry 视图 → 打开最大序号文件末尾准备追加 → 把 `[1, lastApplied]` 的条目重放进状态机 → 补 apply `(lastApplied, commitIndex]` → 起 HTTP 与 tick。

状态机是内存 map，没有独立的操作日志。回放时空 command 的条目跳过，选举 no-op 不进状态机，也不计入 `state rebuilt from wal` 的 `replayed_entries`。

日志里解不出 key/value 的条目让启动直接失败，不静默跳过。`state.lastApplied` 可以落后于状态机里真正生效的位置，永不领先。

## 三、单节点集群档

`cmd/miniraft-kv` 是成员表只有自己的 raft 集群，数据目录默认 `data/`。选举照常跑一轮：自票即多数派，节点先停在 Follower，等满一个选举截止（500~1000ms）自票当选，当选那一轮在日志尾部追加一条 no-op，所以第一条客户端写落在 index 2。

`scripts/crash_inject.sh` 与 `scripts/bench_single_vs_raft.sh` 的对照臂挂在它上面。

## 四、已知限制

- 数据目录不兼容。合并之前的数据目录里 `wal/`（KV WAL）与 `raft/log/*.rlog` 两份内容都在，新代码只读 `raft/wal/`，旧目录读不出来：旧 `raft/state` 的 `commitIndex` 越过空日志的末尾，节点启动时返回 `ErrStateMismatch`。旧数据全部丢弃，迁移不做，脚本每次重建目录（`bench_single_vs_raft.sh` 每档开头 `rm -rf`，`bench_read_modes.sh` 与 `crash_inject.sh` 同样）。默认集群根目录 `data/node-1`..`data/node-5` 里的老目录已删除，现在这五个目录是合并后代码建的。
- 没有快照。重启是全量回放，回放耗时随日志长度线性涨，磁盘占用也只增不减。快照与压缩归 `docs/5. 日志快照.md`，那是下一步工作。
- 一次选举没过半就重开一轮，旧 Leader 独走期间 term 继续推高。Pre-Vote 不做，term 膨胀的量化归 doc 6（D22）。

## 五、下一步

快照与压缩。快照落点与恢复顺序写在 `docs/5. 日志快照.md`：快照是旧日志能丢的依据，落 `<data-dir>/raft/snapshot/`，恢复时先读快照再回放 `snapshotIndex` 之后的条目。

快照标记的 `op` 取值在那一轮定，合并期没有分配第三值。
