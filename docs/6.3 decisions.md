# 6.3 成员变更与 Learner 决策记录

编号接 `5.3` 的 D34 往后排。

## D35 配置条目用 raft 日志承载，command 首字节取 `0x11`

- 背景：成员配置要按 raft 的复制与提交规则走，首先要有一种在日志里表达它的编码。
- 备选：给 `LogEntry` 加一个 kind 字段；用 command 的首字节分流；用 WAL 帧的外层 op 分流。
- 结论：配置条目就是一条 raft 日志条目，command 为 `0x11｜count｜id...`，负载是全量投票集合。
- 理由：RPC 的 `LogEntry` 只有 term、index、command 三个字段，加 kind 要改 `3.1` §4 的形状表、`append-entries` 的必填项检查与两条测试夹具。外层 op 只在磁盘上存在，`AppendRequest` 带不过去，接收方只能靠 command 猜种类。首字节分流与 kvstore 用 `0x01` 标操作码是同一条约定，raft 层对 command 仍然不作解释，只在追加、回放与 apply 三处分流。
- 影响：`membership.go` 两个纯函数 `encodeConfig`／`decodeConfig`；`append`、`commit`、`node.replayLog` 各加一个分支。
- 验证：把配置条目当 KV 条目解、把 KV 条目当配置条目解，两种都判坏记录；配置条目在 `append-entries` 的 JSON 里与普通条目同形。

## D36 配置视图只由快照与日志推出，快照格式升到 MRSNAP02

- 背景：配置条目会随日志前缀一起被删掉，压缩之后要有地方回答「当前投票集合是什么」。
- 备选：把投票集合写进 `raft/state` 的第五个字段；每次变更单独写一个配置文件；快照文件头带上，日志负责之后的增量。
- 结论：快照文件头记投票集合，日志里的配置条目负责快照点之后的变化，`raft/state` 仍是四个标量。
- 理由：配置条目的生效点不等提交，任何独立的落盘副本都要额外定义「未提交的变更算不算」，而日志本身已经给出答案。`raft/state` 每批 apply 重写一次，频率与配置变更差几个数量级，混进去会让每次 apply 拖着配置一起改。压缩之后快照是唯一的前缀来源，投票集合必须随它走。
- 影响：快照文件从 MRSNAP01 升到 MRSNAP02，头部多一段 voters；`current.json` 的字段不变，`checksum` 覆盖新的一段；MRSNAP01 按坏记录拒绝。
- 验证：压缩之后重启，视图等于快照头的集合同样；把快照头的 voters 段删掉后重启，判坏记录并按没有快照起；没有可用快照时回到 `-peers` 全表。

## D37 地址表静态、投票集合动态

- 背景：`Config.Peers` 现在同时承担寻址与「谁有投票权」两件事，成员变更要把这两件事拆开。
- 备选：配置条目带上成员地址，支持节点动态加入与退出；地址表保持命令行给的超集，配置条目只改角色。
- 结论：`-peers` 是地址表，也是首次启动的默认投票集合；配置条目只把某个节点在 voter 与 learner 之间切换。
- 理由：带地址的配置要第二份成员表、第二个落盘点，还要处理新节点的数据目录、地址冲突与旧地址残留。doc 6 基线只要求降级与提升，这两件事已经能覆盖「先追平再纳入 quorum」与「坏成员踢出 quorum」。地址表静态把范围收在角色翻转上。
- 影响：`-peers` 的含义从「成员集合」扩成「所有可能成员的地址」；扩容要改所有节点并重启；配置条目里出现表外 id 判坏记录。
- 验证：`changeMembership` 对表外 id 返回 `ErrConfigRejected`；构造一条含表外 id 的配置条目，解码报 `ErrCorruptRecord`。

## D38 单条变更，提交要新旧两个多数派

- 背景：配置条目自身也要提交，提交条件决定变更期间集群能不能继续选主与写。
- 备选：joint consensus 两阶段（先写 C_old,new 再写 C_new）；单条变更只按新集合算多数派；单条变更加新旧双多数派。
- 结论：一次只允许一条配置条目在飞，提交要求旧集合与新集合各有多数派，`commitIndex` 不越过未提交的配置条目。
- 理由：doc 6 基线 §三写的是「满足新旧配置的 quorum 条件后提交」，双多数派与它逐字对应。单条变更的多数组交集已经保证不出现双 Leader，双多数派是收紧而不是补丁。joint consensus 要多两条日志、两套视图与一份过渡期的 quorum 计算，本项目的变更频率用不到。
- 影响：`Node` 增加 `pendingConfig`，记旧集合、新集合与 index；`advanceCommit` 多一个屏障分支；变更期间的第二个请求回 409。
- 验证：4 个 voter 缩到 3 个时，只有新集合的 2 票不推进提交；只有旧集合的 3 票也不推进；两个条件都满足才推进。配置条目后面紧跟一条普通条目时，后者不能先把前者带过提交点。

## D39 自动降级按 tick 计数

- 背景：豁免之后 5 分钟的计时要有一个时间源。
- 备选：读墙钟毫秒；按 `Tick()` 次数累计。
- 结论：开关 `-learner-demote-ms` 默认 300000，`NewNode` 换成 tick 数，与选举截止同一条口径。
- 理由：`Node` 不读墙上时间，单测按次数调 `Tick()`、零 `sleep`（D16）。快照最小间隔用墙钟是因为它要跨多次触发比较，而自动降级只在一个进程里按拍推进，换成 tick 数不丢信息。代价是 `-tick-ms` 调大之后实际时长跟着变，与选举截止同一个误差量级。
- 影响：`Config` 增加 `LearnerDemoteMS`，开关表多一行；豁免计时表挂在 Leader 上，跟着 matchIndex 走。
- 验证：6000 次 `Tick()` 触发降级，5999 次不触发；中途追平一次则计时清零，重新落后要重新数满。

## D40 变更与查询走 HTTP 两条路径

- 背景：降级、提升需要一个外部入口，测试与脚本也要能读到各节点的视图。
- 备选：只提供 Go 方法，测试直接调；新增 gRPC 服务；复用现有 HTTP 端口。
- 结论：`POST /raft/membership` 提交变更，`GET /raft/membership` 读当前视图，与 `/put`、`/raft/snapshot` 共用一个监听端口。
- 理由：项目里节点间与客户端路径都是 JSON over HTTP，再引一套协议栈只多一份错误映射。进程级用例跑在独立进程里，没有 Go 调用入口；`GET` 让这些用例不用读内部字段就能断言视图。四条拒绝原因共用一个 409 `config_rejected`，具体原因写在 `error` 字段，错误码集合不膨胀。
- 影响：`rpc.go` 两条路由与一组必填字段；`statusFor` 增加 `ErrConfigRejected` 的映射；`3.1` §4 的形状表同步加两行。
- 验证：缺 `id` 或 `role` 回 400；role 取第三值回 400；Follower 回 503 带 leader 提示；四类拒绝各回 409 且 `error` 里能读出原因；`GET` 的 voters 与 learners 都是升序。

## D41 Leader 自降在排完复制之后 step down

- 背景：配置变更可以把 Leader 自己从 voter 集合里去掉，而 Leader 必须属于 voter 集合。
- 备选：追加后立即 step down；等配置条目提交后 step down；追加并排完本轮复制后 step down。
- 结论：追加配置条目并排完这一轮复制之后转 Follower，term 不递增。
- 理由：立即 step down 时这一轮复制还没排进 outbox，配置条目一条都没发出去，变更等于没发生。等提交再退要求一个已经不是 voter 的节点继续担任 Leader，与 doc 6 基线 §六冲突。排完复制再退，条目至少发给了其余节点，新选出的 Leader 有机会带着它。
- 影响：`changeMembership` 末尾一个分支；`role changed` 的 reason 取 `demoted to learner`。
- 验证：5 进程里降级 Leader 自己，配置条目进入其余节点的日志；新 Leader 在 300ms 内产生；旧 Leader 的 `GET /raft/membership` 里自己不在 voters 里；条目被截掉时视图回退到旧集合，两种结果都不出现双 Leader。
