# 9. 二进制使用

两个进程入口。`bin/miniraft-node` 是 5 节点集群里的一员，成员表由 `-peers` 给；`bin/miniraft-kv` 是成员表只有自己的单节点集群，崩溃注入、快照对照和吞吐基线都跑在这一档，恢复路径与 `miniraft-node` 同一条。

```bash
go build -o bin/miniraft-node ./cmd/miniraft-node
go build -o bin/miniraft-kv  ./cmd/miniraft-kv
```

## 开关

18 项开关两个二进制都注册，`miniraft-kv` 忽略 `-peers`，成员表按 `-node-id` 与 `-addr` 现造一条。未识别的参数与非法值直接报错退出，不回落默认值。

| 开关 | 默认值 | 作用 |
|---|---|---|
| `-node-id` | `miniraft-node` 必填，`miniraft-kv` 缺省 `node-1` | 本进程在成员表里的 id |
| `-peers` | `miniraft-node` 必填 | 成员表，形如 `node-1=127.0.0.1:8801,node-2=...` |
| `-addr` | 取 `-peers` 里本 id 那项，`miniraft-kv` 缺省 `127.0.0.1:8742` | 监听地址，客户端与节点间 RPC 合用一个端口 |
| `-data-dir` | `data/node-<id>`，`miniraft-kv` 取 `data` | 数据目录，路径相对当前工作目录 |
| `-election-timeout-ms` | 500 | 选举超时基准 T，随机区间 [T, 2T) |
| `-heartbeat-ms` | 100 | 心跳周期，大于等于 T 时启动报错 |
| `-tick-ms` | 50 | 入口驱动 `Tick()` 的周期 |
| `-raft-fsync` | true | 每条日志追加后 Sync，关掉只用于吞吐对照 |
| `-read-mode` | `lease` | 线性一致读走租约还是每读一轮确认，取 `lease`／`readindex` |
| `-read-timeout-ms` | 1000 | 单次线性读的上界，短过一轮广播会在启动期报错 |
| `-clock-drift-ms` | 50 | 从租约窗口里扣掉的时钟余量 |
| `-snapshot-entries` | 1000 | 快照点后攒够多少条日志触发压缩，0 关掉这条触发 |
| `-snapshot-bytes` | 67108864 | 日志目录长到多少字节触发压缩，0 关掉 |
| `-snapshot-min-interval-ms` | 60000 | 两次快照的最小间隔 |
| `-snapshot-exempt-entries` | 1000 | 落后这么多条以上的成员免于把删除边界压低 |
| `-learner-demote-ms` | 300000 | 豁免成员落后多久被自动降成 learner，0 关掉自动降级 |
| `-max-file-size` | 104857600 | 段文件写到多少字节滚动 |
| `-log-level` | `info` | `debug`／`info`／`warn`／`error`／`panic`／`fatal` |

启动期报错的另外三种输入：`-addr` 与 `-peers` 里本 id 那项不一致、两个 id 共用一个地址、`-peers` 里出现重复 id。同一份数据目录再起第二个进程被 `LOCK` 挡住。

## HTTP 接口

客户端只用两条，其余四条是节点之间和脚本用的。请求体与响应体都是 JSON，键名如下。

| 请求 | 成功响应 | 说明 |
|---|---|---|
| `POST /put`，体 `{"key","value"}` | `{"ok","req_id","index","term"}` | 走完整的日志复制，多数派回执后才返回 |
| `GET /get?key=&consistency=` | `{"key","value","req_id","read_index","term","stale"}` | `consistency` 取 `linearizable`（默认）或 `local`，`local` 档 `read_index` 回 0、`stale` 为真 |
| `GET /raft/membership` | `{"voters","learners","index","term","leader_id"}` | 当前配置与 Leader |
| `POST /raft/membership`，体 `{"id","role"}` | `{"ok","index","term"}` | 手动升降级，`role` 取 `voter`／`learner` |
| `POST /raft/snapshot` | `{"ok","snapshot_index","entries"}` | 让 Leader 当场触发一次压缩 |
| `POST /raft/install-snapshot?index=&term=` | `{"ok","snapshot_index"}` | 请求体是快照文件的原始字节，两个 query 参数缺一个回 400 |

非 Leader 上的 `/put` 与 `/get` 一律 503，响应体固定五键 `error`／`code`／`req_id`／`leader_id`／`leader_addr`，`code` 是 `not_leader`，没听说过 Leader 时两个 leader 字段回空串、键仍在。`req_id` 由服务端自增生成（`req-<序号>`），客户端传不进来，所以同一条写重发两次会占两个 `index`。

## 数据目录

```text
<data-dir>/LOCK                     目录锁，同一份目录只允许一个进程
<data-dir>/log/miniraft-node.log    一个进程一份结构化日志
<data-dir>/raft/state               currentTerm、votedFor、commitIndex、lastApplied 四个标量，JSON 整体重写
<data-dir>/raft/wal/00000000.wal    段文件，命名 %08d.wal，按 -max-file-size 滚动
<data-dir>/raft/snapshot/           快照文件 %08d.snap 与指针 current.json
```

两个二进制的进程日志都叫 `miniraft-node.log`，位置按各自的 `-data-dir` 分开。

## 脚本

| 脚本 | 干什么 | 命令 | 看什么 |
|---|---|---|---|
| `cluster_up.sh` | 起 5 个 `miniraft-node` 并逐个探活 | `scripts/cluster_up.sh [起始端口=8801] [数据根目录=data]` | 每节点一行 `node_id pid addr`，清单写进 `<数据根目录>/cluster.up` |
| `cluster_down.sh` | 按清单逐个 SIGTERM | `scripts/cluster_down.sh [数据根目录=data]` | 每个进程日志末尾一条 `node stopped` 带 `exit_code` |
| `leader_failover.sh` | 杀 Leader 量重选耗时，跑 N 轮 | 先 `cluster_up.sh`，再 `scripts/leader_failover.sh [轮数=3]` | 每轮一行 `killed_leader elected_in_ms term_before term_after writes_inflight` |
| `crash_inject.sh` | 单节点写 N 条、`kill -9`、重启对账 | `scripts/crash_inject.sh [写入条数=2000] [第几条后杀] [raft-fsync] [段上限] [落点=wal]` | 已回执的写是否一条不少 |
| `demote_lagging.sh` | 停一个 voter，量自动降级前后的写延迟 | `scripts/demote_lagging.sh [写入条数=2000] [learner-demote-ms=3000]` | 每阶段一行 `phase acked attempted p50_ms p99_ms voters learners` |
| `bench_single_vs_raft.sh` | 单节点与 5 节点的写吞吐对照 | `scripts/bench_single_vs_raft.sh [写入条数=2000]` | 三档 `single-node-fsync`／`raft-fsync`／`raft-nofsync` |
| `bench_read_modes.sh` | 三种读法的延迟对照 | `scripts/bench_read_modes.sh [读取条数=2000]` | 四档 `lease`／`readindex`／`local`／`lease-t1000` |
| `bench_snapshot.sh` | 压缩开与关的恢复耗时与磁盘对照 | `scripts/bench_snapshot.sh [写入条数=5000]` | 两档 `no-snapshot`／`snapshot` |

## 停点开关

故障注入靠环境变量把进程停在指定提交点。不设或名字不匹配时不睡，进程行为与没有这段代码一致；停点只触发一次，复制重试不会让它再停一遍。

| 变量 | 作用 |
|---|---|
| `MINIRAFT_CRASH_POINT` | 选中的停点名 |
| `MINIRAFT_CRASH_PAUSE_MS` | 在该停点停多少毫秒，停够这段时间内被 `kill -9` 就落在这个窗口里 |
| `MINIRAFT_CRASH_AFTER_MS` | 进程起来多久之后停点才生效，用来先把预热期的写完 |
| `MINIRAFT_SNAPSHOT_PAUSE_MS` | 快照三处提交点的停顿，与上面三个互不影响 |

脚本侧另有三个：`crash_inject.sh` 的 `KEEP=1` 保留数据目录并打印路径，`bench_snapshot.sh` 的 `SNAP_ENTRIES` 覆盖压缩档阈值，`bench_read_modes.sh` 的 `BENCH_LEASE_EXTRA` 往 `lease-t1000` 那档追加节点参数。
