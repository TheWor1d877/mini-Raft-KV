# 6.1 成员变更与 Learner 设计

## 1. 模块定位

负责：把成员角色变更写成一条 raft 日志条目，让它在追加时生效；按投票集合计算多数派；约束 learner 的行为；提供降级、提升、Leader 自降与超时自动降级。

不负责：日志复制本身（`3.1` §7）、快照文件与删除边界（`5.1`）、故障注入矩阵（doc 7）、与 etcd 的对拍（doc 8）。

doc 6 基线的三条规则原样承接：配置条目在追加到本地日志时生效，不等提交；learner 只收日志，不投票、不计多数派；配置条目按新旧两份配置的多数派提交。

成员变更只改角色，不改地址表。新增或移除节点要先改所有节点的 `-peers` 并重启，这部分不做（D37）。

## 2. 架构概览

```text
internal/raft/membership.go   配置条目的编解码、投票集合视图、多数派
internal/raft/node.go         Node 增加 membership 与 pendingConfig，选举与自降的分支
internal/raft/append.go       追加时换视图、截断后重算
internal/raft/commit.go       配置条目的双多数派提交与提交屏障
internal/raft/read.go         确认轮按投票集合计票
internal/raft/snapshot.go     快照文件头写投票集合
internal/raft/install.go      接收快照时替换视图
internal/raft/rpc.go          变更与查询两条 HTTP 路径
internal/raft/config.go       -learner-demote-ms
```

手动变更的路径：`POST /raft/membership` → Leader 校验 → 追加配置条目并 Sync → 换本地视图 → 按地址表复制 → 回执凑齐新旧两个多数派 → 推进提交点 → 打日志。

自动降级走同一条路径：`Tick()` 里 Leader 检查豁免计时 → 到期调用变更，目标是不满足条件的成员，角色取 learner。

启动与压缩两条路径也带上视图：读快照时视图取文件头里的投票集合，回放日志时后出现的配置条目覆盖它；生成快照时把当时的视图写进文件头。

## 3. 包结构与依赖方向

- 允许：`internal/raft` → `internal/kvstore`。kvstore 不认成员配置，配置的编解码在 raft 侧。
- `membership.go` 只吃 `[]byte`、id 列表与地址表，不碰 `wal` 与 `snapshotter` 的具体类型。
- `Config.Peers` 仍是地址表，字段不改；投票集合挂在 `Node.membership` 上，跟着日志视图一起换。
- 禁止：`internal/kvstore` 引用 `internal/raft`。

## 4. 核心接口

```go
// membership.go
type memberSet struct{ voters []string } // 升序，只装 id

func newMemberSet(voters []string) memberSet
func (m memberSet) isVoter(id string) bool
func (m memberSet) majority() int
func (m memberSet) others(self string) []string

func encodeConfig(voters []string) ([]byte, error)
func decodeConfig(cmd []byte, known map[string]string) ([]string, error)

// node.go
type configView struct {
    voters     []string // 当前视图
    index      uint64   // 最后一条配置条目的 index；没有配置条目时取快照点，再没有就是 0
    prevVoters []string // 最后一条配置条目生效之前的集合
}

func (n *Node) changeMembership(id, role string) (index, term uint64, err error)
func (n *Node) Membership() (voters, learners []string, index, term uint64)
func (n *Node) applyConfigLocked(view configView)
func (n *Node) rebuildConfigLocked() configView
```

契约：

| 方法 | 输入输出 | 错误语义 | 并发与幂等 |
|:---|:---|:---|:---|
| `encodeConfig` | 升序 id 列表，输出 `0x11｜count｜id...` | 空集合、重复 id、id 超过 255 字节返回错误 | 纯函数，不改状态 |
| `decodeConfig` | command 字节与地址表，输出升序 id 列表 | 首字节不是 `0x11`、count 与长度对不上、id 重复、id 不在地址表，一律返回 `ErrCorruptRecord` | 纯函数 |
| `changeMembership` | 目标 id 与目标角色 | 非 Leader 返回 `ErrNotLeader`；目标不在地址表、角色没有变化、已有配置条目在飞、降级之后没有投票者，返回 `ErrConfigRejected` | 校验、追加、换视图、排复制在同一段持锁内完成；被拒时日志一条不写；追加后 Sync 失败返回 `ErrIO`，视图与日志都不动 |
| `applyConfigLocked` | 新的 `configView` | 不返回错误 | 只换内存视图，不写盘；同一视图重复调用没有副作用 |
| `rebuildConfigLocked` | 无，输出重算的 `configView` | 不返回错误 | 由快照头里的集合起，按日志顺序重放配置条目；截断之后必须调用 |
| `Membership` | 无 | 不返回错误 | 返回副本，调用方改不到内部切片；未 Start 也能读 |

HTTP 路径与 `/put`、`/get` 共用同一个监听端口：

| 路径 | 请求 | 响应 | 出错 |
|:---|:---|:---|:---|
| `POST /raft/membership` | `{"id":"node-2","role":"learner"}` | `{"ok":true,"index":7,"term":3}` | 缺字段或 role 不是 voter／learner 400 `bad_request`；非 Leader 503 `not_leader` 并带 leader 提示；其余拒绝 409 `config_rejected` |
| `GET /raft/membership` | 无 | `{"voters":["node-1","node-3"],"learners":["node-2"],"index":7,"term":3,"leader_id":"node-1"}` | 无 |

`statusFor` 加一条 `ErrConfigRejected` → 409 `config_rejected`。四种拒绝原因共用一个 code，响应体的 `error` 字段写具体原因：目标不在地址表、角色没有变化、已有配置条目在飞、降级之后没有投票者。

`-peers` 仍是必填，语义扩成地址表：必须包含所有可能成为成员的节点。角色不在命令行给，由配置条目决定。

## 5. 数据格式

配置条目的 command：

```text
0x11                 1B 操作码
voters               2B 投票者数量，大端
voter                2B id 长度 + id
```

id 升序、去重、非空，每个 id 都在 `-peers` 里；任一不符按坏记录拒绝。条目带全量投票集合，不记增量：任意一条配置条目单独就能还原视图。

learner 由「不在 voters 里」推出，条目里不写角色字段。

RPC 形状不动：`LogEntry.Command` 仍是 `[]byte`，raft 层不解释它。只有追加、回放与 apply 三处按首字节分流：`0x01` 是 KV 操作，`0x11` 是配置条目，空字节串是选举 no-op。

快照文件升到 MRSNAP02：

```text
MRSNAP02             8B magic
entries              4B 键值条数，大端
voters               2B
voter                2B id 长度 + id
frame                len 4B | crc32c 4B | payload
payload              op 1B(=0x20) | keylen 4B | key | vallen 4B | value
```

`current.json` 的字段不变；`checksum` 覆盖整份文件，配置段一起校验。MRSNAP01 按坏记录拒绝，旧数据目录按 `3.1` §9 的结论整体丢弃，不迁移（D36）。

`raft/state` 保持四个标量。配置视图没有第二份落盘副本。

## 6. 目录与配置

目录与 `5.1` §6 相同，配置条目就是日志里的一条记录，不新增文件。

| 开关 | 默认 | 含义 |
|:---|:---|:---|
| `-learner-demote-ms` | `300000` | 成员被豁免出 `safeIndex` 之后连续这么久降级为 learner；`0` 关掉自动降级 |

`Config` 增加 `LearnerDemoteMS int64`，`Validate()` 判负数。计时起点沿用 `5.1` §7 的豁免判定：`matchIndex` 落后 `commitIndex` 超过 `-snapshot-exempt-entries` 条即进入豁免。

换算只在 `NewNode` 做一次：`demoteTicks = LearnerDemoteMS / TickMS`，向下取整、至少 1，与选举截止同一条口径（D16）。

## 7. 关键流程

变更（手动与自动共用）：

1. Leader 校验四件事：目标 id 在地址表里；目标角色与当前视图不同；`pendingConfig` 为空；降级之后投票集合非空。任一不满足返回 `ErrConfigRejected`。
2. 追加配置条目并 Sync。Sync 失败时视图不动、复制不排、返回 `ErrIO`。
3. 锁内换本地视图，记 `pendingConfig{old, new, index}`。生效点在这一步，不等提交。
4. 按成员 id 升序给地址表里的其余节点各排一次 `appendOnce`。learner 照常收到复制请求。
5. 回执推进 `matchIndex`。配置条目要旧集合与新集合各有多数派才推进 `commitIndex`；普通条目的提交屏障是它前面未提交的配置条目，不越过。
6. 配置条目提交后清掉 `pendingConfig`，打 `membership change committed`。
7. 新视图不含自己时，Leader 在排完复制之后转 Follower，term 不变，打 `role changed`，reason 写 `demoted to learner`。

接收与截断：

1. `handleAppendEntries` 通过一致性检查后逐条追加。遇到 `0x11` 的条目，当场换视图，不等提交。
2. 截断后缀时调用 `rebuildConfigLocked`：快照头里的集合起，按剩下的日志顺序重放配置条目，最后一条生效。被截掉的那条配置不再有效。
3. learner 收到复制请求的处理与 voter 相同，除计票之外没有分支。

选举与读：

- 候选人只给投票集合里的成员发 `RequestVote`；计票只算投票集合的回执；多数派取 `|voters|/2+1`。
- learner 的选举截止照常递减，到点不发选举。收到 `RequestVote` 时先按 term 规则处理，再以 `learner` 拒绝，reason 写进 `vote denied`。
- 确认轮（`4.1` §7）只给投票集合的成员计票，多数派同样按 voters 算。learner 的回执带轮次号也不计票。
- Leader 只可能是 voter：learner 不发起选举，也不被计票。

启动与快照：

1. 读指针与快照，视图初值取文件头里的 voters；没有可用快照时取 `-peers` 全表。
2. 回放日志，快照点之后的配置条目逐条覆盖视图，最后一条生效；`configIndex` 取最后一条的 index。
3. 生成快照时把当前视图写进文件头，快照点上的视图与文件头一致。
4. 接收快照时用文件头里的 voters 覆盖本地视图，配置条目的压缩点随之前移。

自动降级：

1. Leader 每次处理完回执看一次豁免条件（`5.1` §7）。进入豁免的成员记下当前 tick 序号。
2. 条件消失就清掉这一格的计时。
3. 连续 `demoteTicks` 个 tick 仍在豁免里，走变更路径，目标取该成员，角色取 learner，打 `learner auto demotion triggered`。
4. `pendingConfig` 非空时跳过这一次，下一拍再看。自动降级与手动变更不并发。
5. learner 追平之后不自动提升；提升由外部调用 `POST /raft/membership`。

## 8. 不变式

1. 配置条目一旦进入本地日志就生效，不等提交；视图只由「快照头里的集合 + 快照点之后的配置条目」决定。
2. 投票集合是地址表的子集，非空；Leader 必在投票集合里。
3. 视图生效之后，选举、确认轮与提交计数的多数派都按生效后的集合算。
4. 同一时刻只有一条配置条目在飞：`pendingConfig` 非空时拒绝新的变更，提交或降级之后清空。
5. 配置条目的提交要求旧集合与新集合各有多数派；`commitIndex` 不越过未提交的配置条目。
6. learner 不发起选举、不投票、不计入任何多数派；日志复制与 apply 照常。
7. 截断日志之后视图必须能由剩余日志重算：重算结果等于被截掉的那条配置生效之前的视图。
8. 快照文件头里的投票集合与快照点上的视图一致；恢复时的视图等于快照头加之后配置条目的最后一条。
9. `raft/state` 仍是四个标量，配置视图不落第二份。

## 9. 风险与约束

- 地址表静态：扩容要改所有节点的 `-peers` 并重启，重启期间该节点用全表当默认投票集合，直到收到第一条配置条目才收敛。启动早期存在两个视图不一致的窗口，单条变更的多数组交集保证这个窗口不出双 Leader。
- 配置条目追加之后崩溃、尚未提交：重启后视图仍按这条生效，与运行时一致；这条被新 Leader 截掉之后，视图回退到上一条。
- 自动降级会缩小投票集合。降到 2 个 voter 时，任意一台故障就停写；降到 1 个 voter 时没有容错。降级换掉的是「一个坏成员拖住提交」，代价写在这里。
- learner 落后太多时仍占复制带宽与快照传输。豁免与降级只解决 quorum，不解决追赶。
- 5 分钟是工程阈值；`-tick-ms` 调大时实际时长跟着变，误差与选举截止同一个量级。
- 快照格式改了，MRSNAP01 与 MRSNAP02 互不兼容；磁盘上留下旧快照的目录按「全部丢弃」处理。
- 没有 joint consensus：一次一条变更，第二个变更要等第一个提交，换来的是不需要同时维护两份完整配置与两轮日志。
- 变更接口可重试：第一次已提交时重试按「角色没有变化」拒绝，不产生第二条日志。

## 10. 日志字段

`component` 取 `raft`，新增事件与字段：

| 事件 | 字段 |
|:---|:---|
| `membership change proposed` | `target_id`、`new_role`、`index`、`term`、`voters` |
| `membership change committed` | `index`、`term`、`old_voters`、`new_voters` |
| `membership change rejected` | `target_id`、`new_role`、`reason` |
| `membership applied from wal` | `voters`、`config_index` |
| `learner auto demotion triggered` | `peer_id`、`lag_entries`、`exempt_ticks` |
| `leader stepped down` | `index`、`voters`、`reason`（取 `demoted to learner`） |
