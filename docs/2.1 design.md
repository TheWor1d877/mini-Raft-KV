# 2.1 单机 KV + WAL 设计

概述：`internal/kvstore` 装内存状态机与字节层。map 的一次改动只有 `Apply` 一个入口，落盘与恢复都在 `internal/raft` 的那份 WAL 上：客户端写先追加日志并 Sync，过半确认后 apply 进 map；进程重启时全量回放日志重建 map，扛得住 `kill -9`。进程载体 `cmd/miniraft-kv` 是成员表只有自己的单节点集群，写路径每条一次 Sync（`3.1` §7）。

基线是 `docs/2.  单机KV + WAL.md`，本文把它展开成可实现、可验收的规格。编号引用：决策 D1~D13 见 `2.3 decisions.md`，测试与任务 T1~T18 见 `2.2 test.md`。

## 1. 模块定位

职责：内存 `map[string]string` 状态机加字节层。`Apply` 改 map，`Get` 读 map，`record.go` 对外提供帧编解码（`EncodeFrame`／`DecodeFrame`／`CheckFrame`）和 KV entry 编解码（`EncodeEntry`／`DecodeEntry`），字节里放什么上层决定（D4）。数据目录的独占锁与 zap 日志的封装、脱敏也在这里定义。

边界：日志的追加、Sync、段滚动、坏尾裁剪与恢复扫描在 `internal/raft/wal.go`；`currentTerm`／`votedFor`／`commitIndex`／`lastApplied` 四个标量在 `internal/raft/state.go`。落盘对象只有一棵树：`data/node-N/raft/wal/` 的日志段加同级的 `state`。划分见 D12 与 `3.3` D15。

关系：`internal/raft` 复用本模块的帧原语，把 `op｜keylen｜key｜vallen｜value` 整条 entry 当作日志记录的 `command` 字段；重启路径只有日志回放一条（`3.1` §7）。

## 2. 架构概览

| 内部件 | 职责 | 依赖 |
|:---|:---|:---|
| kv | 内存 `map[string]string` + `RWMutex`，Apply/Get/Close | dir、config、errors |
| record | 字节层的 `len｜crc32c｜entry` 编解码与校验 | 标准库 `hash/crc32` |
| dir | 数据目录、文件命名、进程独占锁 | 标准库 `os`、`syscall` |
| log | zap 结构化日志的封装与通用字段 | 第三方 `go.uber.org/zap` |
| config | 默认值、上限、路径与命令行解析 | 标准库 `flag` |

数据流：

```text
客户端写  →  raft.Propose  →  wal.Append + Sync  →  过半确认  →  apply  →  kv.Apply 改 map
客户端读  →  kv.Get
启动      →  dir.Lock  →  wal 扫描建 entry 视图  →  回放 [1, lastApplied] 建 map  →  补 apply  →  服务
```

map 只在条目落盘且过半确认之后才动，这条顺序在写路径的每个分支都成立；启动与写的逐步流程见 §7。

## 3. 包结构与依赖方向

```text
cmd/miniraft-kv/      进程入口：单节点集群，成员表只有进程自己
cmd/miniraft-node/    进程入口：-peers 给成员表的集群节点
internal/nodeapp/     两个入口共用的起停链
internal/kvstore/     kv.go record.go dir.go config.go errors.go logging.go
internal/raft/        wal.go 落盘与恢复扫描，日志段的字节布局见 3.1 §5
```

- 允许：`cmd` → `internal/nodeapp` → `internal/raft` → `internal/kvstore`；`kvstore` 内各文件同包互引，无环。
- 禁止：`internal/kvstore` 反过来引用 `cmd` 或 `internal/raft`。
- 复用：`logging.go`、`errors.go`、`config.go` 在本模块首次定义，后续模块直接照这套。

## 4. 核心接口

```go
type KV struct{ /* 未导出字段：config、logger、目录锁、RWMutex + map */ }

func Open(cfg Config, lg *zap.Logger) (*KV, error)
func (k *KV) Apply(key, value string)
func (k *KV) Get(key string) (string, error)
func (k *KV) Close() error

func WithRequestID(ctx context.Context, id string) context.Context
```

`lg` 由调用方构造并持有文件句柄，`Open` 不接管它；`Close` 只释放目录锁，日志与游标的收尾归 raft 侧。`ctx` 只用来带 `req_id`。

契约（输入见上面的签名）：

| 方法 | 错误语义 | 并发与幂等 |
|:---|:---|:---|
| Open | 目录被占 `ErrLocked`；IO 失败 `ErrIO`；成功即独占数据目录 | 只允许调用一次；失败时不留半把锁，也不释放持有者的锁 |
| Apply | 不返回错误：一次赋值没有可失败的 IO | 重复 apply 同一条不改变结果（D4）；写序由 `mu` 决定 |
| Get | key 不存在返回 `ErrKeyNotFound`，属正常控制流 | 读不阻塞写，用 `RLock` |
| Close | `ErrIO` | 释放目录锁；重复调用是空操作 |

`Apply` 的调用方只有一个：`internal/raft` 的 apply 循环与启动回放。落盘失败、失效停写、状态码映射都在 raft 侧，见 `3.1` §4 与 D5。

HTTP 入口的状态码映射（D10）由 `raft.NewHandler` 承载：`ErrKeyNotFound`→404，`ErrTooLarge`→413，`ErrCorruptRecord`→500 且带 `offset`，`ErrIO` 与写路径失效→500，`ErrLocked` 只在启动阶段出现、映射成进程启动失败。

请求与响应形状：`POST /put` 收 `{"key","value"}`，回 `{"ok":true,"req_id","index","term"}`；`GET /get?key=` 回 `{"key","value","req_id"}`；出错统一回 `{"error","code","req_id","offset"}`，`code` 是机器可读的类别名（`key_not_found`、`too_large`、`io_error`、`corrupt_record`、`bad_request`、`method_not_allowed`、`not_found`）。value 走请求体，不进 URL。请求体在 `net/http` 的读取阶段就按 entry 上限 4MB 拦掉，超限不到写路径；被拦下的那一条，服务端读走的字节最多是上限再多一个字节。非法 JSON、一个请求体里塞多个对象都是 400，不改动已有状态。`/put` 与 `/get` 的 Leader 判定与读档位见 `3.1` §4 与 `4.1`。

进程退出码：`0` 收到 SIGINT/SIGTERM 后正常收尾；`1` 打不开数据目录、写路径失效、或服务或收尾出错；`2` 配置非法或日志起不来。SIGTERM 走 `Shutdown` → `Node.Close` → `KV.Close`，数据的落盘边界已经在日志上，收尾不再刷写。起不来的错误除写日志外再往 stderr 打一条：数据目录坏到日志也写不出去时，stderr 是唯一能看到退出原因的地方。这两条由 `internal/nodeapp.Run` 实现，两个入口共用。

收尾窗口只用在途请求上，不等「连上了但一个请求头都没发」的连接：入口用 `ConnState` 记下这类连接，收到信号后先关掉它们再 `Shutdown`。`net/http` 把这种连接当忙处理，要等它自己满 5 秒才当空闲（Go 的 Issue 22682），而读请求头的超时也是 5 秒。主动关省掉这 5 秒，窗口不必比它更长。不主动关，`Shutdown` 会把整个窗口耗在一条没人说话的连接上、返回 `context deadline exceeded`，进程按收尾出错退 1，而数据一条没丢。已受理、正在写的请求不受关闭流程影响，仍在窗口内等它完成；空闲的 keep-alive 连接 `Shutdown` 自己会关。

不暴露 `Delete`：`docs/1` 的负载里没有它，加进来会让记录格式多一个 op 分支。空串 key、空串 value 都是合法输入，「不存在」与「值为空串」用长度前缀区分（`2.3` D4）。

## 5. 数据格式

日志里每条记录分两层：外层是帧，固定 8 字节头；帧里先是 `op｜term｜index`，再装本模块的 KV entry 当 `command`，对日志而言 `command` 是不透明字节。`command` 的编码就是下面这套 entry，`op+term+index` 那一段的布局见 `3.1` §5。

```text
一条记录 = 帧头（8B） + 日志自己的头（op 1B｜term 8B｜index 8B） + command（len 字节）

帧头  ┌──────────┬──────────────┐
      │ len  4B  │ crc32c  4B   │
      └──────────┴──────────────┘
command ┌────────┬──────────┬─────────┬──────────┬─────────┐
        │ op 1B  │ keylen 4B│ key N B │ vallen 4B│ value M │
        └────────┴──────────┴─────────┴──────────┴─────────┘
        其中 N = keylen，M = vallen，len = 1 + 4 + N + 4 + M
```

| 字段 | 宽度 | 类型 | 含义 | 约束 |
|:---|:---|:---|:---|:---|
| `len` | 4B | uint32 大端 | 帧内字节的总数，不含帧头 | 上限 4MB；超限判坏记录 |
| `crc32c` | 4B | uint32 大端 | CRC-32C（Castagnoli） | 覆盖 `len` 与帧内全部字节，即 4 + len 个字节 |
| `op` | 1B | uint8 | command 的操作码 | 当前只有 `0x01 = Put`，其余值判坏记录 |
| `keylen` | 4B | uint32 大端 | key 字节数 | 上限 1KB |
| `key` | keylen | 原始字节 | 键，不校验是否为合法 UTF-8 | 允许空串（keylen=0） |
| `vallen` | 4B | uint32 大端 | value 字节数 | 上限 1MB |
| `value` | vallen | 原始字节 | 值 | 允许空串（vallen=0） |

算例：`Put("k1", "hello")` → command = 1 + 4 + 2 + 4 + 5 = 16B → 帧内字节 = 1 + 8 + 8 + 16 = 33B → 记录总长 8 + 33 = 41B，crc 覆盖 4 + 33 = 37 个字节。

- 多字节整数一律大端，无对齐填充，字段按表里的顺序紧排。
- 长度校验在追加之前做：`keylen` 超 1KB 或 `vallen` 超 1MB 返回 `ErrTooLarge`，不产生任何落盘字节；`len` 的 4MB 上限大于业务上限，是给这条判断留位置：盘里不许出现一条永远读不出来的记录。
- `op` 占 1 字节留的是扩展位：以后加 Delete 或快照标记都不改帧格式（D4）。
- 帧头不含 magic、不含版本号，文件只从约定目录读，损坏靠 crc 判（D7）。
- 字节层的入口只有 `record.go` 五个函数：`EncodeEntry`/`DecodeEntry` 管 entry（含 `op` 与内部长度校验），`EncodeFrame`/`DecodeFrame`/`CheckFrame` 管帧头；`internal/raft` 的 WAL 只搬运 `EncodeFrame` 产出的字节，不解释 command。

坏记录与坏尾的五种判定（剩余字节不足 8、`len` 超 4MB、读不满、crc 不等、日志 `op` 不是 `0x10`）由 `internal/raft/wal.go` 的扫描执行，命中即停止扫描并裁剪到坏尾起点，处置与截断落点见 `3.1` §5。command 里的 `op` 在扫描时不校验，解不出来的时候由回放与 apply 在启动期报错（`op` 非 `0x01`、长度对不上都算解不出）。

## 6. 目录与文件

```text
data/
  LOCK                    flock(fd, LOCK_EX|LOCK_NB)，启动时先拿
  log/miniraft-node.log   进程日志，字段口径见 §8
  raft/
    state                 四个标量的原子重写小文件（3.1 §5）
    wal/
      00000001.wal        八位零填充递增序号
      00000002.wal
```

- 一段日志到 `-max-file-size`（默认 100MB）滚动；新段先以 `*.wal.tmp` 名创建、随即 rename 成正式名（D13，序列见 §7）。
- 恢复扫描按序号排序读全部 `.wal` 文件；活跃文件是当前序号最大的那个。`*.wal.tmp` 是没来得及提交的空文件，扫描之前先删掉。
- 不做 `CURRENT` 指针，不删老文件：删旧文件属于日志压缩，快照与压缩的实现见 `docs/5`。
- 路径默认相对当前工作目录的 `data/`，命令行与配置可覆盖（D8）。本模块的开关为 `-data-dir`、`-addr`、`-max-file-size`、`-log-level`，默认值只从 `config.go` 出，非法值直接报错、不回落默认；raft 侧的选举、心跳、读档位开关见 `3.1` §6 与 `4.1` §6。段上限由 `internal/raft/config.go` 取同一个 `kvstore.DefaultMaxFileSize`，命令行只有一根 `-max-file-size`。HTTP 默认监听 `127.0.0.1:8742`，对拍与崩溃注入靠它把多个进程分在同一台机器上。
- 写路径的 Sync 只有日志那一次，开关是 `-raft-fsync`（`3.1` §6）。`-raft-fsync=false` 只跳过日志追加后的 `Sync()` 系统调用，追加照常，给吞吐对照留「完全不 Sync」这一档；默认 `true`。

## 7. 关键流程

启动：拿目录锁 → 建目录 → 读 `raft/state` → 扫 `raft/wal/` 重建 entry 视图并校验游标 → 按 `[1, lastApplied]` 回放 command 建 map → 打开最大序号文件末尾准备追加 → 补 apply `(lastApplied, commitIndex]` → 起服务。恢复阶段一条记录都不逐条打日志，只在坏尾处打一条带 `offset` 的告警；回放完成后打一条 `state rebuilt from wal`，带 `replayed_entries` 与 `last_applied`。空 command 的 no-op 条目不进 `replayed_entries`。

写：`raft.Propose` 编 command → 追加日志并 Sync → 等过半 → apply 循环按 index 升序解出 key/value → `kv.Apply` 改 map → 每满 64 条把 `lastApplied` 写回 `state` → 回调兑现，`/put` 才回 200。客户端等的是「过半确认且已 apply」，不是「写进 page cache」。

日志追加失败：条目不进 map，原样返回 `ErrIO` 并带 `syscall.Errno`。

Sync 失败：盘上边界未知，处理是就地停写（fail-stop）：日志置失效标志，`Propose` 之后一律返回 `ErrIO`，`Get` 仍可服务，进程由入口层退出；重启走正常恢复流程，坏尾会被截掉（D5）。

失效只由 Sync 失败触发：滚动时建新段失败，此前的条目已经落盘、边界已知，`Propose` 返回 `ErrIO` 但不置失效标志，故障排除后写路径继续。是否置失效标志，只看一条判据：盘上有什么是否已知。

滚动：追加前判断当前文件大小 + 本条长度是否越过段上限，越过则 `Sync()` 当前文件 → 以 `*.wal.tmp` 名建新段 → 立刻 rename → 换 fd → 段内偏移归零，之后的写入全程落在正式名上（D13）。滚动期间 map 不加新锁，走的是 `Node` 那把锁。

## 8. 日志与可观测性

用 `go.uber.org/zap`，字段名小写下划线。两个进程入口都写 `data/log/miniraft-node.log`，追加打开、进程退出时关闭，一个进程一份；打开它的是 `raft.NewNodeLogger`，`kvstore.NewLogger` 保留同一套编码与 UTC `ts` 口径（`3.1` §6 末段）。通用字段 `ts`、`level`、`msg`、`component`（取值 `wal`／`kv`／`entry`，raft 侧再加 `raft`），另有 `caller`。

必须打日志的位置：

| 位置 | level | 字段 |
|:---|:---|:---|
| Open 成功/失败 | info / error | data_dir, duration_ms；失败那条带 error |
| 拿到/拿不到目录锁 | info / error | lock_path |
| 恢复遇到坏尾 | warn | file, offset, expect_len, got_len, reason（`3.1` §10） |
| 日志回放完成 | info | node_id, replayed_entries, last_applied |
| 日志滚动 | info | from_file, to_file, size_bytes |
| 日志写路径失效 | error | failed_at_offset, error |
| 一次状态机改动 | debug | key, value_len, value_fp |
| state 游标落盘 | debug | current_term, voted_for, commit_index, last_applied, sync_ms |
| HTTP 请求成功 | debug | req_id, route, status, duration_ms |
| HTTP 返回 4xx/5xx | warn | req_id, route, status, code, duration_ms |
| HTTP 触发的失效退出（D5） | error | req_id |
| 入口起停 | info | 启动那条带 process, node_id, addr, data_dir, members；停止那条带 node_id, write_disabled, exit_code |

排查路径：HTTP 入口为每个请求生成 `req_id` 并透传进状态机调用，出问题先按 `req_id` 与日志 `index` 串起「追加失败 → Sync 失败 → 失效」这条链，再拿 `offset` 去 `xxd` 对应日志段。

脱敏：`value` 不进日志，只记 `value_len` 和指纹前 8 位（crc32c 结果）；`key` 只记前 16 字节。日志不做采样，级别本身控量。

## 9. 风险与约束

- 写路径每条一次 Sync（D19）。掉电丢多少取决于「Sync 之后到掉电之间有没有再来一条已确认写」，Leader 侧每条落完才回 200，所以已确认的写不进丢写窗口；`-raft-fsync=false` 那一档例外，实测读数见 `docs/0` 的崩溃注入表。
- 全量 map 常驻内存，没有容量上限；本期假设数据集能装进内存，压不进去属于压缩模块要解决的事（D9）。
- 日志只增不减，重启时间随段总量线性增长：`boot_ms` 现在量的就是全量回放的耗时，快照与压缩是它的解，见 `docs/5` 与 `3.1` §9。
- CRC-32C 只检测意外损坏，挡不住故意构造的碰撞。
- `rename` 的原子性依赖 POSIX 语义，跨文件系统或某些网络挂载不成立，测试只在本地盘跑。
