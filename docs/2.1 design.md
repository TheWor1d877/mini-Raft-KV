# 2.1 单机 KV + WAL 设计

基线是 `docs/2.  单机KV + WAL.md`，本文把它展开成可实现、可验收的规格。编号引用：决策 D1~D13 见 `2.3 decisions.md`，测试见 `2.2 test.md`，里程碑 M0~M8 与任务 T1~T18 见 `2.4 plan.md`（临时文档，里程碑验收完删除）。

## 1. 模块定位

职责：在单进程里把 Put/Get 落到内存状态机，写路径先追加 WAL 再改内存，重启时扫 WAL 重建状态，能扛住 `kill -9`。

不负责：RPC、选举、日志复制、快照。`currentTerm`、`votedFor`、`log[]` 的持久化归 `docs/3.  投票选举.md` 那条线，本模块只对外提供「追加一段字节、按顺序读回字节」的 WAL 原语，上层往字节里放什么本模块不管（D4）。划分见 D12：`log[]` 复用本模块的 WAL，`currentTerm` 和 `votedFor` 走原子重写的小文件。

关系：它是后面 Raft 的存储底座。判断本模块做对了没有，标准是 Raft 模块接手时不用改 WAL 的记录格式和恢复语义。

## 2. 架构概览

| 内部件 | 职责 | 依赖 |
|:---|:---|:---|
| kv | 内存 `map[string]string` + `RWMutex`，Put/Get/Flush/Close | wal、config、errors |
| wal | 记录编码、追加、按批次 fsync、文件滚动 | dir、record、config |
| record | 字节层的 `len｜crc32c｜entry` 编解码与校验 | 标准库 `hash/crc32` |
| recovery | 按序号扫 WAL 文件、逐条校验、截坏尾、产出重建后的状态 | record、wal |
| dir | 数据目录、文件命名、进程独占锁 | 标准库 `os`、`syscall` |
| log | zap 结构化日志的封装与通用字段 | 第三方 `go.uber.org/zap` |

数据流：

```text
Put  →  record.Encode  →  wal.Append  →  (攒够 64 条) file.Sync  →  kv.map 更新
Get  →  kv.map 读取
启动  →  dir.Lock  →  dir.Open  →  recovery.Scan  →  wal 追加入口  →  服务
```

写路径的顺序（追加成功、该批次落盘成功之后才改 map）是硬约束，任何分支都不许反过来。

## 3. 包结构与依赖方向

```text
cmd/miniraft-kv/        进程入口：加载配置、打开 Store、起 HTTP、优雅关闭
internal/kvstore/       kv.go record.go wal.go recovery.go dir.go config.go errors.go logging.go http.go
```

- 允许：`cmd` → `internal/kvstore`；`kvstore` 内各文件互相引用同一包，无环。
- 禁止：`internal/kvstore` 反过来引用 `cmd`；本包引用后续的共识/RPC 包。
- 复用：日志封装、错误码、配置加载在本模块首次定义，后续模块直接照这套（M1 的交付物之一就是可被复用的 `logging.go`、`errors.go`、`config.go`）。

## 4. 核心接口

```go
type KV struct{ /* 未导出字段：config、logger、目录锁、wal、RWMutex + map */ }

func Open(cfg Config, lg *zap.Logger) (*KV, error)
func (k *KV) Put(ctx context.Context, key, value string) error
func (k *KV) Get(key string) (string, error)
func (k *KV) Flush() error
func (k *KV) Close() error
func (k *KV) WriteDisabled() bool

func WithRequestID(ctx context.Context, id string) context.Context
```

`lg` 由调用方构造并持有文件句柄，`Open` 不接管它；`Close` 只关 WAL 与目录锁，日志文件由入口层关。`ctx` 只用来带 `req_id`，本库不设超时。

契约：

| 方法 | 输入输出 | 错误语义 | 并发与幂等 |
|:---|:---|:---|:---|
| Open | 目录、批次大小、是否同步、logger | 目录被占 `ErrLocked`；IO 失败 `ErrIO`；坏记录不上报，截断处理 | 只允许调用一次，成功即独占数据目录；失败时不留半把锁，也不释放持有者的锁 |
| Put | ctx、key/value 字符串 | 超限返回 `ErrTooLarge`，不产生落盘字节；未落盘一律返回错误且不生效；`ErrIO` 后进入失效状态（D5） | 同 key 同 value 重放无副作用，客户端重试安全；写序由内部锁决定，与 WAL 追加序一致 |
| Get | key | key 不存在返回 `ErrKeyNotFound`，属正常控制流 | 读不阻塞写，用 `RLock`；失效状态下照常服务 |
| Flush | 无 | `ErrIO`；已失效返回 `ErrIO` | 把当前不满一批的记录强制落盘 |
| Close | 无 | `ErrIO` | 先 Flush 再释放 fd 和目录锁；重复调用是空操作，不产生第二次 fsync 失败 |
| WriteDisabled | 无 | 不返回错误 | 读失效标志，入口层据此把进程退掉（D5） |

HTTP 入口的状态码映射（D10）：`ErrKeyNotFound`→404，`ErrTooLarge`→413，`ErrCorruptRecord`→500 且带 `offset`，`ErrIO` 与失效状态→500，`ErrLocked` 只在启动阶段出现、映射成进程启动失败。

请求与响应形状：`POST /put` 收 `{"key","value"}`，回 `{"ok":true,"req_id"}`；`GET /get?key=` 回 `{"key","value","req_id"}`；出错统一回 `{"error","code","req_id","offset"}`，`code` 是机器可读的类别名（`key_not_found`、`too_large`、`io_error`、`corrupt_record`、`bad_request`、`method_not_allowed`、`not_found`）。value 走请求体，不进 URL。请求体在 `net/http` 的读取阶段就按 entry 上限 4MB 拦掉，超限不到写路径。非法 JSON、一个请求体里塞多个对象都是 400，不改动已有状态。

进程退出码：`0` 收到 SIGINT/SIGTERM 后正常收尾；`1` 打不开数据目录、写路径失效、或服务或收尾出错；`2` 配置非法或日志起不来。SIGTERM 走 `Shutdown` → `Close`，未满的一批落盘后再退出。起不来的错误除写日志外再往 stderr 打一条：数据目录坏到日志也写不出去时，stderr 是唯一能看到退出原因的地方。

不暴露 `Delete`：`docs/1` 的负载里没有它，加进来会让记录格式多一个 op 分支。
key 为空串、value 为空串都是合法输入；「不存在」与「值为空串」用长度前缀区分（`2.3` D4）。`Get` 找不到键时返回空串加 `ErrKeyNotFound`，HTTP 入口把它映射成 404。

超时与重试由调用方负责，本库不内置重试；本地盘 IO 不设超时。

## 5. 数据格式

落盘的每条记录分两层：外层是帧，固定 8 字节头；帧里装的 entry 是本模块的 KV 操作编码，对 wal 而言是不透明字节。

```text
一条记录 = 帧头（8B） + entry（len 字节）

帧头  ┌──────────┬──────────────┐
      │ len  4B  │ crc32c  4B   │
      └──────────┴──────────────┘
entry ┌────────┬──────────┬─────────┬──────────┬─────────┐
      │ op 1B  │ keylen 4B│ key N B │ vallen 4B│ value M │
      └────────┴──────────┴─────────┴──────────┴─────────┘
      其中 N = keylen，M = vallen，len = 1 + 4 + N + 4 + M
```

| 字段 | 宽度 | 类型 | 含义 | 约束 |
|:---|:---|:---|:---|:---|
| `len` | 4B | uint32 大端 | entry 的字节数，不含帧头 | 上限 4MB；超限判坏记录 |
| `crc32c` | 4B | uint32 大端 | CRC-32C（Castagnoli） | 覆盖 `len` 与 `entry` 全部字节，即 4 + len 个字节 |
| `op` | 1B | uint8 | 操作码 | 当前只有 `0x01 = Put`，其余值判坏记录 |
| `keylen` | 4B | uint32 大端 | key 字节数 | 上限 1KB |
| `key` | keylen | 原始字节 | 键，不校验是否为合法 UTF-8 | 允许空串（keylen=0） |
| `vallen` | 4B | uint32 大端 | value 字节数 | 上限 1MB |
| `value` | vallen | 原始字节 | 值 | 允许空串（vallen=0） |

算例：`Put("k1", "hello")` → entry = 1 + 4 + 2 + 4 + 5 = 16B → `len` = 16 → 记录总长 24B，crc 覆盖 4 + 16 = 20 个字节。

- 所有多字节整数一律大端，无对齐填充，字段按表里的顺序紧排。
- 长度校验在追加之前做：`keylen` 超 1KB 或 `vallen` 超 1MB，`Put` 返回 `ErrTooLarge`，不产生任何落盘字节。`len` 上限 4MB 大于业务上限，是给这条判断留位置——盘里不许出现一条永远读不出来的记录。
- `op` 占 1 字节留的是扩展位：以后加 Delete 或快照标记都不改帧格式（D4）。
- 帧头不含 magic、不含版本号，文件只从约定目录读，损坏靠 crc 判（D7）。
- 字节层的入口只有 `record.go` 五个函数：`EncodeEntry`/`DecodeEntry` 管 entry（含 `op` 与内部长度校验），`EncodeFrame`/`DecodeFrame`/`CheckFrame` 管帧头；`wal` 只搬运 `EncodeFrame` 产出的字节，不解释 entry。

恢复时的判定顺序：剩余字节不足 8 → 坏尾；`len` 超过 4MB → 坏尾；按 `len` 读不出完整 entry → 坏尾；crc 与重算值不等 → 坏尾；`op` 不是 `0x01` → 坏记录。遇坏尾立即停止扫描并裁剪到坏尾起点。

## 6. 目录与文件

```text
data/
  LOCK              flock(fd, LOCK_EX|LOCK_NB)，启动时先拿
  wal/
    00000001.wal    八位零填充递增序号
    00000002.wal
```

- 单个 WAL 到 100MB 滚动；新段以 `*.tmp` 名创建后立刻 rename 成正式名，之后的写入全程落在正式名上（D13）。
- 恢复扫描按序号排序读全部文件；活跃文件是当前序号最大的那个。`*.tmp` 是没来得及提交的空文件，扫描之前先删掉。
- 不做 `CURRENT` 指针，不删老文件：删旧文件属于日志压缩，本期不做（D7）。
- 路径默认相对当前工作目录的 `data/`，命令行与配置可覆盖（D8）。命令行开关为 `-data-dir`、`-addr`、`-batch-size`、`-max-file-size`、`-fsync`、`-log-level`，默认值只从 `config.go` 出；非法值直接报错，不回落默认。HTTP 监听地址默认 `127.0.0.1:8742`，对拍与崩溃注入靠它把多个进程分在同一台机器上。
- `-fsync=false` 只跳过 `Sync()` 系统调用，批次计数与 `Flush()` 照常，给 T14 留「完全不 Sync」这一档对照；默认 `true`。

## 7. 关键流程

启动：拿目录锁 → 建目录 → 扫 `wal/` → 逐文件逐条校验、截坏尾、重建 map → 打开最大序号文件末尾准备追加 → 起服务。恢复阶段一条记录都不逐条打日志，只在坏尾处打一条带 `offset` 的告警。

Put：编码 entry → 追加写文件 → 批次计数 +1 → 满 64 则 `Sync()` → 更新 map → 返回。批次未满时返回成功，此时数据只在 page cache：进程被杀不丢，页缓存归内核持有，新进程读同一份文件仍能看到全部已确认字节；兑现这个窗口要靠掉电，丢的是最近未满一批的那 ≤63 条（D6）。

写失败：追加返回错误，不更新 map，不改批次计数，原样返回 `ErrIO` 并带 `syscall.Errno`。

fsync 失败：这条路径上已经攒了未确认落盘的记录，无法判断盘上有什么。处理是 fail-stop——置失效标志，`Put` 之后一律返回 `ErrIO`，`Get` 仍可服务，进程由入口层退出。重启后按恢复流程走，坏尾会被截掉（D5）。

失效只由 Sync 失败触发：滚动时建新段失败，此前那批已经落盘、边界是已知的，`Put` 返回 `ErrIO` 但不置失效标志，故障排除后写路径继续。判据是「盘上有什么是否已知」，不是「写有没有报错」。

滚动：追加前判断当前文件大小 + 本条长度是否越过 100MB，越过则 `Sync()` 当前文件 → 以 `*.tmp` 名建新段 → 立刻 rename → 换 fd → 段内偏移与批次计数归零，写序继续。滚动期间 map 不加新锁，仍走 Put 那把写锁。

## 8. 日志与可观测性

用 `go.uber.org/zap`，输出到 `data/log/miniraft-kv.log`（追加打开，进程退出时关闭），字段名小写下划线。通用字段 `ts`、`level`、`msg`、`component`（取值 `wal`／`kv`／`recovery`／`entry`），另有 `caller`。`ts` 固定 UTC RFC3339。

必须打日志的位置：

| 位置 | level | 字段 |
|:---|:---|:---|
| Open 成功/失败 | info / error | data_dir, file_count, recovered_entries, duration_ms |
| 拿到/拿不到目录锁 | info / error | lock_path |
| 恢复遇到坏尾 | warn | file, offset, expect_len, got_len |
| 单次 fsync 完成 | debug | batch_count, fsync, duration_ms |
| 文件滚动 | info | from_file, to_file, size_bytes |
| Put 追加失败 | error | req_id, op_seq, errno, duration_ms |
| Put 被拒（追加返回错误） | error | req_id, errno |
| Put 生效 | debug | req_id, op_seq, key, value_len, value_fp |
| 进入失效状态（D5） | error | failed_at_seq, errno |
| Close | info | pending_batch, duration_ms |
| HTTP 请求成功 | debug | req_id, route, status, duration_ms |
| HTTP 返回 4xx/5xx | warn | req_id, route, status, code, duration_ms |
| HTTP 触发的失效退出（D5） | error | req_id |
| 入口起停 | info | addr, data_dir, write_disabled, exit_code |

排查路径约定：出问题先按 `op_seq` 串起「追加失败 → fsync 失败 → 失效」这条链，再拿 `offset` 去 `xxd` 对应 WAL 文件。

`trace_id`／`request_id`：HTTP 入口为每个请求生成 `req_id` 并透传进 kv 调用，日志里以 `req_id` 出现。库内部自增的 `op_seq` 是写序的唯一依据，两个字段都进日志。

脱敏：`value` 不进日志，只记 `value_len` 和指纹前 8 位（crc32c 结果）。`key` 只记前 16 字节。日志不做采样，级别本身控量。

## 9. 风险与约束

- 批量 fsync 换来写吞吐，代价是掉电时最多丢 63 条已确认的写，进程被杀不丢；这个窗口必须写进对拍结论，不能只报吞吐。
- 全量 map 常驻内存，没有容量上限；本期假设数据集能装进内存，压不进去属于压缩模块要解决的事（D9）。
- WAL 只增不减，重启时间随文件总量线性增长；这是「不做压缩」的直接后果，T18 的长跑记录条数与重启耗时两个点要能画出来。
- CRC-32C 只检测意外损坏，挡不住故意构造的碰撞。
- `rename` 的原子性依赖 POSIX 语义，跨文件系统或某些网络挂载不成立，测试只在本地盘跑。
