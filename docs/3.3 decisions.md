# 3.3 Raft 核心逻辑决策记录

编号接 `2.3` 的 D13 往后排；`2.3` 的 D12 由 D14 改写。

## D14 共识层的四个标量装进同一个原子重写小文件

- 背景：`currentTerm`、`votedFor`、`commitIndex`、`lastApplied` 都是几十字节就能写完的标量，重启时都要直接读到最新值。D12 定的是 term 与 votedFor 各一个文件。
- 备选：两个文件（D12 原口径）；一个文件装四样；全都进 raft 日志靠重放取最新值。
- 结论：一个 `raft/state` 文件，JSON 一行，`state.tmp` + `fsync` + `rename` 整体重写。
- 理由：分两个文件写会出现「term 新、票旧」的中间态，一次崩溃正好落在那个态上，重启后节点带着新 term 却留着旧投票记录，不变式 1 靠运行时判定挡不住。四样东西的更新都是同批语义，一个 rename 就是一次提交。进 raft 日志则违反 D12 的划分：投出这一票之前要知道当前值，靠重放取最新值要多花时间，重写还会破坏 raft 日志只增的约定。
- 影响：`2.3` D12 与本条共同定下持久化清单——四个标量一个文件，`log[]` 一份追加式日志；`2.1` §1 的划分句按这个口径写。commitIndex 与 lastApplied 也进这个文件，raft 日志截断之后两个游标可能要比日志短，写文件的时机由不变式 4 定（`3.1` §7 应用一节）。
- 验证：M9 的用例断言四种字段组合写读一致、崩溃留下的 `state.tmp` 被忽略、半截 state 不会被读成 0 值；不变式 1 那格（投过票之后重启，同 term 再请求投票必须拒）就是这条的直接证据。

## D15 raft 日志独立成文件树，复用 kvstore 的帧原语

- 背景：`log[]` 要落盘。KV 的 `wal/` 已经有一套帧、滚动、目录锁和恢复扫描；D12 写明「`log[]` 复用本模块的 WAL」。
- 备选：两种记录混进 `wal/` 同一条流（`op=0x02`）；raft 日志单独一套文件但自己重写帧编解码；raft 日志单独一套文件并复用 `kvstore` 导出的 `EncodeFrame`／`DecodeFrame`／`CheckFrame`；接一个嵌入式 KV 存日志。
- 结论：raft 日志落在 `data/node-N/raft/log/NNNNNNNN.rlog`，帧头与 crc 口径复用 kvstore 导出的 `EncodeFrame`／`DecodeFrame`／`CheckFrame`／`FrameHeaderSize`／`MaxEntrySize`；100MB 滚动与 `*.tmp` 创建即改名在 `internal/raft` 内按同款手法另实现一份——kvstore 的列段与建段符号未导出，导出面不动；entry 内部字节布局换成 `3.1` §5 那种。
- 理由：两种记录混一条流的代价落在 doc 2 已交付的模块上。`2.1` §5 的五种坏记录判定要按 op 分叉，坏尾裁剪一次砍掉两种记录，KV 重放与 raft 重放要在同一个扫描里分开走，`kvstore.KV.Open` 的返回值形状也得跟着变。两个生命周期也不同：KV WAL 只增不减，raft 日志要按 index 截断尾部并重写，截错了就是砍掉状态机的提交点。复用帧函数、不复用文件，才能同时保住一套 crc 口径和两条独立的恢复路径。
- 影响：依赖方向是 `internal/raft` → `internal/kvstore`（`2.1` §3 的禁止项只挡反方向）；两套扫描代码各读一个目录，`*.tmp` 的清理规则同款。数据目录变成每节点一份，`data/node-1/` 到 `data/node-5/`，各持一把自己的 LOCK。
- 验证：M9 的五种坏记录用例（`3.2` 的 `raftlog_test.go`）；截断用例断言 `os.Truncate` 落在帧起点、截断后重启不重复截；index 出现空洞时 `NewNode` 返回 `ErrStateMismatch`。

## D16 Node 不读墙上时间，tick 由入口层驱动，传输层是接口

- 背景：选举超时 500ms 起、随机化、心跳 100ms，测试要判定这些行为。
- 备选：`Node` 内部起 goroutine 读 `time.Now()`；测试用真 HTTP 打真端口再 `sleep` 等选举；`Tick()` 由外层定时器驱动、传输层收成一个接口。
- 结论：`Node` 只暴露 `Tick()`，内部维护 `electionDeadline` 的剩余 tick 计数；传输层是 `Transport` 接口，单测用内存实现。
- 理由：读墙上时间的状态机没法确定性地测，随机超时会让用例时快时慢，靠 `sleep` 等选举结果的测试在 CI 上时好时坏，也测不出「投票计数到了 3 票但角色还没变」这种中间态。按 tick 次数推进之后，用例写的是「调 11 次 `Tick()`，第 11 次发起选举」，断言落在状态转移本身。
- 影响：`3.2` 里除 M12 的 5 进程用例之外全部零 `sleep`；随机区间断言只看值落在 `[500,1000)` ms，不看真实等待；入口层的 ticker 周期 `-tick-ms` 默认 50ms，选举截止的分辨率带 ±50ms 的误差，这条误差要在 M13 的重选主耗时里写明是误差来源之一。
- 验证：`election_test.go` 的超时边界用例；`cluster_test.go` 的多数派当选、分区、term 膨胀用例；M12 与 M13 用真进程真时间把这条路径的墙上时间部分单独量一次。

## D17 一进程一节点，脚本起 5 个进程

- 背景：5 节点拓扑在一台机器上怎么摆。
- 备选：一个进程里跑 5 个 `Node` 实例；5 个进程（与 D11 的 etcd 侧对称）；容器。
- 结论：`cmd/miniraft-node` 一进程一节点，`scripts/cluster_up.sh` 用 5 个 `-node-id` 起 5 个进程，各自独立 `-data-dir`。
- 理由：`docs/0` 的硬性约束要求坑来自真实运行。进程内 5 节点用不上真 HTTP、真目录锁、真进程边界，`kill -9` 只能模拟成「不调用」，测出来的重选主耗时不代表真实进程；D16 把状态机做成确定性的之后，逻辑正确性交给单测，剩下的观测必须走真进程。容器方案随 D11 的口径一起否决。
- 影响：一台机器 5 个 mini-Raft 进程 + 5 个 etcd 进程（D11），各占一个端口、一份数据目录、一份日志；`-peers` 的成员集合要 5 处配置完全一致，脚本里由同一份清单生成。
- 验证：M12 的放行判据就是 5 个真进程跑通一次写；M13 在这套拓扑上量重选主耗时。

## D18 客户端写复用 `/put`，非 Leader 回 503 带 leader 提示

- 背景：写要经 Leader 走 raft，`2.1` 的 `/put` 是本地直接生效。
- 备选：`/put` 改语义走 raft；新增 `/raft/propose` 给 raft 路径、`/put` 留作单机本地写；非 Leader 上静默转发给 Leader。
- 结论：`/put` 就是 raft 入口，非 Leader 返回 503，响应体带 `leader_id` 与 `leader_addr`；转发由客户端做。
- 理由：`docs/1` 的负载清单写的就是 Put/Get，doc 7 对拍要拿同一串操作打 etcd，etcd 在非 Leader 上的写返回 `not leader` 并带 leader 提示，两侧行为对得上才有对照可写。新增路径等于对拍时在 etcd 侧也要造一个等价入口。服务端静默转发会把「客户端重试」那格负载观测成服务端重试，故障注入时看不出是哪一个在重试。
- 影响：`/put` 从「追加 WAL、改 map、立即返回」变成「追加 raft 日志、复制到多数派、apply 后返回」，响应体新增 `index` 与 `term`；`2.1` §7 的单机 Put 流程留在 `cmd/miniraft-kv` 那个二进制里（D21）。503 的 `code` 取名 `not_leader`，与 `2.1` §4 已有的错误码并列。
- 验证：`http_rpc_test.go` 断言 Follower 上的 `/put` 是 503 且两个提示字段非空、Leader 上是 200 且 `index` 单调；M12 放行判据里其余 4 个节点的 `/get` 要读到同一个值。

## D19 raft 日志每条 Sync，`-raft-fsync=false` 留作对照档

- 背景：D6 给 KV 的写路径定了 64 条一批。raft 日志的落盘节奏要不要同样批量。
- 备选：每条 Sync；攒一批；按时间；跟 KV 共用批次。
- 结论：默认每条 Sync；`-raft-fsync=false` 只跳过那一个 `Sync()` 系统调用，批次计数与文件追加照常。
- 理由：条目没落盘就发给其他节点，掉电之后本节点少一条、多数派多一条，恢复时这条被更高 term 覆盖，客户端已经拿到 200 的写就此消失，`docs/0` 对「已确认的写」的要求就不成立。对照 D6：那边的窗口是 63 条，代价换的是吞吐；raft 日志这边一旦批量，复制回执就可能对应盘上不存在的条目。开关只服务 M13 与 doc 7 的吞吐对照，省下的是一条系统调用，不新增写入路径。
- 影响：一次客户端写发 1 次 raft 日志 Sync，外加均摊 1/64 次 KV WAL Sync 和按批次的 state 文件重写；这个数字与 etcd 侧的每次提交 Sync backend 一起进 doc 7 的归因表，不混进实现质量（同 D11 的口径）。失效判据沿用 D5 的「盘上边界是否已知」，raft 日志的建新段失败不置失效标志。
- 验证：M13 的吞吐对照表给三档：单机 KV（D6 批次）、raft 每条 Sync、raft `-raft-fsync=false`；`3.2` 的用例断言 Sync 失败后 `Propose` 一律 `ErrIO`、`Get` 仍服务、进程由入口层退出。

## D20 冲突回退用 conflictTerm 与 conflictIndex

- 背景：Follower 的一致性检查失败之后，Leader 要往下调 `nextIndex` 重发。
- 备选：每次 `nextIndex--` 逐条回退（论文原写法）；响应里带 conflictTerm 与 conflictIndex 定位到该 term 的最后一条之后。
- 结论：按 doc 3 基线给出的三个分支快速回退，`nextIndex` 最小为 1；分支算出的值不比原 `nextIndex` 更小时退到 `nextIndex-1`，回退因此严格递减。
- 理由：逐条回退在一次 RPC 一个来回的前提下，日志差 N 条就要 N 轮；这一轮的注入实验会造出「旧 Leader 回归后带着一段不同后缀」的场景，逐条回退把恢复时间拉成日志长度的线性函数，这段线性回退会计进 M13 的重选主耗时。基线的响应字段里已经写了 `conflictTerm` 与 `conflictIndex`，实现它只要 Follower 能给「某 term 的第一条 index」、Leader 能反查「某 term 的最后一条 index」，两个查找在内存视图上是 O(1) 的 map。否掉的是不等回执、每次减 1 的盲目回退；提示值不递减时退一步只是兜底——本节点在冲突 term 之后又收了更高 term 的条目时，照提示值跳会让 `nextIndex` 往前挪、同一条请求被反复重发，兜底只在这一格多花一轮。
- 影响：Follower 端要维护 term 到首条 index 的映射，Leader 端要维护 term 到末条 index 的映射，raft 日志截断与追加时两个映射同步更新；`AppendEntries` 响应多两个字段，etcd 的对应字段同名，对拍时能直接比。
- 验证：`append_test.go` 的三个分支用例（冲突 term 存在、不存在、Follower 日志太短）各断言一次 RPC 就把 `nextIndex` 落到正确位置，另加一格断言冲突 term 出现在被拒位置之后时 `nextIndex` 只退一步；追加一轮断言 `success=true` 且条目一致。

## D21 保留 `cmd/miniraft-kv` 作为单机 baseline

- 背景：raft 节点起来之后，单机 KV 的二进制没有客户端流量。
- 备选：删掉单机入口，只留 raft 节点；保留，当作 raft 路径的吞吐对照。
- 结论：保留，两个二进制并存，doc 2 的测试与崩溃注入照常跑。
- 理由：`docs/0` 要求没有 baseline 的数字不进结论。raft 写的延迟里混着 RPC 往返与多数派等待，只有同一台机器上同一份 KV 与 WAL 的单机数字，才能把复制那部分开销单独量出来。删掉之后再补一个对照环境，成本比留着高。
- 影响：CI 里两套测试一起跑；`2.2` 的运行命令不变；M13 的对照表要固定写入条数与批次，两边用同一份负载脚本。
- 验证：M13 的三档吞吐（D19）里第一档由 `bin/miniraft-kv` 产生，数字能指到原始日志与负载命令。

## D22 不做 Pre-Vote，把 term 膨胀作为观测量记录

- 背景：`docs/1` 把 Pre-Vote 划成白板讲稿，不写代码。少了它，被隔离的旧 Leader 会不断推高 term。
- 备选：悄悄实现一个最小版 Pre-Vote；不做，并把膨胀量测出来。
- 结论：不做。网络分区那一格实验（doc 6）记录「旧 Leader 独走期间的 term 增量」和「分区恢复后到重新出 Leader 的耗时」两个数。
- 理由：这一项的代价本身就是要量出来的数据，代码里实现了 Pre-Vote 就量不到了。etcd 实现了 Pre-Vote，对拍时这一格有直接对照对象，差异能归到一条机制上。
- 影响：doc 6 的注入矩阵里这一格的数据要在 doc 7 出现；`3.1` §9 第二条把活锁风险写进约束。
- 验证：本轮无数值断言，M13 只跑一次分区不做的对照；正式数据在 doc 6 的注入实验里产出。

## D23 选举与复制的 RPC 在 `Tick()` 内同步串行发出，回执当场处理

- 背景：`Transport` 的签名是同步的（`RequestVote(to, req) (VoteReply, error)`），而 doc 3 基线写的是「并行向其他所有节点发送」。一次选举要给其余 4 个节点发。
- 备选：每个 peer 一个 goroutine，回执落进缓冲 channel 由下一次 `Tick()` 消费；给 `Transport` 加异步签名；保持并行语义但只在入口层起 goroutine 调 `Tick()`。
- 结论：`Tick()` 里按成员 id 升序依次调用，调用返回即计入票或计为一次失败；`Propose` 同样串行发 AppendEntries。
- 理由：D16 要的是「调 11 次 `Tick()`，第 11 次发起选举」这种断言。goroutine 扇出之后，注册与回执到达的时序进入测试路径，选举类用例只能写成「≤N 次内」，`3.2` 的超时边界那格和「2 票不选」都失去可判性。内存夹具在同一把锁下并发回调会自死锁，要再拆一层锁才能测。串行之后整个选举与复制路径单线程，`Node` 一把互斥锁够用。
- 影响：一条 RPC 卡住会拖慢当轮 tick，代价由 M12 的 HTTP 客户端超时兜住（超时取 `min(2×-tick-ms, -election-timeout-ms)`，`3.1` §9）。成员遍历按 id 升序，顺序固定，`request vote sent` 日志里的 `peer_id` 顺序可复算。doc 3 基线「并行发」的两处按本条改写，实现与测试都不引入 goroutine 扇出。
- 验证：`election_test.go` 断言一轮选举发出的投票条数与顺序；`cluster_test.go` 的分区用例靠 transport 开关让串行调用直接报错，term 膨胀值不受并发影响。
